# LubanAgent 产品需求文档（PRD）

> 文档状态：定稿（2026-07-17 全部待确认事项已决策）
> 关联文档：`../design-docs/LubanAgent-technical-proposal.md`（技术方案，回答"怎么做"；本文档回答"为什么做、给谁做、做什么"）
> 已确认决策：① 通用 Agent 底座，客服为首个验证场景，Agent 定义层必须支持灵活切换 Agent 类型；② 交付形态为完整仓库、克隆即改，用户长期住进去迭代（若依模式）；③ 直接开源做社区（Apache-2.0）；④ **产品主线为"若依式起步基座 + 自带监控"**，治理/评测/成本为基座成色而非主战场；⑤ 品牌定名 LubanAgent（鲁班）；⑥ 升级策略：每次发布提供完整变更说明，克隆用户按需拉取合并；⑦ AI 开发，不受人工投入约束——功能不分期、一次性交付完整能力（F1-F13 + 客服示例 + 最小 RAG），仅按构建依赖排序实现，不存在"暂未实现"的分期；⑧ 技术栈：Python + LangChain + LangGraph；⑨ Agent 定义：配置 + 数据库维护（运行期可改、版本化）；⑩ 首版模型：OpenAI 兼容模式配置国内主流厂商；⑪ 监控/观测采用可插拔适配器，默认集成 Langfuse（开源自部署），可选 LangSmith，不自建；⑫ 交付形态=开源核心（Apache-2.0，F1-F13 Agent 本体）+ 商用渠道层（F14-F16 消息渠道接入/会话状态机/出站风控，独立可拆卸模块，开源版不含）；架构硬约束：核心不依赖渠道层、留 `ChannelConnector` 扩展点，渠道层单向依赖核心

## 1. 产品定位

### 1.1 一句话定位

LubanAgent 是一个开源的、代码优先的 Agent 起步基座：基于 LangChain + LangGraph（Python），把模型接入、Agent 运行、工具治理、确定性流程编排、运行观测、评测、成本治理和部署打通成一个可克隆、可修改、可独立部署的完整代码仓库。**形态对标若依（RuoYi）——用户克隆后长期住进去迭代、上生产，而不是搭完就扔的实验原型**。内置智能客服作为首个完整验证场景；更换 Agent 类型只需更换 Agent 定义与 Tool 集，不改动运行时代码。

一句话类比：**若依之于 Spring Boot，LubanAgent 之于 LangChain/LangGraph**——底层框架给能力，LubanAgent 把能力组装成克隆即用、可长期迭代的完整工程。

### 1.2 定位三要素

**是什么**：一个面向 Agent 开发者的开源起步基座（scaffold），并在脚手架之上多提供一层 **Agent 定义层**：普通 Agent 的全部要素在定义层配置生成，而不是用代码编排。交付物是源码仓库，用户长期在此之上开发业务 Agent，不是平台、不是框架库、不是托管服务。

**不做什么**：

- 不做在线托管 Agent 的 SaaS 平台；
- 不做低代码/可视化工作流设计器（服务运营人员，不是开发者）；
- 不做模型、Prompt 或插件商城；
- 不做通用后台管理能力（用户、角色、权限由业务系统自己解决）；
- 不做具体业务项目（客服是内置示例与验证场景，不是产品本体）；
- **不自建观测/评测平台**——Langfuse（开源自部署）、LangSmith 已成熟，基座以可插拔适配器集成，默认 Langfuse 保住数据主权，不重复造轮子；
- **开源核心不含消息渠道层**——对接外部消息渠道（微信/飞书/钉钉等 IM、京东/淘宝/拼多多等电商客服）、会话状态机、出站风控审核属于独立可拆卸的渠道层模块，开源版不提供，商用版提供。开源用户通过框架的 `ChannelConnector` 扩展点自行接入。

**凭什么存在**：Agent 开发已从"拼 Demo"进入"交付生产系统"阶段，但 Python 生态"库多工程少"：LangChain/LangGraph 给零件，Langfuse/LangSmith 给观测评测，但**把它们组装成一个能长期迭代、能跟上游版本、自带监控的完整工程，仍然要每个团队自己拼**。LubanAgent 的产品主线就是这副"工程组装 + 长期可迭代"——以若依模式切入：用户克隆一个仓库就拿到一整套能上生产的工程骨架，自带监控开箱即用，在自己的领地里加业务 Agent 即可。治理、评测、成本是这副骨架的成色，不是主战场；清醒认识它们会被平台型工具持续追平，持久的立足点是"工程化最完整、可长期跟版、无强制 SaaS 依赖"的起步基座。

### 1.3 交付形态：开源核心 + 商用渠道层

LubanAgent 分两层交付，边界清晰、可拆卸：

| 层 | 内容 | 形态 | 谁用 |
| --- | --- | --- | --- |
| **开源核心（Agent 本体）** | F1-F13：Agent 定义层、模型工厂、Runtime、Tool/MCP、Skill、知识记忆、图编排、多 Agent、观测/评测/成本、工程基座 | Apache-2.0，完整源码，克隆即用 | 所有用户（社区） |
| **渠道层（独立模块）** | F14-F16：多渠道消息接入（IM + 电商客服）、会话状态机、出站风控审核；含官方 connector（微信/飞书/钉钉）与电商参考实现 | 独立可拆卸模块，**开源版不含，商用版提供** | 需要直接对接外部消息渠道的用户 |

**关键架构约束**：开源核心**不依赖**渠道层也能独立运行——业务系统通过 REST/SSE 调用 Agent 即可（被动模式）；装上渠道层后，Agent 能主动接入外部消息流、按会话状态机自动接待/转人工、发出站前过风控（主动模式）。依赖方向单向：渠道层 → 核心（调用 Agent Runtime），核心 → 渠道层禁止。渠道层在核心里只留扩展点（`ChannelConnector` Protocol、会话状态抽象、出站拦截 Hook），实现可整体替换或卸载。

这条边界是商业设计，也是技术设计：核心守住"通用 Agent 起步基座"的定位与开源社区信任，渠道层作为商品承载对外部消息渠道的持续维护（IM 与电商平台的接口、授权、规则变更频繁，维护成本高，不适合作开源社区资产）。

## 2. 目标用户

### 2.1 核心用户

**首要人群：需要在生产环境交付 Agent 应用的 Agent 开发者（开源社区外部用户），以 Python 技术栈为主。**

典型画像：

- 正在为业务系统构建客服、助手、分析或自动化 Agent 的研发团队；
- 对 Prompt 工程、Tool 设计、模型选型和运行治理有工程化诉求，希望站在完整基座上开发的个人开发者或小团队；
- 要求完整源码、自行修改、独立部署，不接受黑盒托管、也不希望观测数据交给外部 SaaS 的团队。

技术栈前提：工程基于 Python / LangChain 实现。Python 是实现手段而非产品定位——产品服务的是 Agent 开发本身。

### 2.2 非目标用户

- 零代码背景的运营、产品人员（应使用低代码平台）；
- 想要开箱即用的托管 Agent SaaS 的团队；
- JVM、.NET 等非 Python 技术栈团队（首期不做其他语言版本）。

### 2.3 为什么是这个人群

Python 是 Agent 开发的主流语言生态，但生态内"库多工程少"：LangChain/LangGraph 提供零件，LangSmith 把观测评测做成外挂 SaaS，CrewAI/AutoGen 重编排轻工程。要把一个 Agent 真正交付到生产环境，团队仍然要自己拼装定义管理、治理、评测、成本和部署——这批重复劳动正是 LubanAgent 要消灭的。客服是第一个验证场景：它同时覆盖知识检索、工具调用、确定性流程和人工接管，足以压测底座的全部主线能力。

### 2.4 开源社区含义

产品从第一天直接开源做社区（Apache-2.0），因此 README、快速开始、文档、示例质量与 issue 响应都是一等公民，与代码同等重要。社区的"克隆到第一个 Agent 跑通"体验是产品门面。

发布纪律：脚手架形态决定了用户克隆改造后难以自动跟进上游。每次发布必须提供完整的变更说明（CHANGELOG 与迁移指南），说明改了什么、为什么改、如何合并；用户按需拉取、自行合并所需能力。模块边界保持清晰可抽离，降低手动合并成本。

## 4. 核心价值主张：若依式起步基座，少写基础代码，专注业务逻辑

**核心就一条：用户不该重写给每个 Agent 都相同的那一大块基础工程。** 从零做一个能上生产的 Agent，工作量大头不在业务逻辑——Agent 定义层、模型接入、工具运行时、流式接口、记忆、RAG、观测、评测、部署，每个团队都在重写同一遍。LubanAgent 把这套基础工程一次性给全，用户只写三样真正属于自己的东西：**业务 Tool（Python 代码）、业务 Prompt、业务知识**。

**产品主线（主战场）：若依式起步基座 + 自带监控。** 同样是为了"少写"——这套可长期迭代的工程骨架别人不给，你就得自己拼：

1. **起步基座：克隆即用、长期迭代、可跟上游版本。** 用户克隆一个仓库就拿到一整套能上生产的工程骨架：模型工厂、Agent Runtime、工具治理、确定性流程编排、部署基座全部打通；**用户在自己的领地（业务 Tool、Prompt、Agent 定义）里开发，不碰框架领地，合并上游升级无痛**。基座还内置 spec-coding skill——规格驱动开发闭环（spec→契约提取→编码→strict-validation 严格验证），克隆即用；既是本仓库自身的开发纪律，也是用户在自己领地里开发 Agent 的可复用方法论。这是若依模式成败的单一关键点，详见架构契约（技术方案第 11 章与 `../design-docs/LubanAgent-architecture-design.md`）。回应 P3（自建框架的痛）、P5（反复重写框架攒经验）。
2. **自带监控：观测/评测开箱即用、可插拔、无强制 SaaS。** Trace、评测、Prompt 管理、playground 不自建，而是以适配器集成成熟开源方案——**默认 Langfuse（MIT、可自部署、数据不出企业边界），可选 LangSmith**。用户克隆即有监控，不必再拼。回应 P1、P2（evals 必须基于真实运行观测）、P4（成本归因）、P7（数据不出边界）。

**基座成色（入场券，非主战场——会被平台型工具持续追平）：**

3. **生产级治理成色。** 行为边界（最大步数、预算、超时）、高风险 Tool 人工确认、模型能力校验与受控降级、测试集回归与历史重放。这些是基座该有的成色，但不是差异化护城河。
4. **成本治理成色。** Token 估算前置、运行预算与超限熔断、KV-cache 友好的上下文组装（命中效果依赖厂商缓存语义）、费用可审计。同上，是成色不是护城河。

**基础价值（始终成立）：**

5. **快——第一天就写业务 Agent。** 克隆仓库、配一个模型，第一个 Agent 即可运行；模型接入、工具循环、流式接口、观测、评测、部署已经打通。
6. **通用——定义即 Agent。** Agent 的身份、指令、大脑、知识、记忆、能力、边界、契约全部定义化且版本化，存于数据库、运行期可维护；客服只是第一个场景，换成 HR 助手、运维助手只需更换定义与 Tool 集。
7. **可控——全源码、代码优先、无黑盒、无强制 SaaS 依赖。** 业务 Tool 就是 Python 代码，确定性规则（权限、金额、审批）由代码执行而非 Prompt 声明；默认观测数据留在自己库里，独立部署，数据不出企业边界（P6、P7）。

## 5. 核心功能

> 归属：F1-F13 属**开源核心**（Apache-2.0，克隆即用）；F14-F16 属**渠道层**（独立可拆卸模块，开源版不含，商用版提供）。

| # | 功能 | 解决的痛点 |
| --- | --- | --- |
| F1 | Agent 定义与版本化：身份、指令、大脑、知识、记忆、能力、行为边界、输入输出契约；定义即 Agent，更换类型不改代码；数据库存储、运行期可维护；一次运行绑定明确版本。附 **Prompt 库**：Prompt 作为独立版本化的一等实体，以 Prompt 为维度草拟、发版、版本历史与复用，可分配给多个 Agent；Agent 定义引用它时在落库前解析成版本快照内嵌全文（Prompt 新版不自动作用于引用方）。这是本仓库内的本地资产版本化管理，不是 Prompt 商城/分发市场 | P1、P7 |
| F2 | 模型中心与模型工厂：模型连接信息存数据库、固定标识引用、切换只改库中映射（不改代码不发版）；能力声明、逻辑大脑（fast/smart/cheap/vision）、按 Agent/环境/运行切换、受控降级；连接与适配代码集中在独立模型模块 | P1、P3 |
| F3 | Agent Runtime：模型-工具循环、步数/预算/超时/取消控制、统一流式事件（SSE） | P1、P4 |
| F4 | Tool 与 MCP 治理：Python Tool；MCP 双向——Client 接入外部 MCP Server 生态、自有 Tool 反向暴露为 MCP Server 供其他 Agent/IDE 调用；调用前权限与参数检查、高风险人工确认、超时/重试/幂等、独立调试与 Mock | P6、P7 |
| F5 | 运行观测：每次 Run 的完整 Trace（Agent 版本、实际模型、Prompt、工具调用、Token、耗时、费用、结束原因） | P1、P2、P4 |
| F6 | 评测体系：测试集、工具调用断言与 LLM-as-judge 评分、回归测试、录制重放、模型/Prompt 对比；基于真实运行观测数据。定位为"可用的评测起点"——evals 是行业未解难题，不做过度承诺 | P2 |
| F7 | 成本治理：上下文组装保证 KV-cache 友好不变量（稳定前缀、append-only），命中效果依赖厂商缓存语义；Token 估算前置（近似值）；运行预算与超限熔断；成本分析与优化建议 | P4 |
| F8 | 工程基座：调用入口鉴权、环境化配置、运行持久化、Docker 部署 | P7 |
| F9 | 知识与记忆：文档解析、向量化检索（可选）、会话/摘要/长期记忆策略（可选） | P5 |
| F10 | 开发者工作台：Agent 定义编辑调试、模型对比、Prompt 调试、Prompt 库管理（草拟/发版/分配/引用反查）、Tool/MCP 测试、Trace 查看 | P2、P5 |
| F11 | 图编排（LangGraph）：确定性业务流程的代码级强制——退款、审批等有固定步骤顺序的流程必须走流水线（步骤、检查点、暂停恢复、人工节点），流程正确性不靠 Skill 或 Prompt 赌 | P1 |
| F12 | Skill 能力包：兼容 Agent Skills 开放标准（SKILL.md 目录包：指令 + 脚本 + 参考资源），元数据常驻、命中后正文与资源渐进加载；Skill 可版本化、可分配给指定 Agent，把团队 know-how 与操作流程打包复用 | P5 |

| | **↓ 渠道层（独立可拆卸模块，开源版不含，商用版提供；核心通过 ChannelConnector 扩展点对接，不装也能跑）↓** | |
| F14 | 消息渠道接入层【渠道层·商用】：统一消息模型（platform/session_id/message_id/content/attachments）、多渠道 connector（微信/飞书/钉钉等 IM + 京东/淘宝/拼多多等电商客服）、渠道可靠性（幂等去重、游标补偿、长连接重连、限流削峰、授权与接口变更巡检） | P7 |
| F15 | 会话状态机【渠道层·商用】：AI 接待 ↔ 人工待接管 ↔ 人工接待 ↔ 关闭；转人工触发（低置信度/敏感词/高风险业务/接口异常/主动接管/超时未解决）；会话级/店铺级/平台级 AI 开关；与平台原生客服转交/分流接口落地 | P1 |
| F16 | 出站风控与回复审核【渠道层·商用】：AI 回复**发出前**做敏感词/违禁词/承诺风险/平台规则校验，按风险等级放行/人工复审/转人工；审核记录与 Trace 关联、可审计 | P6、P7 |

设计原则：

- 普通对话型 Agent 保持简单，RAG、长期记忆为可选能力，简单项目不被复杂组件拖累；但业务流程有强制步骤顺序时（退款、审批、工单流转），必须用图编排做代码级强制——流程正确性不交给 Skill 或 Prompt；RAG 自带防错答守门（相关度阈值 / 知识时效 / 全 miss 拒答短路，代码强制"可不答、不硬编"），拒答行为可用评测的 `expect_refusal` 硬指标回归；
- 避免"虚假通用"：Agent Definition 的字段按三类场景原型设计——客服对话型、知识助手型、审批流程型，首版只实现客服场景，用设计覆盖度保证通用性，而不是靠堆实现数量。

## 6. 功能范围

### 6.1 交付范围

**两层交付，边界清晰（见 §1.3）：**

- **开源核心（Apache-2.0，AI 一次性交付完整能力）**：F1-F13 + 智能客服示例 Agent（内置 Mock 业务服务与最小 RAG）+ 快速开始文档。功能不分期、不按人工投入收缩范围。
- **渠道层（独立可拆卸模块，商用）**：F14-F16 + 官方 connector（微信/飞书/钉钉）+ 电商客服参考实现（京东/淘宝/拼多多）。开源版不含；开源用户通过核心的 `ChannelConnector` 扩展点自行接入外部渠道，核心不装渠道层也能独立运行（业务系统走 REST/SSE 调用）。

**实现顺序（仅依赖序，非产品分期）**：先落核心领地模型与工程基座（F1-F3、F8），再落能力层与治理层（F4-F7），最后落上层编排与扩展能力（F9 知识记忆、F11 图编排、F12 Skill、F10 工作台、F13 多 Agent 协作）。这是构建依赖决定的顺序——图编排依赖 Runtime、多 Agent 依赖图编排——与"做到哪算哪"无关，AI 按序一次性全部实现。渠道层（F14-F16）作为独立模块在核心稳定后开发，依赖核心但不被核心依赖。

**运行期可选性（与分期无关）**：RAG、长期记忆、图编排、多 Agent 协作在运行期是可选能力——简单对话型 Agent 默认不启用，不被复杂组件拖累。这是用户按需启用的设计，不是"暂未实现"；但它们是一等能力，不是边缘附属。

**验收基线**：开发者克隆开源仓库、配置模型后 30 分钟内跑通客服示例，并通过修改 Agent 定义、Prompt、逻辑大脑和 Tool 构建自己的 Agent；示例自带测试集可回归；退款流水线、多 Agent 协作均有可跑示例。渠道层验收（商用）：装上渠道层模块后，能接入至少一个 IM 渠道（如飞书）跑通"消息接入 → AI 接待/转人工 → 出站风控 → 回复"完整链路。

### 6.2 明确不做

- 在线托管与多租户运营；
- 可视化工作流设计器；
- 模型/Prompt/插件商城与 Skill 公共市场（Skill 仅本地目录与私有分发）；
- 通用后台管理（用户、角色、权限体系）；
- JVM、.NET 等其他语言版本（首期不做）；
- 图片、视频等具体业务项目；
- **渠道层不开源**——消息渠道接入、会话状态机、出站风控属商用模块，不进开源仓库；开源核心只留 `ChannelConnector` 等扩展点供用户自行接入。

## 7. 差异化分析

### 7.1 先分赛道：开源 Agent 生态里的四类玩家

市面上的开源 Agent 相关项目不是同一类东西，按"设计初衷"分四类，LubanAgent 的定位要放在这个坐标系里看，而不是简单堆一张对比表：

| 赛道 | 代表项目 | 服务对象 | 给什么 |
| --- | --- | --- | --- |
| 底层编排引擎 | LangGraph、OpenAI Agents SDK | 愿意深度定制的工程师 | 状态图/循环等底层积木，不预设 Agent 长什么样，不管定义怎么存、模型怎么切、成本怎么控 |
| 多 Agent 协作框架 | CrewAI、AutoGen、MetaGPT | 算法/研究团队 | 更高层的协作抽象（角色/任务/团队），但普遍缺 Agent 定义版本化、评测回归、成本治理、部署基座 |
| 低代码/无代码平台 | Dify、n8n | 业务/运营人员 | 拖拽式配置降低上手门槛，代价是深度可控性差，确定性业务规则难以像代码一样可测试可审查 |
| 领域专用库 | LlamaIndex | 需要专业 RAG 能力的团队 | 文档解析/索引/检索的最佳实践，是可叠加组件，不是编排框架的替代品 |

**LubanAgent 的位置**：把 LangGraph 当编排引擎依赖（不重复造图引擎的轮子），在其之上补齐上述四类玩家普遍缺失的一层——Agent 定义入库版本化、模型工厂、治理层（Trace/成本/人工确认）、部署基座。差异不在"编排能力本身"，而在"编排能力之外那块每个团队都要重复拼一遍的工程"要不要用户自己拼。

选型时还有一个容易被 star 数掩盖的维度：**框架的维护状态**。例如 AutoGen 已进入相对维护阶段（微软官方新项目转向 Microsoft Agent Framework）、MetaGPT 近一年少有大更新——这类"明星项目被官方自己放弃"的情况在这个赛道会持续发生。LubanAgent 作为克隆到本地、完全掌控源码的仓库，天然规避"依赖的框架被上游放弃"的风险。

### 7.2 逐个对比

| 对比对象 | 对方的形态 | LubanAgent 的差异 |
| --- | --- | --- |
| LangChain 直接使用 | 库：模型接入、消息、Tool Calling、MCP、RAG 零件 | 零件 vs 整车：Agent 定义版本化、运行治理、评测体系、成本治理、部署基座全部给齐；LubanAgent 把它作为依赖，不是对手 |
| LangGraph | 低层编排引擎：流程拓扑用代码定义（流水线模式），不是脚手架，也没有 Agent 定义层 | 普通 Agent 在 LubanAgent 里不编排：全部要素在定义层配置（入库、版本化、运行期可改），更换 Agent 类型不改代码、不发版；业务流程有强制步骤顺序时（退款、审批）用 LangGraph 编排做代码级强制（收编为模块），不靠 Prompt/Skill 赌流程正确性。层次关系：LangGraph 是引擎，LubanAgent 是脚手架再加一层定义层 |
| OpenAI Agents SDK | 轻量优雅的编排 SDK，但原生只深度适配 OpenAI 自家模型 | 模型中立：OpenAI 兼容协议一套客户端覆盖 DeepSeek/Qwen/GLM/vLLM/Ollama 等，企业多模型/国产模型混用不受限于单一厂商生态 |
| LangSmith / Langfuse | 观测与评测平台（LangSmith 为外挂 SaaS） | 治理与评测内建在工程里：与 Agent 定义同版本、同部署、同数据库，不依赖外部 SaaS，观测数据不出企业边界 |
| CrewAI | 多 Agent 编排框架，"角色化团队"直觉设计，1 天上手 | 编排原语 vs 完整工程：给协作能力但缺 Agent 定义版本化、评测回归、成本治理、观测与部署基座，团队仍要自己拼工程。LubanAgent 把 LangGraph 的多 Agent 引擎组装进完整工程基座——多 Agent Run 与单 Agent Run 同库同治理同部署，编排能力是一等卖点而非外挂 |
| AutoGen | 曾经的多 Agent 对话框架标杆，目前处于相对维护阶段，官方新项目转向 MAF | 同上"编排原语 vs 完整工程"的差异之外，多一层框架生命周期风险的差异：LubanAgent 是克隆到本地的完整源码，不依赖某个外部框架的持续维护投入 |
| MetaGPT | 模拟软件公司角色分工自动生成代码，近一年少有大更新 | 定位完全不同：MetaGPT 是"自动编码"范式验证，LubanAgent 是"交付生产级 Agent 应用"的工程基座，不是同一类需求 |
| 低代码平台（Dify / n8n / Coze 等） | 面向运营/业务人员的可视化编排 SaaS 或自动化平台 | 面向开发者的代码优先工程：全源码、可单测、可 code review、可独立部署；确定性规则由代码保证，不靠 Prompt 或可视化节点约束。服务对象不同，不是同一类需求的替代选择 |
| LlamaIndex | RAG/知识库场景的专业最佳实践库 | 不构成竞争：LubanAgent 内置最小 RAG（够用不追求专业），知识检索是核心场景时可通过知识连接器扩展点接入 LlamaIndex 作为知识层组件，两者叠加使用 |
| 团队自研 | 每个团队自己搭一遍，并在使用中重写 | 直接继承一线实践沉淀：模型工厂处理厂商差异、KV-cache 友好设计、基于真实运行观测的 evals、失败隔离与人工确认，省去数周重复建设和重写代价 |
| 外部消息渠道接入（微信/飞书/京东/淘宝等） | 各团队自己写渠道适配、会话状态机、出站风控，且 IM/电商接口与规则频繁变更 | 开源核心留 `ChannelConnector` 扩展点保证可接入；商用渠道层提供官方 connector + 会话状态机 + 出站风控，插上即用。渠道维护成本由商用版承担，不污染开源社区资产 |

对企业而言，"定义即配置"意味着 Agent 变更不发版、全程可审计、治理统一在定义层执行、无 SaaS 依赖——这是 LubanAgent 面向企业落地的关键差异，也是它成为企业级 Agent 基座首选的理由。

选择官方 LangChain 生态作为基座的原因：LangChain 是 Python Agent 生态中模型接入、Tool、MCP、Memory、RAG 能力最完整的库，LangGraph 提供可选的图编排运行时；LubanAgent 在其上做工程化，不重复造库的轮子。

### 7.3 命中用户的核心需求差异

八类主流框架大多解决"怎么让 Agent 具备某种能力"（编排、协作、低代码搭建、知识检索），LubanAgent 解决的是一个更少被认真对待的问题——**一个团队克隆了某个框架之后，怎么把它经营成一个能长期活下去、能审计、能省钱、能换人接手、还能跟着上游版本继续升级的生产系统**：

| 维度 | 主流框架的典型用户诉求 | LubanAgent 命中的需求 |
| --- | --- | --- |
| 决策阶段 | 大多数框架解决"怎么让 Agent 跑起来" | 解决"跑起来之后怎么长期维护、审计、控成本、让团队其他人接手" |
| 对"发版"的容忍度 | 编程框架 Prompt/配置写死代码里，改了要发版；低代码平台反过来代码可控性太差 | 两头都要：配置像低代码一样运营期可改（存数据库不用发版），底层又要像代码一样可测试、可审查、可长期迭代 |
| 对数据出企业边界的敏感度 | 低代码 SaaS、部分观测平台（LangSmith）默认数据在外部 | 无强制 SaaS 依赖——默认 Langfuse 自部署，内部 DB 是唯一可信源，是企业选型的硬性红线 |
| 长期演进诉求 | 大多数框架没有"如何长期跟框架版本升级"的机制设计 | 框架/用户领地三重隔离 + `.lubanagent-upstream` 清单，解决"克隆改造后怎么合并上游更新而不冲突"这个几乎被所有框架忽视的真实痛点 |

需要诚实认识到的风险：这套"整车"定位的说服力，高度依赖"治理/评测/成本这些工程闭环能力，用户真的懒得自己拼"这个假设成立。若 Dify、LangSmith 这类平台型工具持续把这些能力做得更方便，护城河会被追平——这也是为什么 §4 明确把治理/评测/成本定为"基座成色而非护城河"，真正持久的差异点是"全源码可控、无强制 SaaS 依赖、可长期跟版"。

## 8. 成功度量

**工程指标（产品是否真的好用）：**

- 开发者从克隆仓库到跑通第一个 Agent < 30 分钟；
- 构建一个新 Agent 只需新增 Agent 定义与业务 Tool，不改动 Runtime 代码；
- 接入一个新模型只需新增 Model Definition 与工厂代码，不改动 Agent 业务代码；
- 示例 Agent 的测试集可重复回归，模型/Prompt 变更前后结果可对比；
- 每次 Run 可完整回答：用了哪个 Agent 版本、哪个实际模型、哪个 Prompt、调了哪些工具、花了多少 Token 和费用、为什么结束。

**社区指标（开源是否立住）：**

- README 与快速开始覆盖"克隆到第一个 Agent"全流程，无需读源码；
- 客服示例可作为旗舰场景被直接演示和二次改造；
- 每次发布附带完整 CHANGELOG 与迁移说明；
- 长期跟踪 GitHub star、外部 issue/PR、基于 LubanAgent 构建的公开 Agent 类型数量。

## 9. 风险与应对

| 风险 | 应对 |
| --- | --- |
| Python 生态拥挤，被质疑与官方生态重叠 | 定位是完整工程而非又一个框架：LangChain/LangGraph 是依赖不是对手；差异化聚焦治理、评测、成本与工程闭环 |
| 开源社区冷启动，无人问津 | 客服旗舰示例 + 30 分钟快速开始体验 + 围绕"若依式起步基座 + 自带监控"主线持续输出内容；先在中文 Agent 开发者社区建立认知 |
| 差异化主线被平台型工具（LangSmith、Langfuse 等）追平 | 治理/评测/成本是基座成色而非护城河；壁垒在工程完整度、可长期跟版（领地隔离 + 升级契约）、无强制 SaaS 依赖 |
| 与 Dify/MaxKB/Bisheng 等低代码自部署平台定位混淆 | 明确切割：面向开发者、代码优先、全源码可控；低代码平台面向运营、代码黑盒。README 与对外口径钉死"客服=示例非产品" |
| LangChain/LangGraph 版本快速演进带来升级成本 | 模型创建与厂商适配收敛在模型工厂等少数模块，锁定主版本并跟随社区节奏升级 |
| 用户克隆改造后难以跟进上游更新 | 框架/用户领地三重隔离（文件系统 + 依赖方向 + `.lubanagent-upstream` 清单 + CI 守卫）+ CHANGELOG 按领地分类 + UPGRADE.md 合并指令：上游不主动触碰用户领地（CI 拦截 user-owned 命中），显著降低合并冲突，不承诺任意 git merge 零冲突 |
| 观测后端切换不等价（Langfuse OTel 标准粒度 vs LangSmith LangGraph 原生更细） | 不宣传"完全等价切换"；核心七问由内部 DB 保证，后端原生细粒度差异见适配器源码 `lubanagent/observability/adapters/{langfuse,langsmith,noop}.py` 注释，诚实说明 |
| 功能膨胀成平台 | 坚持代码仓库定位，工作台只服务开发调试，不碰托管与多租户 |
| 简单项目被复杂编排拖累 | RAG、长期记忆、图编排按需启用，普通 Agent 默认不引入 |
| Prompt 承担业务安全 | 权限、审批、金额等确定性规则必须由代码执行，写入安全要求 |
| 评测能力被过度解读 | 文档与宣传口径明确"评测起点"定位，只承诺断言、评分、回归、重放四个可用能力 |
| 渠道层不开源被质疑"开源不彻底" | 明确边界：开源核心是通用 Agent 本体（任何渠道都用得上），渠道层是面向特定消息渠道的持续维护（IM/电商接口频繁变更，维护成本高）；核心可独立运行、留扩展点，不构成 vendor lock-in；商用渠道层是可选增强，非必需 |
| 渠道层与核心耦合、无法真正拆卸 | 架构硬约束：核心 → 渠道层依赖禁止，渠道层 → 核心单向依赖；核心只定义 Protocol（ChannelConnector、会话状态抽象、出站拦截 Hook），实现整体可替换或卸载；CI 用 import-linter 守卫方向 |

## 10. 决策记录（原待确认事项，已全部定案）

1. **品牌**：LubanAgent（鲁班），Apache-2.0 许可证；待执行动作：注册 GitHub 组织与 lubanagent.com / lubanagent.dev 域名（决策时核查均为空闲）；
2. **一期模型**：通过 OpenAI 兼容模式接入国内主流厂商（DeepSeek、Qwen、GLM 等）与私有化部署（vLLM、Ollama）；原生工厂按需在后续版本补充；
3. **Agent 定义维护**：配置 + 数据库——定义存于数据库、运行期可维护、库内版本化；YAML 用于初始化与导入导出；业务 Tool 用 Python 代码实现；
4. **一期 RAG**：包含最小 RAG（单知识库、文档解析、向量检索、引用），否则客服示例的产品知识问答场景立不起来；
5. **客服示例数据**：内置 Mock 业务服务（订单、退款、产品库），克隆即可跑；接真实服务的写法写进文档；
6. **调用入口鉴权**：API Key + 可插拔（可替换、可关闭，方便接入业务网关）；
7. **版本基线**：Python ≥ 3.11；数据库 MySQL 8.0+，开发期支持 SQLite 免安装；
8. **评测与成本治理**：全量交付（AI 开发，不按人工投入收缩范围），宣传口径仍为"可用的评测起点"，不过度承诺；
9. **核心价值表述**（用户拍板）：价值主线是"少写基础代码、专注业务逻辑"；生产级治理/评测与成本治理是这套基础的成色与差异化，不是替代主线；
10. **MCP 与 Skill**：MCP 做双向——Client 接外部生态、自有 Tool 反向暴露为 MCP Server，二者均交付；新增 F12 Skill 能力包，兼容 Agent Skills 开放标准（SKILL.md、渐进加载）；功能定义级用户文档 `LubanAgent-user-guide.md`（同目录）先行产出，作为产品定义评审依据；
11. **图编排**（用户拍板）：退款、审批等有强制步骤顺序的业务流程必须走流水线做代码级强制——Skill 是指令指导、效果不稳定，不承担流程正确性；
12. **多 Agent 协作**（用户拍板）：多 Agent 编排是脚手架的一等卖点，与"若依式起步基座"不冲突——LangGraph 提供编排引擎，LubanAgent 把它组装进完整工程基座（定义层 + 治理 + 观测 + 评测 + 部署）。基于 LangGraph 的受控多 Agent 协作（supervisor / 子 Agent 委派、共享状态、任务路由）纳入交付范围（F13），编排 Run 与单 Agent Run 同库同治理、同部署，不另起一套；长任务与异步运行一并交付。代码优先，不做可视化编排平台。
13. **交付形态：开源核心 + 商用渠道层**（用户拍板）：Agent 本体（F1-F13）是开源核心（Apache-2.0），完全开源；消息渠道接入（F14）、会话状态机（F15）、出站风控（F16）属独立可拆卸的渠道层模块，**开源版不含、商用版提供**。架构硬约束：核心不依赖渠道层（业务系统走 REST/SSE 调用即可独立运行），渠道层单向依赖核心；核心只留 `ChannelConnector` 等扩展点。渠道层不开源的理由：IM/电商渠道接口与规则频繁变更、维护成本高，不适合作为开源社区资产，作为商用商品承载该维护。真实需求印证：自研 AI 客服接入主流电商平台方案中，Agent 本体只占约 1/6 工作量，渠道接入/会话状态/出站风控占 5/6——渠道层正是这 5/6 的商品化沉淀。
