## 0. 结论先行

1. **这篇文章是对 LubanAgent 赛道判断的背书**：DeepSeek 的结论是"模型执行单任务越来越强，瓶颈转向人的注意力与 harness 层的会话/调度/治理"——正是"若依式起步基座 + 自带监控"占的层。他们没有做编排框架、没有做低代码平台，做的是 harness 工程基座。
2. **核心层可吸收四项思想**（均为演进方向，落在已有模块或扩展点上，不动领地契约）：异步 ReAct Loop、上下文 Inline & Spill + 链式召回、外部 Watchdog 控制回路、Fast/Slow Path 两级事件过滤。
3. **渠道层（F14-F16，商用）几乎拿到一份现成的架构需求文档**：双层架构、订阅直通、多信道交互规范、投机执行，四项全部映射到 `ChannelConnector` / `SessionStateStore` / `OutputGuard` 三个扩展点上。
4. **明确不跟三项**：存算分离 + 端侧 daemon（BYOM）、Router 层水平切分、A2A 协议——见 §4。

## 1. 原文架构速览

Super-agent 四特征：**连续**（跨信道感知为同一个 Agent）、**高效**（并行多任务、不等上一个完成）、**主动**（持续观察环境事件）、**持久**（始终在线、异常自愈）。支撑五模块：

| 模块 | 一句话 | 关键机制 |
|---|---|---|
| 双层架构 | 常驻 Router 层管交互与分派，隔离的 Worker 层并发执行 | Session 是实现细节而非用户认知负担；Router 不执行任务、可无 Bash |
| 事件驱动 | 输入从人类提示词变为环境事件（Trigger） | 两级过滤、订阅直通、Inline & Spill、投机执行 |
| 面向人的交互 | 前台对话与后台任务解耦 | 异步 ReAct Loop（start/stop）、多信道输出规范 |
| 计算/状态/环境分离 | Agent Loop 上云无状态化，执行环境留原地 | 两层解耦 + 端侧轻量 daemon |
| Watchdog | 主系统外的独立 Control Loop | 定时驱动，既探进程存活也判任务实质进展 |

## 2. 核心层可吸收的四项（按落地优先级）

### 2.1 异步 ReAct Loop（全双工交互）

**原文思想**：耗时工具调用从同步 `run()` 改为异步 `start()` / `stop()`——`start()` 立即返回 Started，循环不再阻塞；工具完成后结果作为新事件投递回会话；模型可主动 `stop()` 终止过长的后台任务。前台对话响应与后台执行解耦，新输入在当前推理步结束后即被处理。

**我们现状**：工具执行是同步阻塞的（`lubanagent/tool/executor.py` 超时+退避重试，等结果再进下一步）；会话层已有 SSE 流式（`runtime/sse.py`）与可恢复 Run + 取消传播（`graph/checkpoint.py` / `runtime/cancellation.py`），但"Run 进行中无法接受下一条用户消息"的半双工限制与原文描述一致。

**落地位置**：`runtime/agent_loop.py` 的工具调用环 + `tool/executor.py`。异步任务的"完成事件投递"可复用事件流基础设施；`stop()` 对应已有 CancellationToken，语义衔接顺。

**借鉴价值**：直接提升工作台长任务体验（评测跑批、批处理工具不阻塞对话）；也是渠道层"群聊消息不断涌入"的前置能力。

### 2.2 上下文 Inline & Spill + 链式召回

**原文思想**：把上下文窗口当 Cache 管理——Inline（近期很可能用到的信息直接进窗口，省工具往返）+ Spill（超预算/低频信息留窗外，窗口内只留引用与摘要，模型按需读取）；给 Trigger/Thread/Session 等对象唯一 ID，注入时内联紧关联对象的 ID，构成引用图，模型可沿引用逐跳按需召回（Chain of Recall）。原句："浪费上下文窗口，就是浪费模型的智能。"

**我们现状**：`runtime/context_builder.py` 负责上下文装配（教程期 R13 修复过 format_map 崩溃）；长期记忆是全量注入——`LongTermMemory.recall` 取最近 20 条全量进 system suffix（`memory/long_term.py`）；知识检索是单路向量召回，返回内容直接进上下文，无长度预算与"引用 + 按需展开"结构。

**落地位置**：`context_builder.py` 的注入策略 + `memory/long_term.py` 的召回策略。与已在途的检索纵深方案（`LubanAgent-retrieval-memory-resilience-design.md` 的记忆语义化条目）天然合流：该方案解决"召回什么"，本文补"召回后怎么按预算注入"。

**借鉴价值**：原则级设计模式，RAG / 记忆 / 多 Agent 上下文传递三处通用；不需要新框架，改注入策略即可。

### 2.3 外部 Watchdog 控制回路

**原文思想**：持久在线系统仅靠内部逻辑保证不了长期可靠，需在主系统外设独立 Watchdog Session（定时消息驱动，构成外部 Control Loop）。关键洞察：Agent 系统的异常不只是进程崩溃，还有"模型陷入无效循环或方向偏离"——Watchdog 既探基础设施存活，也由模型判断各 Worker 是否有实质进展；维护者可用自然语言向它询问故障、让它在线修正主系统行为（增删提示词、调整触发规则）。

**我们现状**：治理四件（步数/预算/超时/取消）都是**限额式**治理——只能拦"超限"，拦不住"没超限但在空转"；Trace 是旁路双写（DB + Langfuse），只记录不判断；没有独立于主循环的进度判断回路。

**落地位置**：可作为可插拔治理件的新成员（治理层现有 BudgetGuard / CancellationToken 的同层扩展），消费 Trace/Run 状态做周期性判断；与"自带监控"卖点直接咬合——监控发现问题、Watchdog 闭环处理。

**借鉴价值**：把"基座成色"的治理从限额式升级为**进度判断式**，这是与竞品基座拉开差距的点。

### 2.4 Fast / Slow Path 两级事件过滤

**原文思想**：环境事件流"高噪音、低触发率"，对每条事件都调大模型判断不可承受。借鉴计算机系统 Fast Path / Slow Path：确定性、稳定的高频判断固化成代码（来源/白名单/群组范围等准入规则，先滤掉大部分），只把需要语义理解的候选事件交给 LLM 按提示词策略判断；语义层同时是面向人的自然语言扩展点（加策略 = 加提示词）。

**我们现状**：产品哲学完全同构——"确定性规则（权限/金额/审批）由代码执行，不靠 Prompt 声明"（AGENTS.md §2.2）。但目前该原则只落在权限/审批，未上升为事件/输入处理的通用模式。

**落地位置**：开源核心内主要是**写进架构设计文档作为通用模式**（指导后续事件类功能）；真正的主战场在渠道层入站风控（见 §3）。

## 3. 渠道层蓝图映射（F14-F16，商用，不在本仓库）

原文五个模块中有四项直接是渠道层的架构需求，立项时以此文为骨架出草案：

| 原文机制 | 渠道层落点 | 要点 |
|---|---|---|
| 双层架构（Router/Worker） | 会话状态机 + 消息路由 | Router 只管交互与分派不执行任务；用户跨 IM/电商信道感知"始终只有一个 Agent"，底层 Session 对用户透明 |
| 订阅直通 | `SessionStateStore` 扩展点承载 Thread→Worker 订阅关系 | 新任务冷启动走 Router，已归属 Thread 的后续事件程序直通 Worker，不绕全局节点 |
| 多信道交互规范 | `OutputGuard` 出站风控按信道配置 | IM 低打扰（原文验证过的硬规定：单次回复 ≤100 词）；邮件/工单等异步信道走结构化高密度交付 |
| 两级事件过滤 | 入站风控 | 程序层准入（白名单/来源/范围）+ 语义层策略（提示词可扩展），噪声消息不烧模型 |
| 投机执行 | 客服场景"静默预处置" | 用户还在描述问题时后台先检索/核对，确认后才应答，否则保持安静 |

核心侧只需保证扩展点语义够用（这正是"核心不依赖渠道层、留扩展点"契约的验证案例）；本文档不为此改核心代码。

## 4. 明确不跟的三项

| 项 | 理由 |
|---|---|
| 存算分离 + 端侧 daemon（BYOM） | 面向个人开发机间歇在线的场景；LubanAgent 是服务端部署基座，Run 已入库持久化（可恢复运行），无对应痛点 |
| Router 层水平切分 / 多层过滤 | 原文自己的开放问题（§8.1），实验也表明单常驻 Router + 批处理在团队规模下够用；无场景不预设计 |
| A2A 协议 | 开发计划已有同结论观察项（MCP 双向已覆盖当前需求）；原文也只列为开放问题未给方案 |

## 5. 支撑决策的实验数据要点（原文 §7）

- **双层架构 vs 单 Session + Subagent 工具**（约 300 条消息、20 条工作请求 × 5 次）：Super-agent p50 12.4 分钟 / p95 15.7 分钟；单 Session 在中性提示下 5 次运行一次都没调用 Subagent（p95 29.5 分钟），提示优先委派仍有 1 次长尾。结论：靠提示词让模型"临场判断分不分工"不可靠，**系统层面固定职责分工**（Router 不执行、Worker 只收订阅消息）才稳定——这对我们的多 Agent 编排定位是直接支持：编排在系统层，不靠 Prompt 恳求。
- **订阅直通**：不改变任务完成时间，但 Router 决定次数 +30% 场景下读缓存 token 从 2323 万增至 3177 万（+37%）——直通是纯省 token 机制。
- **Router 批处理**：Trigger 到达速率从 1 条/分钟提到 40 条/分钟，batch 从 1.0 升至 2.8，单请求耗时仅 2.5s→3.9s，单决定分摊推理时间 6.4s→1.6s——单常驻 Router Session 的吞吐瓶颈比直觉远。
