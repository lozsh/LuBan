# Spec Coding

## 目标

两条路径，**正向为主，逆向为辅**：

- **正向（意图 → 契约 → 代码）**：把开发意图落成**契约**（载体随宿主，见「契约载体」），按契约编码，经独立 strict-validation subagent **一趟合并校验**「代码是否符合契约」+「资产文档是否符合代码」，默认 FAIL，迭代至 PASS。
- **逆向（代码 → 资产目录，同步模式）**：正向 PASS 后，主 agent 判断本轮改动是否触及资产目录 `docs/specs/` 已登记的事实；命中则派 worker subagent 把契约/决策同步进 `docs/specs/`，再经独立 subagent 校验「资产目录 vs 代码事实一致」。

**完成条件不是"代码写完"，而是契约经独立严审 PASS，且触及的长期事实已同步进资产目录**——下一个人（或下一次任务）打开 `docs/specs/` 就能理解现状，不用翻聊天记录或读任务目录。

## 全流程一览

```
正向（默认路径）：
  F1 前置检查/选契约载体 → F2 proposal（意图与范围）→ F3 契约提取 → F4 按契约编码
  → F5 门槛检查 → F6 资产同步判断闸门（未命中记一句理由，只跑 Section A）
  → F7 严格验证闭环（合并校验：代码 vs 契约 + 文档 vs 代码）→ F8 收尾归档

逆向（文档同步，两条触发）：
  R0  F6 闸门命中后同步（默认，最高频；验证并入 F7 Section B，不单独跑 R3）
  R0' 用户直接要求"更新文档/同步文档/初始化 docs/specs/"
      → R1 同步执行 → R2 门槛检查 → R3 严格验证闭环

改动极小（单行修复、typo）：跳过 F1-F4（契约一句话记在最终回复里），但 F6/F7 不豁免。
```

## 契约载体（随宿主，不重造轮子）

契约 = 本次改动的**可验证事实清单**（接口/数据/行为/边界/验收）。编码前契约必须存在且具体——这是不变量；**载体三选一**：

| 场景 | 载体 | 说明 |
|---|---|---|
| 宿主已有 plan-mode 工作流（项目 CLAUDE.md 约定"先计划后执行"） | **plan 文件**（如 `~/.claude/plans/*.md`） | plan 文件兼任 proposal + contract；F1/F2 的两轮询问合并为 plan 批准一次；不建任务目录 |
| 纯 skill 调用、无 plan mode（脚本/cron/其他 IDE） | **任务目录** `.spec-coding/changes/<change-id>/` | proposal.md + contract.md + tasks.md + review.md，完整结构见下 |
| 改动极小（单行修复、typo） | 无（在最终回复里记一句契约即可） | 但验证闸门 F6/F7 不豁免 |

判定规则：看宿主项目约定，不看个人偏好。plan 文件里必须包含等价于 contract.md 的具体契约段（签名/字段/验收），否则视为契约缺失，先补契约再编码。

## 两个目录，职责分明

| | 任务目录（可选载体） | 资产目录 |
|---|---|---|
| 路径 | `.spec-coding/changes/<change-id>/` | `docs/specs/` |
| 生命周期 | 一次开发任务，完成后归档 | 长期沉淀，随项目演进持续更新 |
| 是否入库 | 否（gitignore，过程产物） | 是（版本化，source of truth） |
| 内容形态 | 本次任务的意图/契约/步骤/审查记录 | 按模块组织的当前系统事实 |
| 读者 | 主 agent、strict-validation subagent（本轮） | 任何人、任何时刻打开都能看懂 |

**任务目录结构**：

```
.spec-coding/changes/<change-id>/
├── proposal.md   # 意图：为什么做、做什么、不做什么（一屏读完）
├── contract.md   # 契约：接口/数据/行为/边界/验收（source of truth，编码与审查都对照它）
├── tasks.md      # 实现清单：checklist + 审查轮次记录
└── review.md     # strict-validation 每轮报告（滚动追加）
```

`<change-id>` 用 kebab-case 描述本次任务（如 `add-refund-approval`），不用日期或流水号占位。

**资产目录结构**：

```
docs/specs/
├── index.md            # 系统一句话定位 + 模块导航表
├── glossary.md          # 跨模块术语（只放两个模块以上都要用的概念）
└── modules/
    └── <module>.md      # 单模块规格全貌：定位/接口/数据/行为/边界，一个文件读完一个模块
└── risks.md             # 跨模块长期风险登记 + 复盘（不放一次性排查过程）
```

模块文件是资产目录的核心：一个模块的接口契约、数据模型、行为规则、边界约束都在同一份文件里，不拆到多个目录，减少人和 AI 来回跳转拼图的成本。

## 核心约束（两路径共用）

- 目标目录必须已存在且是 Git 仓库；不是则停止，提示先 `git init`。
- **契约是编码的 source of truth，资产目录是系统现状的 source of truth**：正向以契约为准校验代码；逆向以代码事实更新资产目录。不编造——找不到证据保留 `[TODO: ...]` 并注明原因。
- **契约螺旋演进（不是瀑布）**：编码中发现契约缺口是常态，不是违规。处置规则：
  - **技术性细节**（参数默认值、错误码选择、字段命名、实现次序等不改变用户可感知行为的）→ 主 agent 自主决策，继续编码，**事后补记进契约**（决策 + 一句理由）；
  - **方向性选择**（改变用户可感知行为、影响范围边界、不可逆决策）→ 停下来问用户，答案写进契约再继续。
  - 判定口诀：这个决策用户半年后回看会不会有意见？会 → 问；不会 → 自主定 + 补记。
- **任务目录轻量、一次性**（仅在使用任务目录载体时）：只服务本次任务，完成后整体移入 `.spec-coding/changes/archive/`，不追求"写全"，够支撑本轮编码与审查即可。
- **资产目录精炼、长期有效**：只登记跨任务仍然成立的事实（接口/数据/行为/边界/长期风险），不登记单次任务的过程细节、排查记录、临时决策草稿。
- **禁止空泛话术**：去掉后信息量不变的句子不写；代码注释/提交同理。
- **主 agent 主导整条闭环**，不外包给单个 subagent 连续执行；只有边界清晰、写入范围明确的局部工作才拆给 worker subagent。
- **worker subagent 与 strict-validation subagent 是两种角色，不可混用**：worker 做局部取证/补文/补码/同步，**不能宣布通过/失败、不能输出 Recommended Verdict**；strict-validation 只审稿取证、不改文件不补码。
- **strict-validation 默认偏向 FAIL**：犹豫时选 FAIL。只有强证据表明已达可交付水平才建议 PASS。
- **派发 reviewer 必须带"改动事实清单"**：不给编码过程上下文，但要给足本轮改动的客观事实（改了哪些文件、新增了什么字段/端点、语义约定），reviewer 才知道核对什么。空派发（只给路径不给事实）不合格。
- 每次进入严格验证前必须**回到主 agent**：汇总本轮修改、更新进度载体（tasks.md 或 plan 文件）、确认门槛检查结果后，再**新开**独立 strict-validation subagent，不复用 worker 或上一轮 reviewer。
- 大仓库默认增量推进，不做无边界全仓扫描。**但改动点驱动的核对有盲区**（没碰的角落漂移永远发现不了）：每累计 5 次资产同步（R1），跑一次全仓漂移抽查——重点核对 `docs/specs/index.md` 与各模块文件里的**计数类声明**（表数/仓储数/错误码数/端点数/测试数）与低成本的 grep 可验断言；发现漂移修正后在 `.spec-coding/progress.md` 记一笔。
- **无内部依赖**：不依赖任何内部 DB 查询、知识库、skill 市场工具。数据模型从 ORM/migration/DDL 代码取证；外部依赖从 import/require/配置取证；参考文档由用户提供文本或公开 URL。
- 只有两种合法终止状态：① strict-validation 不再给 blocking findings 且主 agent 基于证据判定通过；② 存在客观阻塞（事实来源缺失/用户未授权覆盖/仓库事实本身缺失）且已在最终说明写清楚。

## 提问交互规范

- 每次询问都带 chat 输入框（用户随时可额外交流）；skill 自定义项可是选项或输入框。
- **自由输入场景直接给输入框**，不再多一层"其他"引导。
- 选项不超过 5 条；输入框给清晰提示。
- **Claude Code** 用 `AskUserQuestion`；**其他 AI IDE** 用当前工具支持的询问方式，chat 输入框须显式提供。

记法：`[选项：xxx]` 点击选项；`[输入框：xxx]` 带提示输入框。

# 正向路径：意图 → 契约 → 代码

## F1. 前置检查与载体选择

```bash
ls .git/          # 不是 Git 仓库 → 停止，提示 git init
```

**先定契约载体**（见「契约载体」节）：读宿主项目 CLAUDE.md/AGENTS.md——

- 约定了"先计划后执行"（plan mode）→ **载体 = plan 文件**：探索代码库、把意图+范围+**具体契约**（接口/数据/行为/边界/验收）写进 plan 文件，一次批准（范围确认与契约确认合并，不再 AskUserQuestion 二连击）。
- 无此约定（脚本/cron/其他 IDE）→ **载体 = 任务目录**：

询问本次要做什么（不假定用户已有 spec 文档）：

```
本次要实现什么？可以是一句话意图，也可以直接给 PRD/技术方案/开发计划链接或路径。

[输入框：描述你要做的事，或粘贴/填写 spec 文档路径]
[选项：先看看 docs/specs/ 里已有哪些模块，再决定怎么做]
```

- 用户给了 spec 文档路径/URL → Read 读取。
- 用户只给一句话意图 → 直接进入下一步，由主 agent 结合 `docs/specs/`（若存在）与代码现状生成候选范围，供用户确认。
- 读取失败 → 立即询问并写明错误原因，给 `[选项：继续（跳过该文档）]` / `[选项：重试]`。

从意图/spec 提炼一个 kebab-case `<change-id>`，创建任务目录：

```bash
mkdir -p .spec-coding/changes/<change-id>
```

若 `.spec-coding/changes/<change-id>/` 已存在 → 询问 `[选项：继续未完成的任务]` / `[选项：换个 change-id 新建]`。

## F2. proposal（意图与范围）

**plan 文件载体**：plan 文件的 Context/背景段即为 proposal，无需单独产物。

**任务目录载体**：从 `assets/changes/proposal.md` 读模板，一屏写完：

```markdown
# Proposal: <change-id>

## 意图
[为什么做这件事，一到两句]

## 范围
做：
- [要做的事，逐条]
不做：
- [明确排除的事，逐条]

## 涉及模块
- [模块名]（`docs/specs/modules/<module>.md` 若已存在则读取作为现状基线；不存在则视为新模块）
```

展示给用户确认：

```
[选项：确认，开始提取契约]
[输入框：调整范围]
```

## F3. 契约提取

对本次任务涉及的功能，从 spec/意图 + 现有 `docs/specs/modules/<module>.md`（若存在）提取契约，写入载体（plan 文件的契约段 或 任务目录 `contract.md`，后者从 `assets/changes/contract.md` 读模板）。契约是 reviewer 校验代码的唯一依据，**必须具体、可验证**，字段与写法见 `references/spec-driven-guide.md`。至少包含：

- **接口契约**：函数/类/API 签名、参数与返回类型、错误情况。
- **数据契约**：数据模型字段/类型/约束。
- **行为契约**：核心流程步骤、状态转换、前置/后置条件。
- **边界契约**：硬约束（权限、超时、预算、依赖方向等），代码必须遵守。
- **验收标准**：可实跑验证的条件（测试用例、curl、性能阈值）。
- **存疑项**：不明确处，列决策清单逐条询问用户，决策写入契约。

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
正在提取契约：<change-id>
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  接口契约 ✓ / 数据契约 ✓ / 行为契约 ✓ / 边界契约 ✓ / 验收标准 ✓

  → 存疑项决策清单（若有）：
     1. [未明确处] → [选项：...] / [输入框：...]
  → 展示契约摘要，询问（plan 文件载体并入计划批准，跳过此问）：
     [选项：通过，开始编码]
     [输入框：指出契约需修改处]
```

契约核查通过后才编码。

**契约质量铁律**：
- **不变量必须可判定**——每条契约要能写成"给定输入/存储，真或假"的断言；形容词（"可靠的""一致的""高性能"）不算契约，改成可验证条件。
- **任务涉及持久化/异步/可恢复/并发**时，契约按 10 模式速查表逐条过（intent 记录先行、provisioned id、状态=记录规约、mutation line、成本账本解耦、append-only 上下文、声明式 replay……），见 `references/harness-v2-analysis.md` §1。
- **任务本身是"写技术方案/设计文档"**时：方案即契约载体，按 §2 方案模板 8 步产出——范围+Non-goals 钉死 → 概念+可判定不变量 → 记录目录定死（完整类型定义）→ trace+crash 位点表 → 伪代码即规格 → API 所有权表（未实现显式拒绝，禁止假装成功）→ 测试分层随包验收 → 依赖合并顺序收尾。产出后照常走 F4-F8。

## F4. 按契约编码（螺旋演进）

**plan 文件载体**：主 agent 按计划实施，进度用宿主任务工具（TaskCreate/TaskUpdate）跟踪，等价于 tasks.md。

**任务目录载体**：从 `assets/changes/tasks.md` 读模板，把契约拆成 checklist 写入 `tasks.md` 再实现，完成一项勾一项。

编码纪律（两种载体通用）：

- **逐字对照契约签名**：接口签名、参数名、类型与契约一致。偏离按「契约螺旋演进」处置——技术性细节自主定 + 契约补记；方向性选择问用户。
- **边界硬约束由代码强制**：不靠注释或 Prompt 声明。
- **每完成一项自检**：跑该项验收标准（测试/curl/类型检查）。
- **只写契约范围内的事**：发现缺口按演进协议处置，不擅自扩。
- 遵守仓库既有代码风格，读周边代码再下笔。
- **编码结束、进入验证前，把编码期发生的契约演进（自主决策 + 理由）补记进契约载体**——reviewer 和后续维护者要能看到完整决策链。

大任务可拆 worker subagent 并行实现不同文件，但**主 agent 负责契约对齐与集成**；多 worker 不改同一文件。

---

## F5. 门槛检查

```bash
bash <skill根目录>/scripts/verify.sh <目标仓库> --mode forward
```

正向门槛：类型检查 / lint / 单元测试通过（按仓库实际工具链探测，见 `spec-driven-guide.md`）。只做最低门槛，**不能代替严格验证 subagent**。通过后回到主 agent 更新 `tasks.md`。

---

## F6. 资产同步判断闸门（强制，编码完成后、严格验证前）

正向编码完成后、进入严格验证前，主 agent 必须思考本轮改动是否触及 `docs/specs/` 里已登记（或应登记）的长期事实。判断四类命中（任一命中即触发同步）：

| 改动触及 | 触发同步 | 举例 |
|---|---|---|
| 接口契约 | 是 | 新增/改函数签名、API 路由、错误码 |
| 数据契约 | 是 | 新增/改字段、ORM、migration |
| 行为契约 | 是 | 改流程步骤、状态转换、前置/后置条件 |
| 边界契约 | 是 | 改依赖方向、权限、超时、预算硬约束 |

- **命中** → 主 agent 判断影响到哪些 `docs/specs/modules/<module>.md`（或需新建模块文件）→ 派 **worker subagent** 执行 §R1 同步（给契约载体路径 + 改动事实清单 + 受影响模块路径，只做局部同步，不扩权）→ 同步完成后进入 §F7 **合并验证**（Section A + Section B 一趟）。
- **未命中**（纯实现细节、等价重构、修 bug 不动契约）→ 记一句理由写进进度载体，只跑 F7 Section A。

判断由主 agent 做，不外包；同步执行可拆 worker subagent，主 agent 负责范围对齐与最终收口。

**漂移抽查计数**：每次命中并完成同步，累计 +1（记在 `.spec-coding/progress.md`）；累计达 5 次，本轮 F7 验证 prompt 追加 Section C——全仓计数类声明抽查（表数/仓储数/错误码数/端点数/测试数 vs 代码实测），完成后计数清零。

---

## F7. 严格验证闭环（一趟合并：代码 vs 契约 + 文档 vs 代码）

F6 闸门已过（命中则 worker subagent 已完成同步），此时**一趟**验证：

```
主 agent 新开独立 strict-validation subagent，派发 prompt 包含：
  ① 契约载体路径（contract.md 或 plan 文件）
  ② 本轮改动事实清单（客观陈述：改了哪些文件/新增了什么字段端点/语义约定——不灌编码过程）
  ③ 代码路径 + 受影响的 docs/specs/ 文件路径
    ↓
reviewer 一趟输出两 section 的报告：
  Section A：代码 vs 契约（接口/数据/行为/边界/验收逐条核对）
  Section B：文档 vs 代码（docs/specs/ 受影响文件的事实准确性）
  总结论：PASS / FAIL + blocking findings
    ↓
FAIL → 按 blocking findings 逐项修（代码/文档/契约——契约的方向性修改须用户确认）
     → 回主 agent 更新进度载体 → 重新新开独立 subagent（不复用）
     → 重复直到 PASS 或客观阻塞
    ↓
PASS → 进入 F8 收尾
```

核查重点（详见 `references/review-agent.md`）：代码是否实现契约全部接口/数据/行为？是否违反边界硬约束？验收标准是否真的通过？文档声称与代码事实是否一致、有无过度声称？

**持久化/异步系统的验收强化**：此类系统的验收标准按三层设计，reviewer 按 Tier B 核查（详见 `references/harness-v2-analysis.md` §1.10）——Tier A 预填崩溃前缀测恢复、Tier B 逐行断言写入顺序与 trace 一致、Tier C 确定性步进（注入边界逐步驱动）+ 机械崩溃矩阵（每步快照、全部重开、每个跑两遍）。散文化的"覆盖了异常场景"不算验收。

**为什么合并**：代码事实和文档声称核的是同一批代码，两趟独立 subagent 各自重新取证是重复劳动；一趟两 section 省一半 token 与墙钟，且同一 reviewer 对代码的理解是连续的。若本轮 F6 判定未命中（无文档同步），则只跑 Section A。

---

## F8. 收尾与归档

- **任务目录载体**：验证通过后归档：

```bash
mv .spec-coding/changes/<change-id> .spec-coding/changes/archive/$(date +%Y-%m-%d)-<change-id>
```

`.spec-coding/` 整体 gitignore（若宿主 `.gitignore` 尚未包含，追加一行 `.spec-coding/`），归档只为本地留痕方便回溯，不入库。

- **两种载体都要**：在 `.spec-coding/progress.md` 追加一行任务记录（change-id / 一句话内容 / 验证轮次与结论 / 契约载体类型）。progress.md 是跨任务的批次进度登记（哪个单元到哪、PASS 到第几轮、关键决策一句话），长周期开发的主线记忆，与任务目录同 gitignore、本地留存。

# 逆向路径：代码 → 资产目录（同步模式）

逆向路径有两种触发方式，动作一致：

- **R0. 由 §F6 闸门触发**（默认、最高频）：契约载体（plan 文件或 `contract.md`）作为同步依据，直接进入 R1；同步后的验证并入 §F7 合并验证（Section B），不单独跑 R3。
- **R0'. 用户直接要求"更新文档/同步文档/初始化 docs/specs"**（无任务目录场景）：先 `ls docs/specs/ 2>/dev/null` 看是否已有资产；已有则询问 `[选项：增量更新（只改漂移部分）]` / `[选项：重新生成指定模块]`；全新则询问要覆盖哪些模块，再进入 R1（此时以代码现状为依据，无契约可用，验证走 R3）。

## R1. 同步执行（worker subagent 或主 agent 直接做）

取证与填充步骤见 `references/code-to-docs-guide.md`。核心动作：

1. **确定受影响模块**：`docs/specs/modules/<module>.md` 已存在则读取作为基线，做增量更新；不存在则从 `assets/docs/specs/modules/_module-template.md` 起新建。
2. **填充/更新模块文件**：定位、接口、数据模型、行为（状态机/流程）、边界规则——只写本轮改动涉及或明显过期的部分，不做无关的全量重写。
3. **术语**：本轮新增的跨模块概念（两个以上模块都要用到）才写入 `docs/specs/glossary.md`；只在单模块内用的术语写在模块文件里。
4. **风险**：本轮暴露的长期性风险（非一次性任务过程问题）才写入 `docs/specs/risks.md`；一次性排查过程写进进度载体（tasks.md 或 plan 文件），不进资产目录。
5. **导航**：新增/删除模块时同步更新 `docs/specs/index.md` 的模块表。

**只写有据可查**：每项指向具体代码路径/行号或契约明确表述。找不到保留 `[TODO: ...]` 并注明原因。**禁止空泛话术**：一句话去掉后信息量不变就不要写。**章节锁定**：模块文件章节以 `assets/` 对应模板的 `TEMPLATE-LOCK` 清单为准，不新增/改名/调序模板外章节。

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
正在同步资产目录
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  [1/N] docs/specs/modules/<module>.md ✓
  [2/N] docs/specs/glossary.md ✓（若有新增术语）
  [3/N] docs/specs/risks.md ✓（若有新增风险）
  [4/N] docs/specs/index.md ✓（若有导航变化）

  → 展示摘要，询问：
     [选项：通过，进入严格验证]
     [输入框：指出需要修改的内容]
```

## R2. 门槛检查

```bash
bash <skill根目录>/scripts/verify.sh <目标仓库> --mode sync
```

逆向门槛：`docs/specs/` 最小结构完整 + 关键占位已替换。通过后回主 agent。

## R3. 严格验证闭环（独立触发的逆向同步用；F6 触发的并入 F7 Section B）

```
主 agent 新开独立 strict-validation subagent（给代码路径 + docs/specs/ 受影响文件路径 + 改动事实清单，不给同步过程上下文）
    ↓
reviewer 输出报告（PASS / FAIL + blocking findings）
    ↓
FAIL → 按 blocking findings 逐项修 docs/specs/ → 回主 agent
     → 重新新开独立 subagent（不复用上一轮）
     → 重复直到 PASS 或客观阻塞
    ↓
PASS → 若由 §F6 触发（已并入 F7，不到这里）；独立触发则直接输出完成摘要
```

逆向核查重点（详见 `references/review-agent.md` 逆向模式）：抽查文档声明对照代码验证事实准确性；复核 `[TODO]`/占位符合理性；核查模块文件与 `index.md`/`glossary.md` 是否闭环。默认 FAIL。

## 填充/编码原则（两路径共用）

- **正向**：契约为准，逐字对照签名；边界硬约束代码强制；只做契约范围内事；编码期契约演进按技术性/方向性分流处置。
- **逆向**：只登记长期有效事实；只写有据可查；找不到保留 `[TODO: ...]` 并注明原因。
- **不确定就问，但先分类**：方向性不明确 → 问用户；技术性不明确 → 自主定 + 契约补记（见「契约螺旋演进」）。
- **标注惯例**：`[已从代码提取]` 有明确代码证据；`[待人工核查]` 推断可能不准；`[TODO: ...]` 找不到证据需人工补充。

## 常见错误

**目录与流程**：
- 不是 Git 仓库就开始 → 停止提示 `git init`。
- 契约未经核查就编码 → 门闸必须遵守。
- **宿主已有 plan mode 还硬建任务目录**（或反之）→ 载体按宿主约定选，见「契约载体」。
- **plan 文件里只有方案没有具体契约**（无签名/字段/验收）→ 等价于契约缺失，先补契约段再编码。
- 任务目录里塞长期资产（模块全貌、跨任务术语）→ 应该同步到 `docs/specs/`，任务目录只服务本次任务。
- 资产目录里塞一次性排查过程 → 应该留在进度载体。
- PASS 后不判断是否同步资产 → §F6 闸门必须过，未命中也要记一句理由。
- 任务完成不归档 → 长期堆积在 `.spec-coding/changes/` 根目录，应移入 `archive/`。
- 任务完成不在 progress.md 记一行 → 跨任务主线记忆断裂。
- 同步累计 5 次不跑漂移抽查 → 存量漂移（计数差一、枚举漂移）永远发现不了。

**契约与编码**：
- 契约空泛（"实现用户功能"）不可验证 → 必须具体到签名/字段/步骤/验收标准。
- **把所有契约偏离都当违规**（停下来问用户）→ 技术性细节自主定 + 补记；只有方向性才问。
- **把所有契约偏离都自作主张**（方向性也不问）→ 改变用户可感知行为的必须问。
- 边界硬约束靠注释/Prompt 声明不靠代码 → 必须代码强制。
- 越界实现契约外功能 / 遗留契约内未实现项 → 严格对照契约。
- 验收标准没真跑就说通过 → 必须实跑。

**资产同步**：
- 模块文件生成了模板外章节 → 禁止，章节以 `assets/` 的 `TEMPLATE-LOCK` 为准。
- 全量重写整个模块文件而非增量更新命中部分 → 只改本轮涉及或明显过期的部分。
- 枚举值只写"见代码" → 必须列出所有值。
- 空泛话术 → 替换为指向具体代码位置/枚举/系统名/角色的描述。

**审查**：
- review subagent 复用编码/同步过程上下文 → 必须新开独立 subagent。
- **派发 reviewer 只给路径不给改动事实清单** → reviewer 无从下手或漏核；必须给客观事实。
- 把 `verify.sh` 通过当最终验收 → 仍需 strict-validation subagent。
- strict-validation 给 blocking findings 主 agent 没返工或没复审 → 不合格。
- **同一轮改动跑两趟独立 reviewer**（一趟核代码一趟核文档）→ F7 合并验证一趟两 section，除非逆向独立触发。
