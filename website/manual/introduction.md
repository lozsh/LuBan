# 项目介绍

## LubanAgent 是什么

**LubanAgent 是一个可以直接拿来改的 Python Agent 项目。** 模型接入、工具调用、知识库、多 Agent 协作、管理界面、监控和部署已经放在同一个仓库里。你下载源码，接上自己的业务，部署到自己的服务器。

这里的 **Agent**，指的是“能理解用户要求，再调用工具完成任务的 AI 助手”。例如订单助手不只是解释退货政策，还能查询真实订单、检查能否退货，并在获得批准后提交退款。

LubanAgent 提供运行这个助手的工程，不提供你公司的订单系统，也不会替你定义退款规则。它适合想用代码开发、并且长期维护这类系统的团队。

## 先看一个例子：做一个订单助手

用户问：“我买的鞋子还没发货，能退款吗？”要完成这个任务，光把问题发给大模型不够：

1. **知道事实**：查询订单状态，读取退款政策，不能让模型猜。
2. **执行操作**：计算可退金额，调用退款接口。
3. **遵守规则**：不满足条件就拒绝，需要人工批准的操作不能直接执行。
4. **能被维护**：出了错能查记录，改了规则能测试，服务能部署和升级。

**它已经提供的**：连接模型与工具的执行程序、知识检索、审批入口、运行限制、调试界面、调用记录、评测和部署配置。

**你需要写的**：查订单和退款的业务接口、退款资格与金额规则、助手的人设，以及证明它做得对的测试用例。普通助手的配置可以在工作台修改；定义保存在数据库中，YAML 文件只是初始化导入口。业务工具和必须按顺序执行的流程用 Python 写。

仓库自带[智能客服示例](./features/demo.md)，方便对照实现。你也可以做内部知识助手、工单分流、报销审批等系统；客服只是示例，不是产品的使用边界。

## 为什么要用它，而不是从零写

一个助手要长期给用户用，至少要回答五个问题：**它知道什么、能做什么、按什么规则做、做过什么、怎样持续维护。** 这些问题不只属于提示词，也属于软件工程。

直接用模型 SDK 或 LangGraph，你可以自己选择并组装这些部分。LubanAgent 的价值是把常用部分先接好，让你从业务开发开始，而不是先做一轮数据库、执行程序、管理页面和部署脚本的搭建。

你得到的不是一个只能照着运行的演示，也不是只能在网页里配置的托管平台，而是一份可以修改的完整源码。业务代码放在 `app/`，框架代码放在 `lubanagent/`；后续按升级指引合并更新，减少两者互相影响，但不保证每次合并都没有冲突。

如果熟悉 Java 生态，可以类比**若依式起步项目**：不是只给你一个库，而是给你一份可以继续开发的工程。LubanAgent 聚焦 Agent，不做通用企业后台；但它为自身工作台提供登录、平台角色和权限控制。这不是租户、部门或行级数据隔离。

## 项目包含什么功能

下面列的是仓库已有的能力。每个链接都对应使用方式和限制，不需要先掌握所有模块才能开发第一个助手。

| 你要解决的问题 | 项目提供的功能 | 实际能做什么 |
| --- | --- | --- |
| 怎么定义和调整助手 | [Agent 定义与版本](./features/agent-definition.md)、[Prompt 库](./features/prompt-library.md)、[模型管理](./features/models.md) | 保存助手的人设与可用工具，保留修改版本；复用提示词；换模型时调整配置，不必把模型名写死在业务代码里 |
| 怎么让助手处理任务 | [Agent 执行](./features/runtime.md)、[确定性流程](./features/graphs.md)、[多 Agent 协作](./features/multiagent.md) | 简单任务由一个助手处理；固定步骤由代码执行；复杂任务分给多个助手。支持流式响应、取消，以及有检查点的运行显式续跑 |
| 怎么连接数据和业务 | [业务工具与 MCP](./features/tools-mcp.md)、[Skill 能力包](./features/skills.md)、[知识与记忆](./features/knowledge-memory.md) | 调用你写的 Python 函数或外部工具，加载任务指导与脚本，检索业务资料，按配置保留会话上下文 |
| 怎么控制风险和检查效果 | [运行观测](./features/observability.md)、[评测](./features/evals.md)、[成本治理](./features/cost.md) | 检查模型与工具调用记录；比较改动前后的结果；限制步数、用量和时长；让高风险工具按配置等待人工批准 |
| 怎么开发、交付和维护 | [开发者工作台](./features/workbench.md)、[HTTP API](./api/rest.md)、[CLI 命令](./api/cli.md)、[部署](./deploy.md)、[升级](./customization/upgrade.md) | 在网页里配置、调试和排查；让现有业务系统通过接口调用；用迁移、Docker 和 CI 管理交付，按指引跟进源码更新 |

MCP 是连接外部工具的标准协议；Skill 是装有任务说明、脚本和资料的能力包。它们都不是必须使用的前置条件。

## 我该不该用

如果你正在做一个要接真实业务接口、要部署、要持续修改的助手，并且愿意用 Python 开发，LubanAgent 值得试用。尤其是：

- 已经把模型对话跑通，接下来要补工具、知识、监控和部署。
- 需要保留源码与数据控制权，方便团队测试、审查和定制。
- 同一个系统里既要灵活问答，又有固定规则，或者需要多个助手分工。

以下情况可以先选更轻的方案：

- 只是临时实验，几行模型调用就够用，没必要引入完整工程。
- 不想写代码，更希望在可视化界面配置应用。
- 已经有成熟的执行、监控和部署平台，只缺一个编排库。

非 Python 业务也能把它部署成独立服务，通过接口调用；但新增业务工具和流程仍然需要 Python。生产前，你还需要启用平台鉴权、创建管理员、配置真实模型、落实数据备份和业务验收。基座内置平台 RBAC，但不会自动替你设计业务侧组织权限。

### 与常见项目怎么选

| 项目 | 更适合什么需求 | 和 LubanAgent 的主要区别 |
| --- | --- | --- |
| [LangGraph](https://github.com/langchain-ai/langgraph) | 想自己设计执行流程，并集成进已有项目 | 它是本项目采用的执行引擎。LubanAgent 在其上加了配置管理、工具与知识接入、工作台、监控和部署工程 |
| [Dify](https://github.com/langgenius/dify) / [Coze Studio](https://github.com/coze-dev/coze-studio) | 优先通过可视化界面搭建 AI 应用 | LubanAgent 以源码和 Python 业务开发为主；选择重点是开发方式，不是说可视化平台不能用于生产 |
| [Agno](https://github.com/agno-agi/agno) | 用代码构建 Agent、团队和工作流，并接入运行管理能力 | 能力有重叠。重点比较你想集成框架依赖，还是在一份完整工程里继续开发，以及当前版本的部署与升级方式 |
| [Google Agent Starter Pack](https://github.com/GoogleCloudPlatform/agent-starter-pack) | 希望从 Agent 工程模板起步，尤其已采用 Google Cloud | 同属起步工程方向。LubanAgent 不要求特定云厂商，模型与服务可部署在你选择的环境 |

若依是交付形态的类比，不是 Agent 领域的功能替代品。其他项目也有监控、评测或审批等能力，选型应验证你实际要用的版本；LubanAgent 的理由是**整套工程符合你的开发方式**，不是“别人什么都没有”。

## 技术架构图

<a :href="technicalImage" target="_blank" rel="noopener"><img :src="technicalImage" alt="LubanAgent 技术架构图：React 工作台、FastAPI 接口、LangGraph 与 LangChain 执行引擎、能力适配、SQLAlchemy 数据持久化及工程交付" /></a>

*图 2：按前端、接口、执行、适配和持久化展开技术栈，右侧列出构建与交付工具，底部标出外部资源。点击图片查看大图。*

**这张图看实现方式**：React 工作台通过 HTTP / SSE 使用 FastAPI 接口；Python 后端用 LangGraph 执行任务、LangChain 接入模型与工具，再由 SQLAlchemy 访问数据库。这些是同一工程内的技术模块，不是需要分别部署的微服务。

- **最小本地环境**：Python 程序 + SQLite 文件库。FakeLLM 返回固定内容，可以不接真实模型验证安装和调用链路；演示向量也不用于判断实际检索质量。
- **真实业务环境**：再接一个真实模型服务，并实现自己的业务工具。数据库可用 MySQL；知识检索效果需要用实际语料和向量模型验证，不要求额外部署专用向量数据库才能起步。
- **可选观测**：需要更完整的观测界面时接 Langfuse 自部署或 LangSmith，也可关闭；内部运行记录仍写入项目数据库。不同观测后端的展示粒度不完全相同。
- **前端与文档**：工作台开发或构建需要 Node.js，构建后的页面由 Python 服务提供。文档站独立发布，不是业务系统运行依赖。

仓库的 Docker 演示会同时启动应用、MySQL、Langfuse、Langfuse 的 PostgreSQL，以及模拟订单服务。它是一套方便看效果的示例组合，不代表生产必须原样部署五个服务。现成的 IM / 电商渠道连接器不在开源核心中，外部业务系统可通过接口或扩展点自行接入。

决定试用后，进入[快速开始](./getting-started.md)。开始接自己的业务时看[开发指南](../tutorial/index.md)；详细配置与接口见[使用手册](./index.md)。
