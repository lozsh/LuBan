# 项目介绍

## LubanAgent 是什么

LubanAgent 是面向开发者的开源 Agent 工程基座，基于 Python ≥3.11、LangChain 和 LangGraph，使用 Apache-2.0 协议。它把 Agent 运行、模型接入、工具调用、知识检索、多 Agent 协作、监控和部署组装在一个源码仓库里。

你克隆这个仓库，在 `app/` 里开发自己的业务，然后部署到自己的环境。交付物是一个可以长期修改和维护的项目，不是只提供几个调用接口的库，也不是让你在网页里拖节点的低代码平台。

**形态上，它对标若依式的起步项目。** 若依把 Spring Boot 及常用工程能力组装成业务系统的起点；LubanAgent 把 LangChain / LangGraph 及 Agent 常用工程能力组装成 Agent 系统的起点。这个类比只说明交付方式：LubanAgent 不提供若依式的通用用户、角色、菜单管理。

仓库内置智能客服作为完整示例，覆盖咨询、工具调用和退款审批。你可以替换 Agent 定义与业务工具，把它改造成内部知识助手、技术支持系统或审批型办事助手，不必把自己的业务改成客服。

## 为什么要用它

直接调用模型，或用 LangGraph 写出一个 Agent，通常不难。困难是把它交给用户之后，团队还要维护一整套工程：

| 业务开发中遇到的问题 | LubanAgent 已经接好的部分 | 你仍然负责什么 |
| --- | --- | --- |
| 人设和工具配置经常调整，出问题却不知道当时用了哪版 | 定义存入数据库、保留版本，Run 绑定定义版本；运行期修改配置不用重新发版 | 定义内容、发布流程和业务验收 |
| 不同 Agent 要用不同模型，供应商也可能更换 | 模型注册与 fast / smart / cheap / vision 槽位映射 | 选择模型、配置凭据、验证模型效果 |
| 模型调工具可能失控，退款等操作不能只靠一句 Prompt | 步数、预算、超时、取消控制；高风险工具审批；LangGraph 确定性流程 | 工具实现、身份权限、金额校验和审批策略 |
| 一次失败涉及模型、工具、检索多个环节，排查没有现场 | 内部 Run / Trace 记录、Token 与费用归因；可接观测后端 | 业务日志、监控告警和故障响应 |
| 单 Agent 不够，需要流程或多个专家协作 | 单 Agent、图流程、supervisor / 子 Agent 委派共用运行与治理体系 | 流程拓扑、任务分工和协作效果 |
| 从脚本走到服务，还要搭 API、界面、数据库和部署 | REST / SSE、CLI、迁移、工作台、Docker 和 CI | 生产配置、数据备份、安全与容量验证 |
| 克隆后改了源码，不知道怎样合并上游更新 | `app/` 与 `lubanagent/` 分离、依赖方向守卫、按领地分类的升级指引 | 按升级说明合并、处理共享文件冲突、运行回归测试 |

选择它，是为了少做一遍这些组装工作，同时保留源码控制权。预算、审批、评测和费用记录是完整工程应该有的能力，不是“只有 LubanAgent 才能做到”的功能。

## 适合谁，什么时候值得用

比较适合已经有明确业务、准备把 Agent 作为服务持续维护的开发团队：

- 你愿意写 Python，需要接入自己的数据库、订单、工单或内部服务。
- 原型已经跑通，现在需要多人维护、版本回溯、运行排查和稳定部署。
- 业务既有模型自主决策，也有必须按固定步骤执行的流程；还需要多个 Agent 分工。
- 希望源码、数据和部署由自己掌控，而不是必须接入某个托管控制面。

非 Python 业务系统也可以通过 REST / SSE 调用独立部署的服务；但定制工具和框架扩展仍然需要 Python。

以下情况不必优先选它：

- 只做一个短期实验，几行模型调用已经够用。完整基座会增加理解与维护成本。
- 团队希望完全不写代码，在可视化界面配置流程。低代码平台通常更合适。
- 已有成熟的鉴权、运行平台、监控和部署体系，只缺编排引擎。直接使用 LangGraph 或其他 SDK 可能更简单。
- 只需要专业的文档解析与检索能力。先选检索组件，再判断是否需要完整 Agent 工程。

## 有没有对标项目，如何比较

有，但要分清比较的是哪一层。**交付形态对标若依；Agent 生态里，Agno 和 Agent Starter Pack 更值得一起评估；LangGraph 是本项目的底层依赖，不是要替代的对手。**

下面比较的是使用方式与工程责任，不是功能打分。其他项目同样可能提供版本管理、审批、评测或监控，不能把这些能力笼统说成“别人没有”。

| 项目 | 主要解决什么 | 与 LubanAgent 的关系 / 选型重点 |
| --- | --- | --- |
| [若依（RuoYi）](https://github.com/yangzongzhuan/RuoYi) | Java 业务系统的完整起步项目 | 交付形态参考，不是 Agent 领域的功能替代品。LubanAgent 同样允许克隆源码后继续开发，但聚焦 Agent 系统 |
| [Agno](https://github.com/agno-agi/agno) | 代码优先的 Agent / Team / Workflow，以及 AgentOS 运行与管理 | 能力重叠较多，值得直接比较。重点看你要把框架作为依赖集成，还是要在完整源码仓库中长期定制；再检查预算策略、存储、部署与升级方式是否满足业务 |
| [Google Agent Starter Pack](https://github.com/GoogleCloudPlatform/agent-starter-pack) | 带工程、评测与部署能力的 Agent 起步模板，面向 Google Cloud 生态 | 同属工程起步方向。已采用 Google Cloud 的团队可以优先评估它；LubanAgent 不要求特定云厂商，部署方式与模型选择由你决定 |
| [Dify](https://github.com/langgenius/dify) / [Coze Studio](https://github.com/coze-dev/coze-studio) | 可视化构建与运行 AI 应用，可自部署 | 优先比较开发方式。需要可视化配置可选平台；需要业务代码、测试和代码审查成为项目主线，可以评估 LubanAgent。两者都能用于实际业务，不存在一概的“平台只能做原型” |
| [LangGraph](https://github.com/langchain-ai/langgraph) / [OpenAI Agents SDK](https://github.com/openai/openai-agents-python) | Agent 执行、编排及相关 SDK 能力 | 适合自己掌握整体工程的团队。LubanAgent 已采用 LangGraph，并在引擎外组装定义管理、模型工厂、运行治理、工作台与部署 |
| [CrewAI](https://github.com/crewAIInc/crewAI) / [AutoGen](https://github.com/microsoft/autogen) | 多 Agent 协作抽象与运行能力 | 优先比较协作模型，再考虑如何接入现有工程。LubanAgent 的团队委派基于 LangGraph，并与单 Agent、图流程共享数据库与治理 |
| [LlamaIndex](https://github.com/run-llama/llama_index) | 数据接入、索引、检索与知识相关工作流 | 偏向知识与检索组件的选择，不是完整工程基座的同层替代；是否引入更专业的检索组件取决于业务需求 |

链接指向各项目官方仓库。选型时请以候选版本的文档和实际验证为准，本页不承诺其他项目永远缺少某项功能。

## 一次业务请求怎样走完

以“用户申请退款”为例，模型不应该直接决定退款金额并调用支付接口：

1. 业务系统通过 REST / SSE 提交请求，Runtime 加载数据库中的 Agent 定义和版本。
2. Agent 使用逻辑槽位对应的模型理解诉求，再通过业务 Tool 查询订单事实。
3. 必须按顺序执行的资格校验、金额计算和审批，由业务代码与 LangGraph 流程实现。
4. 高风险工具按配置进入人工审批，批准后才执行；运行同时受预算、超时与取消控制。
5. Run / Trace 保存模型与工具调用、版本和用量，工作台用于检查现场。

你提供订单接口、退款规则和审批策略；基座提供运行与工程连接。部署成功不等于规则正确，也不等于模型回答可靠，仍然需要针对实际业务做评测和验收。

## 使用前要知道的边界

- 定义存储在数据库中。YAML 用于初始化导入和迁移，修改 YAML 后需要重新导入，不会自动改变运行期定义。
- 单 Agent、确定性流程和多 Agent 都是完整能力；流程与团队需要编写代码，不提供拖拽式流程设计器。
- 开发期可用 SQLite 和 FakeLLM 验证链路。FakeLLM 的固定回复不代表真实模型效果；生产使用需要配置真实模型。
- 内部数据库保存运行事实。观测集成默认采用 Langfuse 自部署方案，也可选 LangSmith 或关闭；不同后端的展示粒度并不完全等价。
- 本站介绍开源核心。开源仓库不附带现成的 IM / 电商渠道连接器；外部系统可走 REST / SSE 或自行实现扩展点。
- 领地隔离减少合并冲突，不保证任意上游升级都零冲突；共享配置和数据库迁移仍须检查。
- 全源码、无强制 SaaS 依赖，不代表自动满足生产安全与合规。鉴权、网络暴露、数据保护、备份和监控由部署团队落实。
