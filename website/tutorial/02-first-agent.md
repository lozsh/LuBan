# 第 2 课：第一个自己的 Agent——从 YAML 到对话

> 学完本课你能：独立写出一份 Agent 定义并让它出现在工作台；解释「定义落库 + 版本化」比「Prompt 写在代码里」好在哪；亲手验证改 YAML → 重跑 init → 版本号 +1 的完整链路 ｜ 预计耗时 30 分钟 ｜ 前置：第 1 课（环境就绪、服务能起） ｜ 难度 ★☆☆

这一课你要造自己的第一个 Agent：**图书馆借阅助手「小图」**。它会陪我们走完剩下的所有课——第 4 课给它写查借阅和挂失工具，第 5 课给它喂馆藏规章，第 6 课给它配评测，第 7 课给它上流程和团队，第 8 课把它部署上线。

先说实话：这一课结束时小图还不会真的用你的人设说话——它的大脑还是第 1 课那个只会一句台词的 FakeLLM。这一课造的是**身体**：定义、版本、导入链路。第 3 课换上真大脑的那一刻，你会回来问它"你是谁"，那时候人设才真正活过来。身体和大脑分开造，恰好让你看清这个框架最重要的一条设计：**Agent 是配置，不是代码**。

当然，图书馆只是我们的主线。你完全可以换成奶茶店点单助手、社团招新答疑——所有步骤同构，教程末尾 `reference/` 目录只维护图书馆版，保证教程可验证。

## 开课三问：先把直觉押上桌

动手之前，三个问题。带着它们往下走，这一课的每个检查点都是答案的一部分。

1. **"改了 YAML 不重跑 init 就不生效"——这算不算一个坑？** 如果框架让 YAML 即改即生效，不是更省事吗？想想：那样的话，谁是真相、谁说了算？
2. **你改的是键的排列顺序、多敲了一个空行——版本号该 +1 吗？** 一个版本号应该记录"格式的变化"还是"内容的变化"？
3. **调试台里，小图开口说的是"我是 LubanAgent"而不是"我是小图"。** 这个"bug"出在身体的哪一层、还是压根不在身体？

提醒一下：这三问问的都不是"怎么操作"，而是"为什么这样设计"。跟着动手步骤走的时候，把每个检查点当作对这三个问题的部分回答——课末小结对完整答案。

## 1. 学习目标

- 写出一份最小可用的 Agent YAML 并导入生效
- 解释 YAML（投喂口）和数据库（存储）的分工，以及为什么改 YAML 必须重跑 `luban init`
- 验证版本化行为：内容变化 → 版本 +1；内容不变 → 不追加
- 用 `luban export` 导出定义并理解往返无损

先划一下本课的边界：工具、知识、技能、图编排——定义里这些段位本课全部留白，它们的挂载方式是第 4、5、7 课的内容。一份定义可以很小，也可以随业务长大；**两个必填项就能跑，每个新字段对应一类新问题**，这是字段设计的"渐进增强"。所以别被手册里十几个字段吓到——你今天只需要 8 个。

## 2. 概念讲解：Agent 是配置，不是代码

回想一下传统做法：一个 AI 助手的人设（系统 Prompt）、它能用什么工具、守什么规矩，都写死在代码里。改一句人设 = 改代码 = 走一遍提交、评审、构建、发版。人设这种一天要调三次的东西，凭什么要走发版流程？

发版流程是为"改一次、稳定很久"的东西设计的——引擎、协议、数据结构。人设不是。人设是**运营资产**：今天语气亲切一点，明天收窄服务边界，后天馆长提了新要求。让运营资产走工程发版，就像为换一张海报重新盖一栋楼。

LubanAgent 的回答：**Agent 的一切要素是一份定义（definition），存在数据库里，带版本号**。改人设 = 改一条库记录 = 立即生效，不发版。每次修改产生一个不可变的历史版本——出了问题可以回滚，评测时可以钉住某个版本对比（第 6 课）。

"不可变"三个字值得停一下。历史版本不可变意味着：上周三那次投诉对应的 Run，永远能精确回溯到当时生效的那一版定义——不是"大概是那个版本吧"，是有据可查。审计、复盘、评测对比，全都建立在这个地基上。

那 YAML 是干什么的？**投喂口**。仓库自带的 `app/agents/*.yaml` 是定义的"源文件草稿"，`luban init` 把它们灌进数据库。之后系统运行读的是库，不是 YAML——所以改了 YAML 必须重跑 `luban init` 才生效。这个分工你上一课已经听过一遍，这一课亲手验证它。

把一份定义的一生画出来，一共五站：

```text
YAML 草稿（app/agents/*.yaml）
   │  luban init（解析 → 校验 → 比对 → 落库）
   ▼
数据库当前版（唯一真相，系统运行只读这里）
   │  每次内容变化
   ▼
不可变历史版本（v1、v2、…，可导出、可回溯）
   │  每次 Run 启动
   ▼
Run 绑定当时的定义版本（事后可精确回溯）
   │  luban export
   ▼
YAML 文件（带走、备份、迁去另一个库）
```

五站走完，你会发现每一站都有明确的进入条件：YAML 要过校验才能落库，内容变了才追加版本，Run 绑的是快照不是"最新版"。没有一站靠"碰运气"。

一份最小定义只有两个必填项：`name`（即 Agent 的 key）和 `instruction`（系统 Prompt）。其余字段都是渐进增强——本课只用 `greeting`（进会话的问候语）、`brain`（逻辑槽位，下一课细讲）、`memory`（记忆策略）、`limits`（治理限额：步数/Token 预算/超时）。你还会看到两个不需要理解就能用的：`description` 是工作台列表里的一句话简介；`io_contract` 声明输入输出形态，本课恒为 text/text，照抄即可。工具、知识、技能这些以后再挂。完整字段表别背，[Agent 定义手册](../manual/features/agent-definition.md)是字典，用到再查。

"渐进增强"展开看就是：两个必填项就能跑，每个新字段都对应一类新问题。这些字段其实各有各的读者：

| 字段 | 内容给谁"读" | 什么时候起作用 |
| --- | --- | --- |
| `instruction` | 模型 | 每次 Run，作为系统提示词 |
| `greeting` | 用户 | 进会话第一眼（静态文本，不过模型） |
| `description` | 开发者 | 工作台列表里的一句话简介 |
| `limits` | 框架（治理层） | 每次 Run 的步数/预算/超时硬边界 |
| `io_contract` | 调用方 | 声明输入输出形态 |

另外说一句：本课的 `instruction` 是"内嵌写法"。等你的提示词多起来，还有引用 Prompt 库的写法——人设模板单独管理、多个 Agent 复用，见[Prompt 库手册](../manual/features/prompt-library.md)。本课先用内嵌，字段最少，心智负担最低。

顺带认识一下 `limits`，虽然本课不会触发它：`max_steps: 12` 是说一次 Run 最多走 12 步（模型每"想一轮"或"调一次工具"算一步），`budget_tokens: 50000` 是这次 Run 的 token 预算，`timeout_sec: 120` 是超时。这是治理的第一课：**Agent 不是想跑多少步就跑多少步**——失控的循环必须在框架层被截断，而不是靠模型自觉。本课对话一轮就结束，碰不到这些边界；第 4 课接上工具后它们开始有意义。

### 框架为什么这样设计：三个"为什么不"

**为什么不让人设写在代码里？** 代码的强项是"精确、可测试、变更受控"，但代价是每次变更都要走完整交付链路。人设恰恰是**高频、低风险、需要快速试错**的变更——它错了最多是语气不对，不会拖垮服务。把高频试错的和低频严谨的分开存：人设进数据库（快改快生效、带版本回滚），执行逻辑留代码（测试覆盖、评审把关）。这个切分线和第 0 课"确定性规则由代码执行"是同一条原则的两面：**变的、靠人判断的进配置；死的、要担保的进代码**。两种做法的差异放到日常场景里看最直观：

| | 人设写在代码里 | 定义入库（LubanAgent） |
| --- | --- | --- |
| 改一句人设 | 提交 → 评审 → 构建 → 发版 | 改一条库记录，立即生效 |
| 出了问题 | "当时跑的是哪版代码？"说不清 | Run 绑定版本，精确回溯 |
| 回滚 | git revert + 再发一遍版 | 切回历史版本 |
| 多环境迁移 | 各环境代码分支对齐 | export / init 往返 |

**为什么 YAML 不干脆做成存储，即改即生效？** 因为一个系统不能有两个真相。如果 YAML 文件和数据库都能改 Agent，那"现在线上跑的到底是哪个版本"就永远说不清：文件系统里一份、数据库里一份，两边还可能不一致。LubanAgent 的答案是唯一的真相在数据库，YAML 只有两种身份：**初始化导入**（第一次把定义送进库）和**导出迁移**（把库里的定义带去别处）。`luban export` 导出的永远是库，不是文件——这一点步骤 5 你会亲手验证。文件是信使，不是档案室。

**为什么版本比对的是"解析后的定义对象"，而不是 YAML 文件文本？** 因为文件文本里全是噪音：键的顺序、空行、引号风格、单行还是多行写法——这些对 Agent 行为零影响，却会让文本比对天天误报"变了"。按解析后的对象比对，格式怎么折腾都是 `(unchanged)`，只有真正影响行为的值变了才 +1。这是对"版本号可信度"的保护：**版本 +1 必须意味着行为可能变了**，否则版本号很快就会贬值成没人在乎的计数器。常见坑一节那个"版本号比我改的次数多"的坑，根子就在这——连行尾空格都是字符串值的一部分。

**为什么导入要校验字段白名单，而不是"不认识的字段悄悄忽略"？** 因为宽松是隐形的坑：字段名手滑打错一个字母，悄悄忽略的话你会得到一份"缺了一块"的定义，它照样能跑，但行为不对，而且你查不出原因。白名单校验让 init 当场报错、指认是哪个键——把问题拖到它最便宜的时刻（导入时）暴露，而不是最贵的时刻（运行时）爆发。常见坑一节那个"未知键"报错，现在你知道该谢谢它了。

四个"为什么不"指向同一条底层原则：**把"变的、高频的"放进数据，把"死的、要担保的"放进代码，中间用唯一的真相（数据库）和显式的边界（校验、版本、绑定）隔开**。第 4 课的工具风险分级、第 7 课的图节点，都是这条原则在不同层的投影。

最后把"身体和大脑"的分界钉成一张表，本课剩下的每一步都在验证左列：

| | 身体（本课） | 大脑（第 3 课） |
| --- | --- | --- |
| 是什么 | 定义、版本、导入链路 | 槽位后面绑的模型 |
| 住在哪 | 数据库的定义表 | 数据库的模型注册 |
| 坏了什么表现 | init 报错、工作台看不到 | 回复内容不对劲 |
| 本课状态 | 交付 | FakeLLM 占位 |

## 3. 动手：主线步骤

六个步骤是一条验证链，每步的产出是下一步的输入——检查点对不上时，九成是跳了步或者上一步没做实。

### 步骤 1：从内置客服复制一份起点

```bash
cp app/agents/customer_service.yaml app/agents/my_lib_assistant.yaml
```

为什么从客服复制，不从空文件写？因为内置客服是这个仓库的"标准答案"——它的结构、字段用法都是仓库作者背书的写法。从它出发删到你需要的最小集，比从零猜字段快得多，也安全得多。后面任何时候迷路了，都可以打开 `app/agents/customer_service.yaml` 对照。

复制完，`app/agents/` 目录里是 10 个 YAML：9 个内置 + 你这 1 个。从这一行命令起，你在 `app/` 领地的资产开始积累了。

然后打开 `app/agents/my_lib_assistant.yaml`，**整个文件替换**为下面这份（不是改几行——把客服的工具、知识、技能段全删掉，那些第 4、5 课再加；留下的字段都是你现在认识的最小集）：

```yaml
name: my-lib-assistant
description: 图书馆借阅助手：查借阅记录、校园卡挂失、馆藏规章咨询
greeting: 你好，我是图书馆助手「小图」～借阅查询、挂失补办、规章咨询都可以找我。
instruction: |
  你是「小图」，学校图书馆的借阅服务助手。
  服务范围：借阅记录查询、校园卡挂失、馆藏规章咨询。
  边界：不处理图书采购建议、不提供文献代查，超出范围如实说明并建议到馆咨询前台。
brain: smart
memory: session
limits: { max_steps: 12, budget_tokens: 50000, timeout_sec: 120 }
io_contract: { input: text, output: text }
```

逐段看一眼这份定义，每个字段你都已经认识：`instruction` 里写了服务范围和边界——注意**边界是写给人设里的**（模型的语言层），而"超范围怎么办"将来还会配上代码层的拦截（第 4 课的工具权限）；`brain: smart` 绑的是槽位不是模型名（第 0 课讲过的解耦垫片，下一课兑现）；`limits` 给了它一副缰绳。

再看 `instruction` 本身的写法，它其实只有三个成分——身份、服务范围、边界。这不是本课的发明，是写系统提示词的通用骨架：模型需要知道"我是谁、我管什么、我不管什么"。第 6 课配评测时你会发现，**边界那句"超出范围如实说明"就是你的第一道安全断言的来源**——现在写下的每个字，后面都会变成可检验的断言。

✅ 检查点：文件保存后，`grep name app/agents/my_lib_assistant.yaml` 输出 `name: my-lib-assistant`——注意 `name` 就是 Agent 的 key，横线命名。

### 步骤 2：导入落库

```bash
.venv/bin/luban init
```

✅ 你应该看到：输出列表多了一行 `my-lib-assistant@1`（首次导入，版本 1），其余 9 个内置 Agent 都是 `(unchanged)`。

记住 `my-lib-assistant` 这个 key：它是将来 URL 里的 Agent 名、工作台里的标识、命令行里的参数——key 是 Agent 在整个系统里的身份证号，`name` 填什么，处处都用什么。第 1 课 curl 里的 `customer-service-bot`，就是内置客服的 key。

这一行输出的信息量比你以为的大：init 扫描的是 `app/agents/` 目录下**所有** YAML，逐个和库里的最新版比对——你的新文件库里没有，判定为首次导入；其余 9 个内容没变，判定为 `(unchanged)`。一份命令同时处理"新增"和"不变"两种情况，这就是幂等导入的全貌。

拆开看，init 对每个文件依次做了四件事：读文件 → 解析成定义对象 → 字段校验（白名单，不认识就报错）→ 和库中最新版比对决定"新建、+1 还是不动"。你后面遇到的大部分 init 问题，都能在这四步里定位到是哪一步出的错。

### 步骤 3：工作台确认

刷新工作台 **Agents 页**（服务没在跑就先 `bash scripts/dev.sh start`——第 1 课的 stop 是可选步骤，别卡在这）。

✅ 你应该看到：`my-lib-assistant` 出现在列表里，版本 1。点进去能看到你写的人设全文——**注意你现在看到的内容来自数据库**，不是 YAML 文件。做个实验：把 YAML 文件里的 description 随便改一个字，刷新工作台——没有任何变化。数据库里存的还是老版本。这就是"投喂口 vs 存储"。

这个实验请一定亲手做。读十遍"YAML 不是存储"，不如亲手改一次看着它"不生效"。做完把 description 改回来。

顺便留意：工作台的版本历史里还能对两个版本做差异对照——等第 4 步产生 v2 之后回去点一下，v1 → v2 改了哪一行一目了然。这是"快照可回溯"的日常形态。

### 步骤 4：验证版本化——改一次，重导一次

把 YAML 里 `instruction` 的第一句改成：

```
你是「小图」，学校图书馆的借阅服务助手，语气亲切像个耐心的学姐。
```

然后：

```bash
.venv/bin/luban init
.venv/bin/luban init   # 紧接着再跑一遍
```

✅ 你应该看到：第一次输出 `my-lib-assistant@2`（内容变了 → 追加新版本）；第二次输出 `my-lib-assistant@2 (unchanged)`（内容没变 → 不追加）。工作台刷新后小图的版本变成 2，点版本历史能看到 v1 和 v2 两个快照。

三连击看清楚：改 → +1；不改 → 不加；**同样的内容跑多少遍都停在同一个版本**。v1 没有被删——它作为不可变快照躺在历史里，随时可以导出（下一步）或回滚。

不可变快照不是"占地方的备份"，它有三个实打实的用途：**回滚**（新版本改坏了，切回旧版）；**审计**（上周那次投诉对应 v 几，一查便知）；**评测钉版本**（第 6 课你会把两个版本各跑一遍评测集，用数据决定留哪版）。快照在，这三种操作才可能。

这个行为比你想象的更重要：**部署脚本反复跑 init 是安全的**——不会无限膨胀版本号，也不会把你在线上调过的东西改回 YAML 的状态（那个更深的坑第 3 课会专门验证）。

### 步骤 5：导出——定义随时能带走

```bash
.venv/bin/luban export my-lib-assistant
```

✅ 你应该看到：stdout 打出一份 YAML，字段与你最后保存的版本一致（export 导出的是**数据库里的当前版**，不是你手上的 YAML 文件——如果两者不一致，以这个输出为准，说明你忘了 init）。加 `--output x.yaml --version 1` 可以导出历史版本快照。

两个方向都体验一遍最有感觉：init 是文件 → 库，export 是库 → 文件，`--version 1` 还能把已经"过去时"的版本捞回来。定义存库、随时导出成文件、文件又能 init 回库——这条往返链路就是你将来迁移环境（开发库 → 生产库）的通道。第 8 课部署时，生产数据库就是靠同一条链路拿到你的定义的。

同一条通道，三种典型用法：**备份**（把当前版导出成文件存档）、**迁移**（新环境 init 这份文件，一步拿到全部定义）、**审计**（导出历史版本，和当前版逐字段比对，看这几个月改过什么）。一个命令，三种场景，全靠"库是唯一真相"撑着。

### 步骤 6：跟小图说句话（诚实的部分）

调试台选 `my-lib-assistant`，说"你是谁"。

✅ 你应该看到：回复**还是那句** `你好，我是 LubanAgent。`——FakeLLM 不读人设，它的剧本只有一句台词。小图的身体（定义、版本、导入链路）已经就位，大脑还没换。这不是失败，是这一课和下一课的分界线。

顺便把开课第三问在这里收一半：说"我是 LubanAgent"不是身体的 bug——定义、版本、导入全都正确工作了（前面五个检查点为证）。问题出在大脑层：FakeLLM 根本不读定义。**分层的好处此刻显形**：你能在两节课之间确切知道"坏的/没到位的"是哪一层，而不是面对一团"整个机器人不对劲"的浆糊。

预告一下第 3 课同一句话的两种命运：FakeLLM 回"你好，我是 LubanAgent。"，真模型回"我是小图呀，借阅查询、挂失补办都可以找我～"。同一个身体，同一份定义，唯一的变化是槽位后面绑的模型——到时候你会对"定义决定它长什么样，模型决定它想什么"有肌肉记忆。

### 六步检查点地图

| 步骤 | 检查点 | 它证明了什么 |
| --- | --- | --- |
| 1 | `grep` 出 `name: my-lib-assistant` | 文件写对，key 合规 |
| 2 | 输出 `my-lib-assistant@1` | 定义通过校验，首次入库 |
| 3 | 工作台可见；改 YAML 不生效 | 库是唯一真相 |
| 4 | `@2` → `(unchanged)` | 版本化语义完整 |
| 5 | export 输出 = 库中当前版 | 往返链路无损 |
| 6 | 固定台词 | 大脑未换（下一课的活） |

六个格全绿，这一课的"身体"就算交付了。

### 顺带回答三个常见疑问

**"我能改内置客服的定义吗？"** 能——它也在库里，工作台里改了立即生效。但教程建议留着它当参照物：你的实验都在 `my-` 前缀的 Agent 上做，内置客服是永远的"标准答案"。

**"改坏了怎么办？"** 版本历史回滚，或者把 YAML 改回去重跑 init。最坏情况：删掉本地库重来——第 1 课的 migrate + init 三分钟就能复原一切。开发环境的一切都是便宜可弃的，这也是 SQLite 的赠品。

**"多个 Agent 能共用一份提示词吗？"** 能，用 Prompt 库的引用写法（前面提过）。这正是"定义是数据"的红利：数据可以引用数据，改一处、处处生效。

## 5. 常见坑

**改了 YAML，工作台没变化。** 最高频问题。YAML 是投喂口不是存储——重跑 `luban init`。判断你看到的是不是库里的内容：`luban export <key>` 导出的永远是库。

**init 报 `未知键` 一类校验错误。** YAML 里出现了不认识的字段（多半是从客服 YAML 复制时带了没删干净的段，或者手滑打错字段名）。错误信息会指出是哪个键，删掉或改对即可——字段白名单在 `lubanagent/cli/yaml_io.py`，字典在[Agent 定义手册](../manual/features/agent-definition.md)。

注意这个坑的正面价值：**报错发生在导入时，不是运行时**。字段写错了，init 当场拦下并指认是哪个键——坏定义进不了库。这比"导进去了、运行时才炸"友好一个数量级，也是"YAML 是投喂口"的另一层含义：投喂口有安检。

**name 里有下划线或大写。** key 的惯用命名是横线小写（`my-lib-assistant`）。下划线能过校验，但和仓库内置 Agent 的风格不一致，工作台里看着也别扭。而且这个 key 会出现在 URL、命令行、API 路径里——横线小写在任何地方都不用转义。

**版本号比我改的次数多。** 先搞清 init 到底比什么：它比较的不是文件文本，而是解析后的定义对象——调整键的顺序、加空行、单行/块写法互换，这些纯格式调整都会显示 `(unchanged)`，不会 +1。真正会让版本 +1 的只有字符串值本身变了，包括不容易察觉的那种：`instruction` 块里行尾多敲的空格、块内多出的空行，它们都是字符串的一部分。怀疑时 `luban export my-lib-assistant` 导出当前版，和你的 YAML 逐字段比对，一眼就能看出是哪个值不同。

这条坑反过来读就是设计意图：版本号只对"行为可能变化"敏感。你要的正是这种敏感——不敏感的版本号才可怕。

本课排障三板斧，比任何单个坑都通用：**拿不准看到的是哪份内容 → `luban export` 看库**；**init 报错 → 看它指认的键名**；**版本号可疑 → 版本历史里 diff 两个快照**。三招都查不出，再提 Issue。

本课建立的认知，后面每一课都在直接复用——现在多花一分钟理解，后面省下的是整课的困惑：

| 本课建立的认知 | 后面哪课直接复用 |
| --- | --- |
| init 幂等 + 版本化 | 第 3 课（换槽位映射）、第 8 课（部署自动 init） |
| export / init 往返 | 第 8 课（开发库 → 生产库迁移） |
| limits 治理限额 | 第 4 课（工具循环）、第 7 课（流程与团队） |
| instruction 身份/范围/边界骨架 | 第 5 课（RAG 人设）、第 6 课（安全断言的来源） |

## 6. 动手练习

**练习 A（模仿）**：给小图换一个你自己写的 `greeting`，走完 init → 工作台确认 → export 验证的完整链路。进阶版：这次不写 YAML，直接在工作台的编辑界面改 greeting 保存——观察它同样产生新版本。两条路改的是同一个库，这就是"库是唯一真相"的完整含义。

**练习 B（变式，重要）**：把 `instruction` 整段删到只剩一句"你是图书馆助手"，init 后导出看一眼。然后想：第 3 课接上真模型后，这个人设会产出什么样的回复？先写下你的预判，第 3 课结束回来对照——这个练习是让你提前体感"人设的详细程度直接决定回复质量"，比任何解释都管用。

**练习 C（综合）**：用你自己的场景（奶茶店/社团/实验室）从零写一份新定义（不复制客服，从空文件开始），只准看字段名不许抄内容。写完 init，确认导入成功。从下一课起你可以两条线并行：跟着教程走图书馆主线，同时用自己的 Agent 做每课练习的变体。

## 7. 思考题

- 为什么 `name` 之外还要有 `description` 和 `greeting`？它们分别给谁看？（提示：description 给工作台列表里的**你**看，greeting 给对话开始时的**用户**看——同一份定义服务三种读者：模型读 instruction，人读其余。）
- `limits` 里三个限额分别防什么失控场景？如果把 `max_steps` 设成 1000 会怎样？（提示：工具循环、长对话复读、下游卡死——治理边界便宜的时候就要立，出了事再立就贵了。）
- 定义入库带版本后，"回滚"变得很容易。但什么情况下回滚是危险的？（提示：新版定义期间产生的 Run/Trace 是按新版跑的——回滚定义不回滚历史。想想哪些操作该配评测先行，第 6 课见。）

## 8. 小结与下一课预告

小图有了身体：一份入库的、版本化的定义，以及一条你已经亲手验证过的"改 YAML → init → 版本 +1"链路。你也有了"投喂口 vs 存储"的实感——这个心智模型后面每一课都会用到。

这一课你带回三个可迁移的心智模型，值得用一分钟向同事复述：

- **库是唯一真相**：YAML 是信使，工作台和 API 是另外两个信使——改谁都行，改的都是同一个库；
- **版本号只对内容敏感**：格式噪音不配消耗版本号，+1 必须意味着行为可能变了；
- **快照不可变**：回滚、审计、评测钉版本，三种能力都建立在"历史版本永不改写"上。

开课三问，对答案：

- **第一问（YAML 即改即生效不好吗）**：不好，因为真相必须唯一。文件和库若都能生效，"线上到底跑的哪版"永远说不清，审计和回滚都失去地基。LubanAgent 让数据库当唯一的档案室，YAML 只当信使——文件可能丢、可能过期，库里每次保存都是带版本号的不可变快照。
- **第二问（改格式该不该 +1）**：不该。init 比对的是解析后的定义对象，不是文件文本——键顺序、空行、写法风格这些噪音不配消耗版本号。**版本 +1 必须意味着行为可能变了**，否则版本号会贬值成没人在乎的计数器。代价是行尾空格也算"值的一部分"，`luban export` 是你的比对工具。
- **第三问（"我是 LubanAgent"的锅在哪层）**：不在身体。定义、版本、导入链路五道检查点全部通过，问题出在大脑——FakeLLM 不读人设。这正是分层的价值：你能确切指出问题在哪一层，而不是面对一团浆糊。下一课换掉那一层，人设立刻活过来。

进下一课前盘点你手里的东西：一份 v2 的 `my-lib-assistant` 定义（在库里，不在文件里）；一条亲手验证过的导入链路；一个还欠着真大脑的调试台入口。第 3 课开局你只需要再备一样东西——一个大模型 API Key。

下一课换大脑：注册 DeepSeek（或任一 OpenAI 兼容模型），绑到 smart 槽位。然后你会回来问小图"你是谁"——它终于开口说出"我是小图"的那一刻，前面两课的铺垫全部兑现。顺便你会看清"换模型不改代码"不是口号：改一条库里的映射，同一个 Agent 立刻换脑。
