# 第 4 课：写自己的 Tool——让小图真的会做事

> 学完本课你能：用 `@tool` 装饰器写出一个低风险工具和一个带审批的高风险工具，挂到 Agent 上跑通完整链路 ｜ 预计耗时 45-60 分钟 ｜ 前置：第 3 课（真模型已绑 smart 槽位） ｜ 难度 ★★☆

## 引子：会说话的 Agent，和会做事的 Agent

第 3 课结尾留了一个缺口：小图的服务范围写着"借阅记录查询"，可它没有查询工具。现在拿真模型问它"我借了哪些书"，它会一本正经地回答——书名、日期，编得有鼻子有眼。真模型编起来比 FakeLLM 像真得多，**这正是第 0 课说的幻觉：模型缺信息时不会承认缺，会补一个像的**。

堵幻觉的正路只有一条：给它真的信息源。这一课把"说"变成"做"——写两个工具：一个查借阅记录（只读，低风险），一个挂失校园卡（收 20 元工本费，高风险走审批）。

先给你打个预防针，免得你到处找“复杂”在哪：两个工具总共二十几行 Python。Tool 开发的心智负担极低——`@tool` 装饰器一挂，函数写完就完事。真正值得花脑子的地方只有一个：**这个工具该定什么风险等级**。定级定错，轻则审批流形同虚设，重则真金白银出去。这也是本课练习的主角。

顺便定一下预期：这一课你写的代码不复杂，但读代码的时间应该比写代码多——两个工具的声明差异、审批链路里每一环是谁在负责、签名冻结在什么时候起作用，这些才是值钱的部分。工具本身只是几行胶水，治理声明才是你在生产里安睡的底气。

## 开始前，先想三个问题

凭直觉猜，本课第 2 节和步骤里会揭晓：

1. 模型能看到你 docstring 里写的参数说明吗？——你给 `student_id` 写了注释"学号（如 2023011234）"，模型调用工具时看得到这行字吗？
2. "工具失败后自动重试三次"听起来很贴心。为什么 LubanAgent 的默认是 0——一次都不重试？
3. 你给已上线的工具加了一个参数。Agent 定义一行没改，为什么旧版本 Agent 会直接拒绝运行？

第 1 题在第 2 节揭晓，第 2 题在「框架为什么这样设计」揭晓，第 3 题在概念节的「签名冻结」揭晓。

## 1. 学习目标

- 用 `@tool` 装饰器写工具并理解参数 JSON Schema 是怎么从函数签名自动生成的
- 区分 `risk` / `approval_required` / `idempotent` / `timeout_seconds` 四个治理参数各自为谁服务
- 走通高风险工具的完整审批链路（事件 → 人工决定 → 执行）
- 对“什么操作该要审批”形成自己的判断标准

四条目标一条比一条主观：前两条是“会写”，第三条是“会连”，第四条是“会判”——最后一个才是本课的灵魂，也是练习 C 专门训练的部分。生产事故里，工具写错参数的情况远少于工具定错级的情况。

## 2. 概念讲解：模型说，代码做

第 0 课讲过 Tool 的分工，这里讲实现视角。一个 Tool 在 LubanAgent 里就是**一个普通 Python 函数 + 一份装饰器声明的元数据**：

```python
@tool(key="my_lib_lookup", description="按学号查询借阅记录。",
      risk=RiskLevel.LOW, timeout_seconds=10.0, idempotent=True)
def my_lib_lookup(student_id: str) -> dict:
    """查借阅记录。"""
    ...
```

没有基类、没有接口、没有注册表文件——任何普通函数挂上装饰器就是个工具。你要在框架里"注册"什么？什么都不用：导入即注册（步骤 1 你会看到 `__init__.py` 里那行 import 就是全部注册动作）。

关键在**框架怎么让模型知道这个工具的存在**：运行期把工具清单（名字、描述、参数结构）发给模型——参数的 JSON Schema 是从函数签名**自动生成**的：`student_id: str` 变成 `{"type": "string"}`。划重点：模型能看到的参数信息**只有参数名和类型**。docstring 里写的参数说明是给人看的——你三个月后回来改代码时的提示，模型根本看不见。模型读了清单，决定调用时输出一段结构化数据（工具名 + 参数值），框架解析后真的去调你的函数，把返回值喂回模型组织答案。

所以你写工具时唯一的"接口设计"工作是：**函数签名**。参数名要语义清晰（模型看不到参数说明，全靠名字猜该传什么），类型注解要给（模型靠它生成正确类型的值）。

装饰器的治理参数各自为谁服务：

- `risk`：风险等级。`LOW`（只读，直接执行）/ `MEDIUM` / `HIGH`（默认要审批）。
- `approval_required`：显式声明要人工审批。**HIGH 或 approval_required 任一为真就进审批闸门**——审批与否由代码强制，不靠模型自觉。
- `idempotent`：幂等性。它是自动重试的**前提**，不是开关——只有幂等工具才会被重试，而且还得显式设 `max_retries` 大于 0 才真的会重试（默认 0，一次都不试；本课的 lookup 没设，失败就直接返回失败）。扣费/挂失这类非幂等操作重试一次就是双倍扣钱，永远别开。
- `timeout_seconds`：单次执行超时。防工具把整个对话挂死。

四个参数放在一张表里对照，两个工具的定级差异一目了然：

| 治理参数 | my_lib_lookup | my_lib_report_loss | 差异理由 |
|---|---|---|---|
| `risk` | LOW | HIGH | 只读查询 vs 收费操作 |
| `approval_required` | 未设（不审批） | True | 查询无需人点头；收钱必须 |
| `idempotent` | True | False | 查多少遍结果一样；挂失不可撤销 |
| `timeout_seconds` | 10.0 | 15.0 | 都防挂死，收费链路给宽一点 |

读这张表的方法比表本身重要：每一行的“差异理由”都指向一个业务事实，而不是一个参数默认值。以后你给任何工具定治理参数，照这个格式自问一遍——答不出“理由”的参数，就是还没想清楚的参数。

还有一个隐蔽但重要的机制：**签名冻结**。工具的参数结构会算一个哈希记进 Agent 版本快照；你以后改了工具签名（比如加参数），旧版本 Agent 会报"签名漂移"拒绝运行——防止"定义说两参、代码要三参"的静默错乱。碰到它时重新 init 一次产生新版本即可。

这套机制初见会有点“过度设计”的感觉，练习 A 会让你亲手触发一次签名漂移，那时你就懂它拦的是什么事故了。

### 一次工具调用的完整旅程

把第 3 课事件流里那两帧展开，从模型视角到代码视角走一遍全程：

1. **清单下发**：Run 启动时，框架把该 Agent 挂载的所有工具整理成清单（工具名、description、自动生成的参数 JSON Schema）发给模型；
2. **模型决策**：模型读用户输入，判断该调哪个工具、填什么参数，输出一段结构化数据（工具名 + 参数值）；
3. **治理检查**：框架拿到这段数据，先查风险等级和审批声明——该拦的在这里拦（你第 3 课见过的 `tool.approval.requested` 就是这一环发出的）；
4. **真实执行**：检查通过，框架解析参数、调用你的 Python 函数——`tool.started` 在这一刻发出；
5. **结果回喂**：函数返回的 dict 原样喂回模型，由它组织成人话答复——`tool.finished` 收尾。

五个环节里，模型只参与第 2 环和第 5 环。第 3、4 环是纯代码——审批、超时、重试这些你信得过的东西，全住在模型碰不到的地方。

### 框架为什么这样设计

四个设计点，每个都对着一类真实事故：

**参数 Schema 为什么从签名自动生成，而不是让你手写一份 JSON Schema？** 因为接口只能有一个事实源。手写 Schema 意味着同一个参数结构存在两份——函数签名一份、Schema 一份——改了签名忘了改 Schema，模型拿着旧结构填参数，运行时才炸，而且炸得莫名其妙。从签名生成，"代码即接口"，Schema 永远和函数一致；工作台里你看到的参数 Schema（步骤 3 的检查点）就是这份自动生成的产物。代价是你得接受约束：想给模型更多的参数信息？给不了，只有名字和类型——所以参数名必须起得像文档。

**为什么重试默认是 0，而且以幂等为前提？** 想一下重试在什么场景触发：工具超时、网络抖动、下游 5xx。如果这个工具是"扣 100 块钱"，第一次请求其实成功了、只是响应没回来，重试就是再扣 100。**重试对幂等操作是救命，对非幂等操作是双倍扣钱**——框架没法替你判断哪个是哪个，所以把决定权留在声明里：`idempotent=True` 是资格，`max_retries>0` 是意愿，两者都满足才重试。默认全关，是最安全的默认。

**为什么审批由代码闸门执行，而不是在 Prompt 里要求模型"花钱前先询问用户"？** 第 3 课步骤 6 你已经见过答案的一半：模型是概率系统，Prompt 约束是请求不是强制，总有被绕过的时候——尤其面对精心构造的输入。审批闸门长在工具声明上（`approval_required=True`），框架在**执行前**检查，不满足就挂起等人。模型连"尝试执行"的机会都没有，谈不上"说服"。

**为什么风险定级写在工具声明处，而不是搞一套全局审批策略（比如"所有写操作都审批"）？** 因为"危不危险"是业务知识，只有写工具的人知道。`refund_apply` 收钱所以要审批，`query_order` 只读所以不用——这个判断离开具体工具就不成立。放全局策略层，要么粗到误伤（把无害操作也拦下），要么细到失控（策略文件膨胀成第二份业务逻辑）。定级贴着工具走，审批的粒度才跟业务的风险粒度对齐。

## 3. 动手：主线步骤

五个步骤一条直线：建包 → 写两个工具 → 挂载 → 单测 → 对话验收。顺序别乱——尤其步骤 4 的在线试跑，务必在步骤 5 对话之前做：先验证工具本身，再看模型调度，问题永远分层查。

### 步骤 1：建工具包

```bash
mkdir -p app/tools/my_library
```

新建 `app/tools/my_library/__init__.py`：

```python
from . import lookup, report_loss  # 导入即注册
```

新建 `app/tools/my_library/lookup.py`：

```python
"""查借阅记录（低风险只读工具）。"""

from lubanagent.core import RiskLevel
from lubanagent.extension import tool

# 教程演示用内置数据；真实场景换成 HTTP 调用你的业务系统，
# 模式照抄 app/tools/customer_service/order.py。
_BORROWS: dict[str, list[dict]] = {
    "2023011234": [
        {"title": "三体", "due": "2026-09-20", "renewals_left": 1},
        {"title": "机器学习系统设计", "due": "2026-09-12", "renewals_left": 0},
    ],
}


@tool(
    key="my_lib_lookup",
    description="按学号查询借阅记录（书名/应还日期/剩余续借次数）。",
    risk=RiskLevel.LOW,
    timeout_seconds=10.0,
    idempotent=True,
)
def my_lib_lookup(student_id: str) -> dict:
    """查借阅记录。

    参数: student_id: 学号（如 2023011234）
    """
    records = _BORROWS.get(student_id, [])
    return {"student_id": student_id, "count": len(records), "records": records}
```

数据先写死在模块里——这一课的注意力留给工具机制。真实场景换成 HTTP 调你的业务系统（就是 `httpx` 一个 GET），对照范本见文末延伸阅读里的 `app/tools/customer_service/order.py`。

读这段代码时留意两件事：其一，docstring 里那段"参数: student_id: 学号"——还记得开头的第 1 题吗？这段话**模型看不到**，它是写给未来维护这份代码的你自己的；模型看到的只有参数名 `student_id` 和类型 `str`。这个名字起得好（谁一眼都看懂是学号），所以模型不会填错。其二，返回值是 dict——工具返回什么，模型就原样看到什么，所以返回结构要自含语义（`count`、`records` 这些键名就是给模型读的字段说明）。

✅ 检查点：`grep -c "@tool" app/tools/my_library/lookup.py` 输出 1。

这个检查点验证的不只是“装饰器写了没”，还有“写在函数上而不是写在注释里”——grep 数的是代码里的装饰器实例，粘贴时漏掉、缩进错位这类低级错误在这里就地暴露，不用等到服务重启后的扫描报错。

### 步骤 2：写高风险工具

新建 `app/tools/my_library/report_loss.py`：

```python
"""校园卡挂失（高风险工具：收工本费、触发人工审批）。"""

from lubanagent.core import RiskLevel
from lubanagent.extension import tool

CARD_LOSS_FEE = 20.0  # 挂失补办工本费（元）


@tool(
    key="my_lib_report_loss",
    description=f"提交校园卡挂失申请（高风险：收工本费 {CARD_LOSS_FEE:g} 元，需人工审批）。",
    risk=RiskLevel.HIGH,
    timeout_seconds=15.0,
    idempotent=False,
    approval_required=True,
)
def my_lib_report_loss(student_id: str) -> dict:
    """挂失校园卡并生成补办申请。

    参数: student_id: 学号（如 2023011234）
    """
    return {
        "student_id": student_id,
        "status": "loss_reported",
        "fee": CARD_LOSS_FEE,
        "pickup": "三日后凭学生证到图书馆前台领新卡",
    }
```

对照两个工具的声明差异：lookup 是 `LOW + idempotent`（查询幂等，具备被重试的资格），report_loss 是 `HIGH + approval_required + 非幂等`（收钱的事，拦下来等人点头，失败不重试）。

这四行声明的差异不是风格偏好，是逐条有业务理由的定级决策：挂失收 20 元真金白银 → 要审批；挂失动作不可撤销（你不能“取消挂失”恢复原卡）→ 非幂等，绝不重试；查询只读、查多少遍结果都一样 → 幂等，给重试留资格。**每一行治理参数都能答出“为什么”**——练习 C 会专门训练这个能力。

把你自己代入一次审批官的角色：如果挂失不需要你点头就能执行，谁该对 20 元和不可恢复的旧卡负责？审批链路不是流程负担，是责任边界的物理存在——代码闸门把“系统要花钱”和“人同意花钱”强制隔开，这个隔断在任何 AI 系统里都不该由模型自己拿捏。

✅ 检查点：两个文件都保存，`__init__.py` 的 import 与文件名一致（`lookup`、`report_loss`）。

### 步骤 3：挂到小图身上

`app/agents/my_lib_assistant.yaml` 的 instruction 服务范围那段后面加一行，并加 `tools` 段：

```yaml
instruction: |
  你是「小图」，学校图书馆的借阅服务助手，语气亲切像个耐心的学姐。
  服务范围：借阅记录查询、校园卡挂失、馆藏规章咨询。
  查借阅用 my_lib_lookup（要学号）；挂失用 my_lib_report_loss（收 20 元工本费，走人工审批）。
  边界：不处理图书采购建议、不提供文献代查，超出范围如实说明并建议到馆咨询前台。
brain: smart
tools: [my_lib_lookup, my_lib_report_loss]
memory: session
...
```

（注意人设里顺带告诉了模型每个工具是干嘛的、什么时候用——工具的 `description` 模型也看得到，但人设里的使用规则让调度更稳。）

"调度更稳"值得展开一句：description 回答"这个工具是什么"，人设里的规则回答"什么场景该用它"。两者都进模型的上下文，但人设里的规则是按你的业务场景写的调度指令——比如"挂失要先确认学号"这种流程性要求，只有人设能表达。

导入并重启（工具注册发生在服务启动扫描时，新文件必须重启生效）：

```bash
.venv/bin/luban init
bash scripts/dev.sh restart
```

✅ 你应该看到：init 输出 `my-lib-assistant@3`（或你当前的版本 +1）；工作台**工具页**出现 `my_lib_lookup` 和 `my_lib_report_loss`，点开能看到自动生成的参数 Schema。

签名冻结的“冻结”动作，就发生在你眼前这次 init 里。

以后每次 init 输出的版本号，都可以理解为一次“行为快照”的封装：定义、工具签名、知识配置在那一刻被钉在一起。版本化不是官僚流程，是回滚和对比的基础设施——第 6 课的版本对比评测，就建立在它上面。

### 步骤 4：不起对话，先单测工具

写完工具不用急着对话——工作台工具页每个工具都有**在线试跑**（不起 Runtime、不走模型，直接执行工具函数）：

```bash
curl -X POST http://localhost:8000/v1/tools/my_lib_lookup/test \
  -H "Content-Type: application/json" \
  -d '{"student_id": "2023011234"}'
```

✅ 你应该看到：`{"success": true, "value": {"student_id": "2023011234", "count": 2, "records": [{"title": "三体", ...}, ...]}, ...}`。

注意请求体**就是参数本身**（不是包一层的 `{"args": ...}`）。这一步验证的是工具函数本身没写错——把"工具坏了"和"模型没调对"两类问题分开查，是排障的基本功。以后遇到"Agent 调工具不对劲"，第一反应永远是先来这里跑一遍：工具层对了，问题才在模型侧或编排侧；工具层就错了，模型侧查到天亮也是白查。

### 步骤 5：对话里用低风险工具

调试台选小图，输入：`我是学号 2023011234 的学生，我借了哪些书？`

✅ 你应该看到：回复里出现《三体》和《机器学习系统设计》、各自的应还日期——来自你刚写的工具返回的真数据。curl 看事件流（或看调试台的工具状态行）：`tool.started`（模型决定调 my_lib_lookup）→ `tool.finished`（真数据回来）。从这一刻起，小图在借阅查询上**不可能再编**——它说的每一本书都来自工具返回。

"不可能再编"不是修辞。模型的能力边界由上下文决定：借阅数据只存在于工具返回里，上下文里没有的信息它无从编起。引子里那个"一本正经编书名"的小图，和眼前这个小图，差的就是这一个工具。

### 步骤 6：走挂失审批

/chat 页选小图，输入：`我的校园卡丢了，学号 2023011234，帮我挂失`

✅ 你应该看到：气泡内出现**「批准 / 拒绝」按钮**（不是直接执行）——my_lib_report_loss 是高风险，闸门拦下等人点头。点「批准」，挂失真实执行，模型接着告诉你工本费 20 元、三日后凭学生证领新卡。事件流里是 `tool.approval.requested` →（你点按钮）→ `tool.approval.resolved`。

> 用 curl 走这条链也行，但**别加 `--max-time` 短超时**：审批等人点击期间连接要保持——浏览器天然如此，curl 加了超时会在你批准前把连接掐断。这是真实踩过的坑。

第 3 课你用的是内置客服的退款审批；这次是你自己写的工具、自己定的风险等级——同一套闸门机制，你已经会造受它保护的东西了。注意一个细节：从 `approval_required=True` 这行声明到"批准/拒绝"按钮出现在气泡里，中间你**没有写任何前端或流程代码**——审批 UI、事件流、挂起恢复全是框架的。你声明风险，框架负责执行风险策略。

- [ ] 工具页看到两个 my_lib 工具，Schema 自动生成
- [ ] 在线试跑直接返回借阅数据（步骤 4）
- [ ] 对话中 tool.started / tool.finished 出现，回复含真数据（步骤 5）
- [ ] 挂失走完「审批按钮 → 批准 → 执行 → 告知工本费」（步骤 6）

最后一条是本课的“毕业证”：前四条验的是操作，这一条验的是判断。如果哪条差异你说不出理由，回到第 2 节的对照表和“框架为什么这样设计”再读一遍——定级理由讲不清的工具，不该上生产。

## 5. 常见坑

这一课的坑有个共同主题：**你以为做了，框架没看见**。改了文件没 import、改了签名没 init、模型说了“做了”但事件流里没有——全在这一类。逐个看：

**改了工具/加了新工具，工具页没有。** 工具注册在服务启动扫描时发生（由 `EXTENSION_PACKAGES` 驱动，默认扫描 `app.tools` 和 `app.graphs` 两个包——工具和图都靠它发现）。`bash scripts/dev.sh restart`。另外检查 `__init__.py` 有没有 import 新模块——没 import 就不会被扫描到。

**对话中说"我帮你查了"但事件流里没有 tool.started。** 模型在编造工具调用（幻觉的变体）。常见原因：人设里没写清什么时候用哪个工具，或工具 description 太含糊。把使用规则写进人设（见步骤 3 的做法）。

**报"工具签名漂移"。** 你改了已挂载工具的函数签名，而 Agent 版本快照里记的是旧签名。重跑 `luban init` 产生包含新签名的新版本即可。这是保护，不是故障。

**在线试跑 400/422。** 九成是请求体格式——参数直接放 body（`{"student_id": "..."}`），不要包 `{"args": {...}}`。

## 6. 动手练习

三个练习分别训练三种能力：A 练「改动工具会遇到什么」，B 练「定级改松会失去什么」，C 练「从零定级」。C 是主菜——它不写代码，写的是判断。

做完 C 后再读一遍第 2 节「框架为什么这样设计」的第三点，你会有第二轮收获。

**练习 A（模仿）**：给 lookup 加一个可选参数 `title_filter: str = ""`（按书名过滤），重启后先在线试跑，验证工具本身能跑、能过滤——注意试跑端点不经过 Agent 版本校验，这里**永远不会**报签名漂移。然后到 /chat 或调试台发起一次小图的会话：这时才会撞上"签名漂移"——想想为什么（提示：版本快照里钉的是旧签名，防止旧定义配新代码）。重跑 `luban init` 产生新版本后恢复。

**练习 B（变式）**：把 report_loss 的 `approval_required` 改成 `False`、`risk` 降到 `MEDIUM`，重启重导，再走一次挂失。观察：这次没有审批按钮，直接执行了。改回去。然后想一个问题：**风险等级定低了，谁来兜底？**（答案在第 0 课：没人——这就是为什么定级是严肃决策。）

**练习 C（综合，本课主菜）**：给图书馆再加一个"续借"工具 `my_lib_renew(student_id, title)`：把指定书的 `renewals_left` 减一、应还日期延 30 天。**先别写代码**——先回答三个问题并把答案写下来：①它该是什么风险等级？②要不要审批？③幂等吗？然后再写代码、按你自己的答案定参数。写完后对照：内置客服的退款工具定 HIGH+审批，你的续借和它比，危险程度差在哪？（参考思路：续借改的是借阅状态不直接动钱，但消耗了不可逆的续借次数——现实中这类"中等风险"的定级争议最大，值得多想一分钟。）

## 7. 思考题

概念题，先自己想，再看括号里的提示：

1. **`idempotent=True` 的 lookup 为什么还要设 `timeout_seconds=10`？幂等不是已经保证安全了吗？**（提示：幂等防的是"重复执行"，超时防的是"永远不返回"——一次查询挂住 60 秒，整个对话就卡在那，两者管的是不同的事故。）
2. **工具的 `description` 和人设里的使用规则都进模型上下文，信息重复了，能不能只留一个？**（提示：description 跟着工具走、所有挂载它的 Agent 共享；人设规则跟着 Agent 走、只管自己的业务流程——它们的作用域不同。想想"收 20 元工本费"这句更适合放哪。）
3. **签名漂移报错时，为什么框架选择"拒绝运行"而不是"用旧签名兼容运行"？**（提示：兼容运行意味着模型会按快照里的旧参数结构去填一个代码已经不认的调用——这正是签名冻结要拦的静默错乱；宁可不跑，不能跑错。）

## 8. 小结与下一课预告

开头三个问题，现在回收：

- **第 1 题**：模型看不到 docstring——它只拿到参数名和类型，`student_id: str` 自动生成的 `{"type": "string"}` 就是它关于这个参数的全部知识。所以**参数名是接口，注释是遗产**，两者都写，但别指望注释替你传话。
- **第 2 题**：重试默认 0，因为框架无法替你判断工具是否幂等——对查询是救命的重试，对扣款是双倍扣钱。`idempotent` 给资格、`max_retries` 给意愿，双条件满足才重试。
- **第 3 题**：签名冻结拦的是"旧版本定义配新签名代码"的静默错乱——拒绝运行是保护，不是故障，重新 init 即可。

小图现在会做两件事了：查借阅（低风险直通）和挂失（高风险审批）。这一课你真正动笔的代码不到三十行，但治理声明、审批链路、签名冻结、排障分层——这些东西会跟着你到每一个生产工具里。更重要的是练习 C 那个问题——**风险定级是工程判断，不是模板填空**。

还差最后一块能力：馆藏规章咨询。规章有几十条，不可能写成人设（塞不下、改不动），也不能靠工具（每条规章不是"操作"是"知识"）。下一课用 RAG：上传规章文档、切块、校准阈值——顺便见识这个框架最硬核的一个特性：**宁可说不知道，不硬编答案**，而且这条底线是代码守的，不是求模型守的。
