# 第 8 课：部署上生产——全栈、观测、以及升级不丢改动

> 学完本课你能：用 Docker 起五服务全栈并在 Langfuse 回放自己的 Trace；演练一次「跟上游升级不丢改动」的合并；用评测回归证明升级没改坏东西 ｜ 预计耗时 60 分钟 ｜ 前置：第 7 课 ｜ 难度 ★★★

最后一课。前七课你一直在自己的笔记本上折腾——`dev.sh` 起停、SQLite、终端里看日志。这一课把小图带出笔记本：Docker 全栈部署、独立观测系统、还有这个框架最独特的一个承诺的实操验证——**你在这个仓库里写了两课的 `app/` 领地，框架升级时会不会被冲掉？**

先回答一个你可能憋了很久的问题：为什么部署要五个服务？因为一个真实的 Agent 系统不止"跑模型的 API"：应用本体（app）、数据库（MySQL）、观测（Langfuse + 它自己的库）、还有客服示例依赖的假业务系统（mock-biz）。开发期它们被 SQLite 和 noop 观测简化掉了，生产形态得把它们各就各位。

这里藏着一个部署课最重要的一句话，先放在前面：**开发和生产跑的是同一套代码，差的是"周边系统的成色"。** 这一课你做的所有事——换 MySQL、接 Langfuse、改环境变量注入方式——没有一个字动到 Agent 的业务逻辑。这也是你敢把第 1-7 课的产出直接搬上生产栈的底气。

**带着三个问题往下读**，本课结尾揭晓答案：

1. 观测系统（Langfuse）挂了，你的 Agent 该不该跟着挂？
2. 生产形态里为什么没有"前端服务器"这个东西——前端去哪了？
3. 上游升级凭什么敢承诺不冲掉你的 `app/` 领地？这个承诺靠什么兑现，靠自觉吗？

这三个问题对应本课的三根支柱：观测分层、交付形态、领地契约。它们也是你评估任何一个"Agent 基座"够不够格进生产的三个试金石——问完这三个问题，大部分玩具和真基建就分出高下了。

## 1. 学习目标

前两条是部署技能，后两条是升级纪律。这个配比是有意的：部署是体力活，照着敲就能过；升级是脑力活，要理解领地规则才能处理真实世界里的合并冲突——所以本课把最重的篇幅留给了后者。

- 用 docker compose 起五服务全栈，验证每个服务的角色
- 接上 Langfuse，双端（Langfuse / 工作台 Traces）回放同一条 Trace
- 完成一次模拟的「上游升级合并」，确认 `app/` 领地完好
- 用第 6 课的评测集做升级后的终检

## 2. 概念讲解：镜像、观测分层、领地契约

这一节的三个概念各管一件事：镜像管"交付什么"，观测分层管"怎么看它"，领地契约管"怎么跟着它长大"。三者共同回答一个问题：这个基座凭什么能长期住人。逐个看。

**单镜像单端口。** app 的镜像里装了三样东西：Python 运行时、后端、**构建好的工作台前端**（构建期用 node 打包，运行期由 FastAPI 在 8000 端口一并托管）。所以生产上没有"前端服务器"这个东西——一个镜像一个端口，反向代理都省了。

拆开看这个设计的三笔账：**构建期**，node 把工作台打成静态文件，塞进镜像——从此前端有了"版本"，跟着镜像一起前进和回滚，不存在"代码是新的、页面是旧的"的经典事故；**运行期**，FastAPI 托管这些静态文件——少一个服务就少一份部署、监控、网络配置的成本；**发布期**，你交付的 artifact 从"两个东西的组装说明书"变成"一个镜像"——拷走就能跑，换台机器也是同一份行为。小团队最稀缺的不是功能，是运维带宽。

顺带把整个项目的三种部署形态放在一张表里看清楚（本课走的是第二种）：

| 形态 | 命令 | 适用 |
|---|---|---|
| 本地开发全栈 | `scripts/dev.sh start` | 日常开发：API :8000 + 工作台 :5173 热更新（前七课你一直在用的） |
| Docker 单机全栈 | `docker compose up -d --build` | 演示/自托管：五服务一键起 |
| 生产部署 | 同上 + 生产清单改造 | 容器编排进你的基础设施（K8s 把 compose 服务逐个搬） |

注意第三形态的表述：**K8s 不是再学一套，是把 compose 里的五个服务逐个搬进你的编排**——每个服务的镜像、环境变量、健康检查你已经全部见过，搬家而已。compose 文件本身就是最准确的部署说明书。

补一句为什么本课拿第二种形态当教学场：镜像、环境变量、健康检查、依赖关系这些真正的难点，全部已经在 compose 里一字不差地摆着——你在这里踩的每一个坑，搬到任何编排平台上还是同一个坑，只是换了个名字（compose 的 healthcheck 到了 K8s 里叫 readinessProbe，概念原样平移）。反过来，直接从编排平台入门的人往往说不清自己的服务依赖谁、先起谁——compose 是最好的编排入门教材。

**观测的三个层次。** 这个框架的观测设计值得看清楚再配：

1. **内部 DB 永远是 source of truth**——每个 Run/Trace 先落库，这一层不需要任何配置；
2. **Langfuse 是旁路**——Trace 同步外发到自部署的 Langfuse（数据在你自己的服务器上，这是"数据主权"），用于漂亮的 UI、筛选、对比；外发失败不阻断业务（失败记录留痕、自动重试）；
3. **可切换可关闭**——`OBSERVABILITY_BACKEND=none/langfuse/langsmith`，不宣传"完全等价切换"。

为什么"双端回放同一条 Trace"是这一课的检查点？因为它一次验证了前两层：内部库里有（工作台能放），外发也活着（Langfuse 能放）。

**领地契约（本课的主角）。** 回想第 1 课的"你住哪里，框架住哪里"：`app/` 是你的领地，`lubanagent/` 是框架。这个分界有三件配套设施保证它不只是口号：

- `.lubanagent-upstream`——一个清单文件，把仓库里每个文件归类（framework / shared / scaffold-seed / user-owned），合并冲突时按类处理；
- **CHANGELOG 按领地打标签**——`[framework]` 的变更你直接合并；`[scaffold-seed]`（种子文件，如客服示例）的变更默认保留你的版本；`[migration]` 附带数据库升级命令；
- **UPGRADE.md**——每个版本的合并指引。

上游升级的操作形态：`git fetch upstream && git merge upstream/master`，冲突按上面的规则处理。这一课你会演练一遍（用本地分支模拟上游）。

为什么这一课才把领地契约当主角？因为前七课你一直住在领地里却毫无察觉——没有冲突的领地，和没有口号没区别。**升级是领地契约的验证时刻**：只有当你真的拉下一个上游版本、真的面对一次合并，你才知道"框架不踩你的领地"是制度保证还是一厢情愿。这一课就是替你提前踩这个时刻。

### 框架为什么这样设计：内部 DB 是 source of truth，Langfuse 是旁路

钩子问题 1 的答案就写在"旁路"两个字里。把这条依赖方向画出来：业务 → 内部 DB（必达），业务 → Langfuse（尽力）。**观测数据的写入路径，永远不横在业务的关键路径上。**

这个取舍的另一面是：Langfuse 挂了、升级了、被你切成 `none`，你的 Agent 照常对话，工作台 Traces 照常可查——观测体验降级，业务和数据零损失。反过来如果观测是主路：观测系统一抖，生产对话跟着抖，你就把"看清楚系统"变成了"系统的单点"。**凡是可能故障的外部依赖，都必须设计成"挂了也不拖累主线"**——这是所有生产系统的通律，框架只是把它执行得很彻底。

顺带回答"为什么强调自部署（数据在你的服务器上）"：Trace 里是真实的用户问题、调用参数、费用归因——这些是敏感数据。旁路可以换（langsmith 也行），数据主权不能让。"可切换但不宣传完全等价切换"是诚实的工程表述：各后端能力有差异，切换是降级/升级的权衡，不是魔法。

### 框架为什么这样设计：定义和数据走两条路

步骤 1 里那句"镜像带定义，不带数据"，值得升格成一条设计原则来看。它回答的是每个部署系统都逃不掉的问题：**镜像里到底该装什么？** 答案是：所有随代码演进的东西（代码、Agent 定义、评测集——它们在 git 里有版本、能回滚）；排除所有随运行累积的东西（知识库 chunk、模型槽位映射、Trace 历史——它们的生命周期跟着数据库走，跟着备份策略走）。

想反例：如果把知识库文件烤进镜像，上传一份文档就要重新构建一次镜像——"传个文件"变成一次发布事故；如果把 Trace 挪进镜像层，回滚镜像等于删证据。**定义随代码走（git 管），数据随库走（备份管），环境随配置走（环境变量管）**——三条路各走各的，才不会互相把对方拽下悬崖。

### 框架为什么这样设计：容器启动自动 migrate + init，且幂等

部署过系统的人都有过这种经历：起服务、忘了建表、忘了导数据，第一个请求 500，再回滚补脚本。框架把这个流程压进容器启动命令：`luban migrate && luban init`，并且两者幂等——重复执行不产生副作用。这意味着两件事：**起容器永远是安全的**（编排系统随时可以重启它），**部署脚本永远是简单的**（不需要"先跑这个再跑那个"的顺序编排）。幂等不是洁癖，是给自动化留的活路。

### 框架为什么这样设计：领地契约靠清单和标签，不靠自觉

钩子问题 3 的答案：**承诺必须机器可执行，否则只是口号。** 三件套各管一段：`.lubanagent-upstream` 清单让"哪些文件是你的、哪些是框架的"成为机器可查的事实（上游改动 CI 会先扫一遍，动到 user-owned 直接拦截）；CHANGELOG 的领地标签让每一次上游变更**自带合并指令**——你不用读 diff 猜意图，标签告诉你该合并、该保留、还是该跑迁移；UPGRADE.md 把这版本的特殊步骤写成清单。三层合起来，"跟上游升级"从玄学变成流程。

## 3. 动手：主线步骤

### 步骤 1：起全栈

一条命令，五个服务。先别急着敲，看一眼这条命令的两个词：`-d` 是后台运行（终端还给你），`--build` 是先构建镜像再起（第一次必须，之后镜像没变可以省）。compose 文件把五个服务的镜像、端口、依赖关系、健康检查全部声明在内——**这份 YAML 就是这个项目的部署拓扑图，值得打开从头读一遍，比任何架构文档都准。**

```bash
docker compose up -d --build
```

首次构建约 3-5 分钟（含前端构建）。起来后五个服务：

| 服务 | 端口 | 角色 |
|---|---|---|
| app | 8000 | 后端 API + 工作台（同端口）；容器启动时自动跑 `luban migrate && luban init`，幂等，重起安全 |
| mysql | 3306（内部） | 生产数据库 |
| langfuse | 3000 | 观测 UI |
| langfuse-db | —（内部） | Langfuse 自己的 Postgres |
| mock-biz | 9100 | 客服示例的假业务系统 |

五个服务里最容易被小看的是 mock-biz。它存在的意义是：客服示例的查单/退款工具得有个地方调——一个真的订单系统。部署这个栈时想一件事：**将来真实落地，这个位置站的就是你的业务系统**——Agent 系统不吞并业务系统，而是和它并肩、通过接口互调。这一课的栈里每个服务的位置，都对应着真实生产架构里的一个坑位。

还有个细节：mock-biz 在 compose 里没映射宿主机端口——app 是通过 compose 内网的服务名（`BIZ_BASE_URL=http://mock-biz:9100`）调它的，9100 是容器网络里的端口，你在宿主机上 curl 不到。又是那个"视角"问题：有些端口属于容器网络，不属于你。

✅ 你应该看到：`docker compose ps` 五个容器全部 `running`；其中 app/mysql/langfuse-db 配了 healthcheck、过一会显示 `running (healthy)`，langfuse 和 mock-biz 只显示 `running`（它们没配 healthcheck，**不是故障**）。浏览器开 http://localhost:8000 ——工作台出来了，这次不是 Vite 开发服务器，是镜像里构建好的前端。

注意那两行"没有 healthcheck 不是故障"——**判定一个系统是否正常，看它声明的健康标准，不看你顺手的直觉。** healthcheck 是服务对外的体检承诺，没承诺就是没承诺，五秒的"它是不是挂了"的疑心，是这一课送你的生产思维热身。

打开 `docker-compose.yml` 逐行读时，重点盯五样东西——它们是所有编排文件的通用词汇：

- **ports**——绑在 `127.0.0.1` 上（演示不把端口暴露到外部网卡，生产上用反向代理挡在前面）；
- **environment**——容器的全部配置注入点，你加模型 Key、Langfuse Key 都在这里；
- **depends_on**——启动顺序：app 等 mysql 通过健康检查才起（`service_healthy`），依赖关系不是装饰，是排障时的第一现场；
- **healthcheck**——每个服务对外的体检承诺，`docker compose ps` 里那个 `(healthy)` 就来自这里；
- **volumes**——四个数据卷（MySQL 数据、Langfuse 数据、知识库文件、头像文件），标出了"哪些数据出了镜像、要靠卷活着"。

更值得看的是 Agent 列表：你的 my-lib-assistant、my-lib-triage、my-lib-rules **都在**（内置客服也在）。因为镜像构建时把 `app/` 领地整棵 COPY 了进去（`.dockerignore` 不排除它），容器启动时 `luban init` 会扫描 `app/agents/*.yaml` 全量导入——你跟完第 2-7 课的成果，跟着代码一起进了生产栈。这就是"定义即代码"的好处：Agent 定义可版本化、随镜像走，不用手动搬运。

但分清楚**不在**的东西：8000 端口后面是一个全新的 MySQL 容器库，你开发库里的**运行时数据**一样都没跟过来——知识库的 chunk（第 4 课上传的文档）、模型注册与槽位映射（第 3 课两步 PUT 的结果）、Trace 历史。镜像带定义，不带数据；数据要么对生产库重做一遍，要么另行迁移。定义和数据走两条路，这是部署任何系统前都值得先想清楚的那条线。

### 步骤 2：在生产栈上跑一次对话

为什么对话对象选内置的客服 Agent 而不是你的 my-lib-assistant？因为客服示例自带完整的工具链和 mock-biz 假业务系统——在生产栈上它能展示"全链路都在"：模型、工具、业务系统、观测。你的 my-lib-assistant 也在栈里（下一步验证），但它依赖的模型注册和知识库数据还没迁过来——先验证系统，再补数据。

```bash
curl -N -X POST http://localhost:8000/v1/agents/customer-service-bot/runs \
  -H "Content-Type: application/json" \
  -d '{"input": "帮我查一下订单 ORD-1001"}'
```

（诚实说：零密钥状态下生产栈和开发栈一样跑 FakeLLM——固定一句台词，不做工具决策，所以这单不会真的"查"。mock-biz 容器确实在栈里等着，但要真走通查单/审批，先往 compose 的 app 服务 `environment` 加你的 API Key 环境变量（如 `DEEPSEEK_API_KEY`），`docker compose up -d app` 重建，再对生产库重做第 3 课的两步——`PUT /v1/models` 注册模型、`PUT /v1/brain-mappings` 绑槽位。）

✅ 你应该看到：完整的 SSE 事件流，和第 1 课那条 curl 结构相同（回复内容也是 FakeLLM 那句固定台词）——生产栈和开发栈跑的是同一套代码。

**现在就对照一遍**：把这条 SSE 的事件序列和第 1 课记录的比一比。事件名、顺序、结构完全一致——你在开发栈上写的一切调试经验（怎么读事件流、怎么定位工具调用），到生产栈上原样可用。**开发/生产同构，是"调试技巧保值"的全部前提。**

### 步骤 3：接 Langfuse，双端回放

compose 已经把 `OBSERVABILITY_BACKEND=langfuse` 和 `LANGFUSE_HOST=http://langfuse:3000` 配好了，缺的只有两把 Key。往 compose 的 app 服务 `environment` 里加两行：

```yaml
      LANGFUSE_PUBLIC_KEY: pk-lf-...   # 浏览器开 http://localhost:3000，注册账号后在 Settings 里创建
      LANGFUSE_SECRET_KEY: sk-lf-...
```

两个别踩的坑：一是别想着改根目录 `.env`——`.dockerignore` 排除了 `/.env`，它根本进不了镜像；二是 `LANGFUSE_HOST` 保持 compose 里已有的 `http://langfuse:3000` 别动——那是 app 容器在 compose 网络里找 Langfuse 的地址，改成 `localhost:3000` 就变成"app 容器自己"了，Langfuse 会不可达。你自己用浏览器访问 Langfuse 时才是 `localhost:3000`，两个视角别混。

把这个"视角"问题说透：`localhost` 永远指"说话的进程自己"。你在宿主机终端里说 localhost，指的是宿主机；app 容器里的进程说 localhost，指的是那个容器。compose 网络里的服务互相找对方，用的是服务名（`http://langfuse:3000`）——这是 compose 的 DNS 在服务名和容器 IP 之间做的翻译。**配置文件里写的每一个地址，先问一句"这是谁的视角"，能省掉一整类玄学故障。**

第一个坑值得多看一眼，它背后是生产铁律：**密钥不走镜像。** `.env` 被 `.dockerignore` 排除，是为了让"镜像 = 纯净的代码 + 依赖"；Key 属于环境配置，走环境变量注入——同一个镜像，配上不同的 Key 就是不同的环境。把密钥烤进镜像，等于把家门钥匙焊在门上。

`docker compose up -d app` 重建 app 使 Key 生效，然后再跑一次步骤 2 的对话。

✅ 你应该看到：**Langfuse**（http://localhost:3000，首次访问注册管理员账号）的 Traces 列表里出现这次 Run，点开能看到完整的调用树；**工作台 Traces 页**也能回放同一条——双端同源，一处不留另一处也查得到。配置前的那些 Run 只在工作台里（内部 DB 一直都在写）——这正是"内部库 source of truth、Langfuse 旁路"的直观体现。

那个"配置前的 Run 只在工作台里"的细节，就是钩子问题 1 的实物演示：**Langfuse 加入之前的历史记录一根毛都没少**——因为它们从来不是存在 Langfuse 里的。旁路后加、旁路可换，主线的数据一天都没离开过你自己的库。

### 步骤 4：演练「跟上游升级不丢改动」

这是毕业前最重要的一课。用本地分支模拟上游发新版（在你的开发仓库、不是 Docker 里）。

先说为什么用"本地分支模拟"而不是直接对真上游操作：演练的价值在于**可以反复、可以搞砸**。本地分支随便建随便删，merge 搞砸了大不了 reset；对真上游操作一旦踩坑，你的领地可能当场挂彩。**危险的操作先在沙盘上推演，是生产纪律，也是学习纪律。**

开始前先 `git status` 确认工作区干净——你 `app/` 里有未提交改动的话，先 commit 到 master，否则下面 `git commit -am` 会把它们一起卷进演练分支。

```bash
# 1. 制造"上游新版本"：从当前点拉一个分支，改一处框架文件（模拟上游修 bug）
git checkout -b simulated-upstream
echo "# upstream patch" >> lubanagent/runtime/context_builder.py
git commit -am "simulated upstream change"
git checkout master

# 2. 回到 master——你自己的改动已 commit 在 master 上（所以上面要求先清工作区）

# 3. 合并"上游"
git merge simulated-upstream
```

✅ 你应该看到：合并干净完成（无冲突或冲突只在框架文件）——`app/` 下你的全部产出（agents/tools/datasets/graphs/multiagents）原封不动，框架文件更新了。

这次合并能这么顺，本质是**两个开发线在空间上不相交**：模拟上游只改了 `lubanagent/`，你的提交只在 `app/`——git 的三方合并对不相交的改动从不为难人。真正考验规则的是双方都改同一文件的时刻，那就是 CHANGELOG 领地标签和 `.lubanagent-upstream` 清单上班的地方（见常见坑第三条）。

用下面四条命令验一遍，再收尾：

```bash
ls app/agents/          # my_lib_assistant.yaml 还在
git diff simulated-upstream -- app/   # 你的领地与上游无交集
git reset --hard HEAD~1               # 真正还原模拟改动：这次 merge 是 fast-forward，master 已经指在演练提交上，光删分支引用不会让代码回退，必须 reset 回 merge 之前
git branch -D simulated-upstream      # 清理演练分支（reset 后它不再合并进 master，-d 会拒绝，用 -D 强删这个一次性的演练分支）
```

收尾确认：`git log --oneline -2` 里看不到 "simulated upstream change" 那条提交，`lubanagent/runtime/context_builder.py` 尾部也没有 `# upstream patch`——框架领地干净如初。

把这次演练和概念节的三件套对上号：清单（`.lubanagent-upstream`）告诉你 `app/` 全是 user-owned、上游根本不会碰；这次模拟上游也确实没动 `app/`（git diff 为空就是证明）；如果有冲突，你会按 CHANGELOG 的标签决定听谁的。**演练一次，三件套就从"背过的概念"变成"用过的工具"。**

真实场景里把 `simulated-upstream` 换成 `upstream/master`，配合 CHANGELOG 的 `[migration]` 标签跑 `luban migrate`、`[scaffold-seed]` 的保留指令处理种子文件——流程完全同构。这套"能长期跟上游"的能力，是你选"基座"而不是"一次性模板"的根本理由。

### 步骤 5：升级终检——评测回归

模拟升级后，跑第 6 课的评测集做终检（在开发环境。演练里的模拟改动刚才已还原，这一步主要是把习惯练成肌肉记忆——真实升级合并完成后，它就是不折不扣的硬检查）：

```bash
.venv/bin/luban eval run my-lib-assistant --dataset app/datasets/my_lib_eval.yaml --compare my-baseline.json
```

注意这条命令的三个前提：在开发环境跑（生产栈还没有你的评测基线）、对的是第 6 课存的旧基线、跑之前模拟改动已还原。三个前提都为同一个目的服务——这一步练的是**流程**，不是这次的结果。

✅ 你应该看到：`regressions: []`。**升级（或任何大动作）之后跑一次评测回归**，这是这套教程希望你带走的工作习惯——它把"应该没改坏"变成"没改坏，有证据"。

体会一下这条命令在这个时间点的分量：git 合并验证的是**代码**没丢，评测回归验证的是**行为**没变。两道检查一个管领地、一个管质量，合起来才是完整的"升级没出事"。只查代码不查行为，你防不住"依赖版本升级导致模型行为漂移"这类代码层面看不见的事故。

顺带记一条基线的生命周期：基线不是一次性的存档。日常改动若评测确认无回归，旧基线继续用；若行为是**有意**变更（比如改了人设、换了模型），跑完 `--compare` 确认差异全部符合预期后，重新 `--save` 固化新基线并在提交说明里写明原因——基线和代码一样，是需要版本管理与变更理由的资产。

### 步骤 6：收工（可选）

```bash
docker compose down        # 停栈（数据卷保留）
docker compose down -v     # 连数据卷一起清（彻底重置）
```

两条命令的区别是"数据卷"三个字：第一条停服务、留数据（下次 `up` 回来一切如旧），第二条连 MySQL 的数据一起抹掉。在生产语境里，这就是"重启"和"重置"的区别——**敲第二条之前，先想清楚你愿不愿意失去这个库里的所有 Trace 和知识库文件。**

顺带一个组合技：只重置数据、不动镜像——`down -v` 之后重新 `up`，本地镜像缓存还在，栈很快就能起来。生产语境里这个组合对应"重建一个干净环境"：镜像还是那个镜像（行为可复现），数据从零开始积累。

- [ ] Langfuse 与工作台双端能放同一条 Trace
- [ ] 模拟升级合并完成，`app/` 领地零改动
- [ ] 升级终检 `regressions: []`

## 5. 常见坑

这一课的坑密度是八课之首，因为 Docker 和 git 都是"命令对了但视角错了照样翻车"的典型。逐条对号入座，每条都建议撞到再回来读第二遍。

**`docker compose up` 构建慢/失败。** 前端构建吃网络（npm 源），参考第 1 课坑 5 换镜像。构建失败看 `docker compose logs app`。

**Langfuse 配了但 Trace 不出现。** 检查三点：Key 是否从 Langfuse Settings 里创建（不是自己编的）、app 容器是否重建过（环境变量在容器创建时注入）、`LANGFUSE_HOST` 从 app 容器的视角是否可达（compose 网络内是 `http://langfuse:3000`，宿主机访问才是 `localhost:3000`——compose 文件里已配好，自己改时别改错视角）。

这条坑里最阴的是第二点：**环境变量是容器创建时注入的，改 compose 文件不等于生效**——必须 `docker compose up -d app` 重建容器。你可以用 `docker compose exec app env | grep LANGFUSE` 直接看容器里的实际值，别猜。

**合并冲突比预想多。** 看冲突文件的领地归属：framework 的优先上游（你本来就不该改它），scaffold-seed 的优先自己（`git merge -X ours`），你的 user-owned 文件上游根本不会动。拿不准时对照 `.lubanagent-upstream` 清单。

**生产栈里我的知识库/模型配置不见了。** 正常——镜像只带定义不带数据：`app/` 领地整棵 COPY 进镜像、init 自动导入你的 Agent，但 DB 里的运行时数据（知识库 chunk、模型注册与槽位映射、Trace 历史）不会跟镜像走。补齐 = 对生产库重新上传知识（第 4 课的操作）+ 重做第 3 课的两步 PUT，Trace 则从头积累。

把四条坑的共同点提出来：**它们全是"视角"问题**——构建失败是网络的视角，Trace 不出现是容器的视角，冲突处理是领地的视角，配置消失是定义与数据的视角。生产排障的第一反应永远是"我现在站在谁的视角上看"。

## 6. 练习

三道练习是本课真正的功力所在：A 让你亲手补齐"数据侧的发布"（教程主线为了控制篇幅只带了定义侧），B 让你用实验验证观测分层，C 让你产出一份自己的验收清单——那是你下一个项目的起点。

**练习 A（模仿）**：验证镜像的边界。栈起来后先确认两件事：工作台 Agent 列表里有你的 my-lib-assistant（定义随 `app/` 领地进了镜像），知识库却是空的（chunk 在你的开发库里，没跟镜像走）。然后给 compose 的 app 服务加上你的 DeepSeek Key（环境变量）重建，对生产库重做第 3 课的两步（`PUT /v1/models` + `PUT /v1/brain-mappings`），再补一次知识上传，把"帮我查订单 ORD-1001"真正走通——这一趟补的就是"数据侧的发布"。

**练习 B（变式）**：把 `OBSERVABILITY_BACKEND` 切成 `none`，重建，跑一次对话——工作台 Traces 依然全量可放（内部 DB 不依赖观测后端）。再切回 langfuse。理解"可关闭"不是"关了就瞎"。

**练习 C（综合，毕业验收）**：写一份你自己的「毕业验收单」：列 8-10 条你认为这个项目必须成立的验收项（至少覆盖：三种执行形态各一条、守门一条、评测回归一条、升级合并一条），逐条跑通并留证据（命令输出/截图）。这份单子就是你以后带自己的 Agent 项目上线的 checklist 初稿。

## 7. 思考题

1. 生产清单里建议改掉 MySQL 默认密码和 Langfuse 默认密码，为什么密钥类配置不直接写进镜像？（提示：镜像会被推到仓库、分发给同事——想清楚"谁都能拿到镜像"意味着什么。）
2. `OBSERVABILITY_BACKEND=none` 时你的评测回归还能跑吗？（提示：回看第 6 课——`--compare` 走哪条链路，依赖不依赖观测后端。）
3. 真实升级时 CHANGELOG 里出现 `[migration]` 标签，你在 merge 之后、重启服务之前还必须做哪件事？漏了会发生什么？（提示：容器启动命令里那两个幂等操作，其中之一。）

## 9. 小结与下一课预告

回收开头的三个问题：

1. **观测挂了，Agent 不挂**——内部 DB 是必达的 source of truth，Langfuse 是尽力而为的旁路，外发失败不阻断业务；
2. **没有前端服务器，因为前端是构建产物**——node 打包进镜像、FastAPI 同端口托管，一个镜像一个端口一条发布流水；
3. **升级承诺靠机器兑现**——`.lubanagent-upstream` 清单 + CHANGELOG 领地标签 + UPGRADE.md 指引，让"不冲掉你的领地"成为可执行的流程而非口头善意。

八课走完，你手里是完整的四级火箭：**会干活的 Agent（2-5 课）→ 护住的评测（6 课）→ 编排与团队（7 课）→ 带得走的部署与升级（8 课）**。这不是教程的句号——第 9 课的毕业设计里，你要把整套东西独立跑一遍，那才是你自己的第一行生产线。
