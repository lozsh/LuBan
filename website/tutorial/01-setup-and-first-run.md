# 本地运行

安装并启动本地 API 与工作台，验证一次对话、SSE 事件和 Trace。需要 Python ≥3.11、uv；运行工作台还需要 Node.js ≥20。默认 SQLite 与 FakeLLM 不需要外部密钥，固定回复只用于验证链路。

## 1. 实现方式：你装的到底是什么

**为什么是克隆仓库，不是 `pip install`？** 因为你跟 LubanAgent 的关系不是"使用一个库"，而是"住进一个基座"。你要在里面长期写自己的 Agent、自己的工具——这些代码就住在仓库的 `app/` 目录里。类比一下：用库像租酒店的房间，基座像拿了毛坯房的钥匙——结构是别人的，装修是你自己的，而且物业（框架）升级不会铲掉你的装修。`app/` 你的领地和 `lubanagent/` 框架领地的分界，「Agent 基础概念」讲过，从本文起你每次打开仓库都会看到它。

**三条命令各干了什么。** 后面要跑的 `migrate`、`init`、`start` 不是三个咒语，各有一件事干：

- `luban migrate`——建表。在数据库（开发期是 SQLite，一个本地文件，免安装）里创建全部表结构。
- `luban init`——种子落库。把仓库自带的种子（一个假模型 + 9 个 Agent 的 YAML 定义）写进数据库。
- `scripts/dev.sh start`——起服务。后端 API 在 8000 端口，工作台前端在 5173。

本文结束时，你机器上会住着四样东西——先点名，后面对着它们排障不慌：

| 住客 | 是什么 | 住在哪 |
| --- | --- | --- |
| 后端 API | FastAPI，所有 REST/SSE 请求的入口 | :8000 |
| 工作台前端 | Vite 开发服务器 | :5173 |
| 数据库 | SQLite 本地文件（免安装），表结构 + 种子数据都在里面 | 位置见 `.env` 配置 |
| 假大脑 | FakeLLM，空库默认绑定四个初始槽位 | 数据库的模型注册里 |

这里有个认知现在就要立起来，「创建自己的 Agent」马上要用：**YAML 是投喂口，数据库才是存储**。`luban init` 把 `app/agents/*.yaml` 里的定义灌进数据库，之后系统运行读的是库，不是那个 YAML 文件。所以改 YAML 不会自动生效，要重跑 `luban init`。先记住，「创建自己的 Agent」你会亲手验证这个行为。

**零密钥能跑到哪一步？** 两个兜底让你不用任何 Key 就能起全套环境：数据库用 SQLite，模型用 FakeLLM。FakeLLM 是一个"假大脑"——它会走完对话的全部流程（事件流、Trace、记忆一应俱全），但回复永远是同一句固定台词。它的作用是让你零成本验证"链路是通的"；至于查订单、答 FAQ、走审批这些需要真智力的活，要等「接入真实模型」接上真模型（届时你需要一个大模型 API Key，调用费用以供应商实际计费为准）。

最后再领地复习一遍，因为从后续开发起你要开工了：`lubanagent/` 是框架领地，你原则上不动它——本文用到的 API 层、SSE 协议、Trace 落库都住在那里；`app/` 是你的领地，「创建自己的 Agent」的 Agent YAML、以后你的工具和流程都住这里。这套分界由两条 CI 守卫看着：import-linter 拦依赖反向（框架不许 import 你的代码），`.lubanagent-upstream` 清单守卫拦上游改动误触你的领地——这就是"跟上游升级不丢自己的东西"的机制保证，「部署与升级」你会亲手演练一次。

### 框架为什么这样设计：四个"看起来多此一举"的决定

这一节回答你在步骤里迟早会冒出来的四个"为什么"。它们的共同点：答案都不在"怎么做更快"，而在"怎么做不会在三个月后坑你"。

**为什么建表（migrate）和种子（init）是两条独立命令，不合成一条"一键初始化"？** 因为它们是两类变更：建表改的是**结构**（加字段、加索引），种子改的是**数据**（导入、更新 Agent 定义）。分开了，你才能只重跑种子而不碰表结构，也才能在升级后单独补迁移。它们的幂等语义也是各管各的：migrate 幂等靠版本号（跑到 `head` 就不动），init 幂等靠内容比对（下一节细讲）。合成一条，两种语义就搅在一起了。顺带说一句：到「部署与升级」你会发现 Docker 镜像启动时把这两步合在一起自动跑——那是部署层的编排，引擎层始终是两个动作。

**为什么 init 设计成幂等，而不是"跑第二次就报错"？** 想一个真实场景：部署脚本每次发版都要跑初始化。如果 init 不幂等，脚本第二次执行就炸，你就得在脚本里写各种"先检查再执行"的补丁。幂等让"重复执行 = 无害"成为框架保证，而不是你的脚本技巧——这是把复杂度从用户侧挪进框架侧的典型取舍。「创建自己的 Agent」你会看到它更精细的一面：内容没变就不追加版本，内容变了才 +1。

**为什么开发环境用 SQLite、生产用 MySQL？** 因为你第一天要跨过的门槛越少越好——SQLite 是一个文件，不用装服务、不用配账号，`rm` 掉就重置。而生产要的是并发和持久，那是 MySQL 的活。关键在于：**两边的代码路径是同一套**，换数据库 = 改一条连接配置，你写的 Agent、工具、流程一个字不用动。基座替你扛住了"开发顺手"和"生产靠谱"之间的矛盾。

**为什么默认模型是 FakeLLM？** 因为它把两类问题解耦了：链路问题（装没装对、服务起没起、事件流通不通）和智力问题（模型答得好不好）。零密钥环境下链路问题必须能独立暴露——如果你第一次跑就接真模型，报错时你分不清是环境坏了还是模型调不通。「接入真实模型」接上真模型后你还会感谢它的另一个好处：FakeLLM 让工具调用、Trace、评测这些功能可以写自动化测试，整个仓库几百个测试不花一分钱 API 费。

## 2. 操作步骤

### 步骤 1：克隆并安装

```bash
git clone https://github.com/lubanagent-dev/LuBan.git luban-tutorial   # 名字随意，下面统一叫它"仓库根目录"
cd luban-tutorial
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -e ".[dev]"
```

这条命令拆开看：`uv venv` 建一个独立的 Python 虚拟环境（你的依赖不污染系统 Python，搞砸了删掉 `.venv` 目录重来）；`-e ".[dev]"` 装的是**可编辑模式**的 LubanAgent 本体加 dev 附加组——后者是 pytest、ruff 这些开发工具链，跑指南用不上，但你以后在这个仓库里写测试、跑 lint 会用。可编辑模式意味着你改 `app/` 里的代码，服务重启后立刻生效，不用重装。

预期结果：安装滚动输出，末尾无红色报错。首次约 2-5 分钟（取决于网络）。

> Windows 用户：命令里的 `.venv/bin/` 在你的机器上是 `.venv\Scripts\`。

### 步骤 2：配置

```bash
cp app/config/.env.example .env
```

预期结果：仓库根目录出现 `.env` 文件。先不用改任何内容——打开扫一眼就行，你会看到数据库、观测、鉴权几组配置，全部带缺省值，此时一个都不用动。

为什么现在一个都不用动？因为缺省值就是为"零密钥跑通"调好的：数据库指 SQLite，观测后端默认关，鉴权用开发档。这一步的意义是给你看清楚**有哪些旋钮**——等「接入真实模型」要填 API Key、「部署与升级」要接观测后端时，你改的都是这里。

### 步骤 3：建表 + 种子

```bash
.venv/bin/luban migrate
.venv/bin/luban init
```

顺序不能反：先有表，种子才有地方落。init 往库里写数据，表都不存在，写什么？

预期结果：`migrate` 输出一段 Alembic 迁移日志（Alembic 是数据库表结构迁移工具）（`Running upgrade ...`，末行 `migrated to head`）；`init` 逐行输出 9 个 Agent，每个形如 `cs-faq@1`——`@1` 表示首次导入、版本 1。

顺手再跑一遍 `luban init`，这次输出变成 `cs-faq@1 (unchanged)`：内容没变就不追加新版本。`init` 是幂等的，重复跑安全——这个行为「创建自己的 Agent」你会靠它验证"改了 YAML 才产生新版本"。

注意那个 `(unchanged)`：init 判断的不是"这个 Agent 导入过没有"，而是"这次的内容和库里最新版一模一样吗"。同样的内容，跑一百遍也只有一个版本。这个细节现在记下，「创建自己的 Agent」它就是主角。

### 步骤 4：起服务

```bash
bash scripts/dev.sh start
```

首次运行会自动 `npm install` 拉前端依赖（约 1 分钟，之后秒起）。

预期结果：`bash scripts/dev.sh status` 显示——

```
后端 :8000 跑中 (pid ...)
前端 :5173 跑中 (pid ...)
```

两个端口、两个进程：后端是 FastAPI（8000），前端是 Vite 开发服务器（5173）。开发期分开跑，改前端代码热更新不用动后端；到「部署与升级」部署时你会发现两者合进同一个 8000 端口——那是生产形态，现在不用管。

浏览器打开 http://localhost:5173 ，左侧是工作台导航（Agents / Prompt 库 / 模型 / 工具 / Skills / 知识库 / 流程图 / Traces / 评测）；导航最上面还有「调试台」和「用户端聊天」两个入口，步骤 6/7 会分别用到它们。

### 步骤 5：工作台走一圈

别急着对话，先把 9 个页面点一遍，混个脸熟：

混脸熟这件事，用表格记更牢——每页一行，最后一列是它将来"主场"的开发任务：

| 页面 | 放什么 | 什么时候细讲 |
| --- | --- | --- |
| **Agents** | 9 个内置 Agent 的列表——版本、状态、调试入口都在这。你以后自己的 Agent 也住这里 | 「创建自己的 Agent」 |
| **Prompt 库** | 人设模板 | 用到再查[Prompt 库手册](../manual/features/prompt-library.md) |
| **模型** | 模型注册（「接入真实模型」会回来细看模型页） | 「接入真实模型」 |
| **工具 / Skills** | Agent 能调用的工具和能力包 | 「编写业务工具」 |
| **知识库** | 文档上传与切块（「配置知识检索」的主场） | 「配置知识检索」 |
| **流程图 / Traces / 评测** | 图编排拓扑、运行回放、评测报告 | 评测、流程与部署指南逐一回来 |

现在每页都还是"别人家的东西"，看不懂很正常。这一步的目的只有一个：**让你的大脑建立目录索引**——「配置知识检索」我说"去知识库页"，你不用找。哪天忘了某个页面是干嘛的，也回这张表。

预期结果：Agents 页列出 9 个 Agent，`customer-service-bot`（内置客服「小鲁」）排在你眼前。

### 步骤 6：调试台，第一次对话

**Agents 页 → `customer-service-bot` → 进"调试台"**（或直接开 http://localhost:5173/agents/customer-service-bot/debug ），输入：

```
你好
```

预期结果：回复是——

```
你好，我是 LubanAgent。
```

无论你问什么，都是这一句。**这是预期行为，不是坏了**：空库零密钥下，fast/smart/cheap/vision 四个初始槽位都绑着 FakeLLM，它的剧本就这一句台词。槽位可以在模型中心新增、编辑和改名，不限于这四项（见[模型中心](../manual/features/models.md)）。你要在这一步确认的是：对话链路通了——输入被接收、Run 被执行、回复流式吐回来。

多试两句别的（"帮我查订单""你是谁"）你会确认：连人设都没读——"我是 LubanAgent"不是 `customer-service-bot` 的人设里写的「小鲁」。FakeLLM 不看定义，它只负责让管道里有水流过。水是真是假，「接入真实模型」再说。

### 步骤 7：用户端聊天页

开 http://localhost:5173/chat ——这是没有管理侧栏的用户端视角，选 `customer-service-bot` 再说句话。

预期结果：带问候语的聊天界面（问候语来自 Agent 定义里的 `greeting` 字段——定义里的静态文本，不需要模型），回复依旧是那句固定台词。

留意一个对比：问候语是"活的"（来自定义），回复是"死的"（来自 FakeLLM 剧本）。本文你已经摸到了这个框架的一个边界：**定义决定 Agent 长什么样，模型决定它想什么**——前者不需要任何 Key 就在生效，后者是「接入真实模型」的事。

### 步骤 8：用 curl 看原始事件流

图形界面把细节藏起来了，现在扒开看。跑：

```bash
curl -N -X POST http://localhost:8000/v1/agents/customer-service-bot/runs \
  -H "Content-Type: application/json" \
  -d '{"input": "你好"}'
```

这条命令里的 `-N` 是关掉 curl 的输出缓冲——SSE 是一条一条事件推过来的，不关缓冲你会攒一大坨一起看到，感受不到"流"。URL 里的 `customer-service-bot` 就是 Agent 的 key：**一个 URL 路径，定位一个 Agent**，你「创建自己的 Agent」造的小图到时候也是这个格式。

预期结果：一串 `event: ...` / `data: {...}` 帧，肉眼能认出「Agent 基础概念」讲过的那几种事件——

```
event: run.started        ← 开头，带 run_id
event: token.delta        ← 每帧吐几个字（固定台词也是"流式"吐出来的）
event: run.completed      ← 结尾，data 里带完整 output
```

一帧的标准长相是两行：`event:` 行给事件名，`data:` 行给 JSON 负载。将来你写消费代码，就干两件事：按事件名分发、按负载取字段——不管后面有多少种事件，都是同一套解析逻辑。

这就是 SSE（Server-Sent Events）流——你的业务系统将来接 LubanAgent，消费的就是这条流。注意这一跑里**没有** `tool.started` 之类的工具事件：FakeLLM 不做工具决策。接上真模型后（「接入真实模型」），同样的命令会多出 `tool.started` → `tool.finished` 两段——到时候你会回来重跑这条命令做个对照。

把"预告"和"实见"对个账，FakeLLM 的边界就一目了然：

| 「Agent 基础概念」预告的事件 | 本文出现了吗 | 为什么 |
| --- | --- | --- |
| run.started | 出现 | 每次 Run 必发 |
| token.delta | 出现 | 固定台词也是流式吐的 |
| tool.started / tool.finished | 没出现 | FakeLLM 不做工具决策 |
| run.completed | 出现 | 收尾必发 |

为什么逼你用 curl 看一遍？因为工作台只是这套 API 的一个消费者。你以后把 Agent 接进自己的业务系统，对接的就是这条原始流——今天看懂了它，明天调试对接问题时你就能分清"是我客户端解析错了"还是"是服务端真没发这个事件"。顺带记下一个工程习惯：**看不懂一个界面行为时，绕到它背后看原始 API**——这个习惯在「配置知识检索」调检索、「评测与回归」看评测明细时都会救你。

### 步骤 9：回放刚才的现场

工作台 **Traces 页**，找到最近一次 Run（就是刚才 curl 那次），点进去。

预期结果：这次 Run 的完整现场——用了哪个模型（`fake-chat`）、什么时候开始结束。工具调用区是空的（没调用过工具），但结构都在。

「Agent 基础概念」说的"每个事件都留痕"就是这个。以后你的 Agent 说了不靠谱的话，来这调现场——「接入真实模型」接真模型后，这里的工具入参出参、Token 消耗都会丰富起来。

补一个架构事实，「部署与升级」会用到：Trace 首先落在**内部数据库**——它是 source of truth，不看任何第三方脸色；Langfuse、LangSmith 这类观测平台是旁路双写，想接就接、想换就换、想关就关。你今天在这页看到的，永远不依赖任何外部 SaaS。

### 步骤 10：收工（可选）

```bash
bash scripts/dev.sh stop
```

预期结果：`status` 显示两个进程都不在了。想再跑，`start` 回来即可（数据库和种子都还在，不用重新 migrate/init）。

最后这句值得嚼一下：stop/start 循环之间，**状态是持久的**——它住在 SQLite 文件里，不在进程内存里。这就是第 2 步"配置不用动"的底气：环境是一次搭好、反复使用的，不是每次启动都从零来。

### 本文命令速查

五条命令收在这里，「部署与升级」部署前你还会用到它们：

| 命令 | 干什么 | 重复执行 |
| --- | --- | --- |
| `.venv/bin/luban migrate` | 建表（Alembic 迁移到 head） | 安全，到 head 就不动 |
| `.venv/bin/luban init` | 种子落库（假模型 + 9 个 Agent） | 安全，内容不变就 `(unchanged)` |
| `bash scripts/dev.sh start` / `stop` | 起 / 停前后端 | —— |
| `bash scripts/dev.sh status` | 查前后端进程状态 | —— |
| `curl -N -X POST http://localhost:8000/v1/agents/customer-service-bot/runs ...` | 裸看一次 Run 的 SSE 事件流 | —— |

分清两类命令：`migrate` 和 `init` 是一次性基建（偶尔跑），`start` / `stop` / `status` 是日常开关（天天用）。分清了，你就知道哪些命令该记住、哪些忘了再回来查。

## 4. 常见问题

**问它查订单/答 FAQ，它还是那句固定台词。** 预期行为，不是坑——零密钥下 FakeLLM 不做工具调用、不做检索，它只负责证明链路是通的。查单、审批、FAQ 引用这些体验从「接入真实模型」接上真模型开始。

**`scripts/dev.sh` 报 permission denied。** 用 `bash scripts/dev.sh start` 显式用 bash 跑（本指南所有命令都写全了），或 `chmod +x scripts/dev.sh` 一次。

**端口被占。** `8000`（API）、`5173`（前端）任何一个被占，对应服务起不来。`lsof -i :8000` 找到占用进程处理掉。

**`npm install` 卡住或失败。** 网络问题，多数是 npm 源。换国内镜像（`npm config set registry https://registry.npmmirror.com`）后删掉 `lubanagent/ui/node_modules` 重跑。

**`luban init` 报数据库相关错误。** 九成是忘了先跑 `luban migrate`（表还没建）。按步骤 3 的顺序来。

一个通用的排障心法，比任何单个坑都值钱：**卡住时先跑 `bash scripts/dev.sh status`**。三个症状对三种病——服务没起（去 start）、服务起了但检查点对不上（回上一个绿色检查点重做）、服务起了且检查点全绿但还是不对（提 Issue）。别在没验证上一行命令的情况下连跑三行——那样坏的是哪一步就永远说不清了。
