# 接入真实模型

注册真实模型并绑定 fast / smart / cheap / vision 槽位。前置条件：服务已启动，并且有可用的模型凭据和连接地址。使用示例前检查模型供应商的接口、价格和可用模型。


## 1. 实现方式：为什么 Agent 不该写死模型名

设想你把 `deepseek-chat` 这个模型名直接写死在小图的代码里。三个月后会发生三件事中的一件：

- DeepSeek 涨价了，你想把日常对话换到便宜的 Qwen——改代码，发版；
- DeepSeek 服务抖动，你想临时降级到备胎模型——改代码，发版；
- 来了个视觉任务，需要换多模态模型——又是在同一个地方动刀。

每次都是"改代码 + 发版"，而模型选型明明是个**运营决策**，不是工程决策。

LubanAgent 的解法是中间加一层间接：**逻辑槽位**。Agent 定义里不写模型名，写的是"我需要哪种档次的大脑"——`fast`（快而便宜，典型用途是路由、分类这类短平快任务）、`smart`（主力推理）、`cheap`（批量低值任务，省钱跑量）、`vision`（多模态）。槽位到具体模型的映射存在数据库里，运行期解析。于是换模型变成了改一条映射记录：Agent 一个字都不用动，新起的对话立即走新模型。

把整条解析链摆出来你就明白这层间接有多薄、多干净：

```text
Agent 定义：brain: smart        ← 只表达"我要主力大脑"
      ↓ 运行期查库
槽位映射：smart → deepseek-chat  ← 换模型就改这一行
      ↓ 运行期查库
模型记录：base_url / api_key_env / capability / 单价
      ↓
OpenAI 兼容客户端发出请求
```

Agent 永远只认识槽位。槽位指向谁、那个模型长什么样、多少钱一次——全在库里，随时可改。

### 接入方式：为什么 OpenAI 兼容协议是默认

步骤 2 的注册请求里有个字段值得提前说：`factory: "openai_compat"`。它声明的是「用哪个工厂模块来连这个模型」。

OpenAI 的请求/响应格式早就成了行业事实标准——DeepSeek、通义、智谱这些厂商，以及 vLLM、Ollama 这类私有化部署方案，全都提供 OpenAI 兼容端点。这意味着一套客户端代码可以覆盖绝大多数模型：步骤 2 里的三个接入字段（`base_url` + `api_key_env` + `model_name`）就是全部接入成本，不存在「每接一个厂商写一轮适配」的问题。

万一哪天你要接一个不提供兼容端点的厂商，适配代码也只加在模型工厂这一个模块里——Agent 定义、槽位映射、工具、知识库全部无感。适配差异收敛在一个窄点上，是这个设计能长期维持的前提：**抽象会破，所以适配点必须窄**。

这套机制还有个隐藏好处：**计费**。注册模型时带上单价（每千 token 输入/输出价格），每次 Run 的 Token 消耗就能换算成钱，按 Agent 归因——你花的每一分钱都查得到出处。

把计费链路拆开看，一共三步：

1. **消耗记账**：每次 Run 结束，本次对话实际消耗的输入/输出 Token 记进 Trace——实测值，不靠估算；
2. **单价折算**：Token 消耗乘以注册模型时填的两个单价字段，得到这笔 Run 的费用——所以单价必须填对，否则折算无从谈起；
3. **按 Agent 归因**：费用挂在 Run 上，Run 挂在 Agent 上——按 Agent 维度的成本统计因此对得上账。

三步全在框架内部完成，不需要访问任何厂商账单系统——这也是它**实时**的原因：对话结束的瞬间费用就在 Trace 里了，不用等月底对账。

最后交代 FakeLLM 的退场方式：它不会被卸载，只是不再被槽位引用。哪天你想零成本跑链路测试，把槽位指回 `fake-chat` 就行——假大脑一直在那候着。

这个「候着」不是 nostalgia，是工程手段。本地运行与定义验证你其实一直在用它：零密钥跑通全链路、CI 里确定性回归、演示时不烧钱——全靠一个行为固定、永远在线、永不宕机的假大脑。真模型上来之后它退居幕后，但每次你想验证「问题出在链路还是出在模型」时，第一个动作永远是切回 `fake-chat` 做对照。这个排障习惯从今天开始养成。

### 框架为什么这样设计

三个设计点，每一个都对应你将来会撞上的真实麻烦：

**为什么槽位写进 Agent 定义、模型放进数据库，而不是干脆让 Agent 直接配模型名？** 因为两者的变化节奏完全不同：Agent 的人设、工具、边界是工程资产，改一次要走测试和评审；模型选型是运营决策，随时要变。把高频变更的（模型）从低频变更的（Agent）里隔离出去，各自才能按各自的节奏动。这也是「创建自己的 Agent」"定义入库版本化"的另一半意义——版本快照钉住的是行为契约，不该被模型选型牵着走。

**为什么 Key 用 `api_key_env` 引用环境变量，而不是把 Key 存进数据库、更不让你随请求传上来？** 数一遍泄漏面就懂了：存代码，会进 git 历史；存 YAML，会跟着定义导出迁移；随 API 请求传，会进服务日志和 Trace。引用环境变量名而不是 Key 本身，Key 只活在服务进程的环境里——数据库被导出、定义被分享、日志被翻查，都拿不到 Key。

**为什么单价字段（`input_price_per_1k` / `output_price_per_1k`）放在模型注册里，而不是做成全局配置？** 因为"费用 = Token 消耗 × 单价"，Token 消耗记在每次 Run 上，单价只可能属于模型——同一个 smart 槽位上周指 A 模型、本周指 B 模型，两段时间的费用要各用各的单价折算。单价跟着模型走，按 Agent、按模型、按天的成本归因才对得上账。步骤 9 你会亲手验一次这笔账。

## 2. 操作步骤

这些步骤为后续工具调用、评测和部署准备模型连接与槽位映射。

### 步骤 1：配置 API Key

打开 `.env`（「本地运行」从 `.env.example` 复制来的那份），找到 `DEEPSEEK_API_KEY=` 这一行，把 Key 填到等号后面：

```
DEEPSEEK_API_KEY=sk-你的key
```

注意是**填在原有那行上**，别用 `echo ... >> .env` 往文件末尾追加——文件里本来就有一行空的 `DEEPSEEK_API_KEY=`，追加会留下两条同名键，虽能跑但是脏行。（Key 从 platform.deepseek.com 注册获取。用其他厂商就填对应的 `DASHSCOPE_API_KEY` / `ZHIPUAI_API_KEY` / `OPENAI_API_KEY` 行。）

填完 Key 要重启一次服务才生效（环境变量在进程启动时读入，服务起着也读不到新值）：`bash scripts/dev.sh restart`。

 检查点：`grep DEEPSEEK .env` 只打出一行，且是你的 key（这个文件已被 gitignore，不会被提交——**任何情况下都不要把 Key 写进代码或 YAML**）。

注意这条纪律和上面 `api_key_env` 的设计是同一件事的两面：框架在数据库那一侧替你挡住了 Key，你在 `.env` 这一侧也别亲手把它送进 git。

顺带一提，`.env.example` 里那行空的 `DEEPSEEK_API_KEY=` 就是留给你填的——从「本地运行」复制文件起，这个约定一直没变。

### 步骤 2：注册模型到模型工厂

服务起着（`bash scripts/dev.sh start`），然后：

```bash
curl -X PUT http://localhost:8000/v1/models -H "Content-Type: application/json" -d '{
  "key": "deepseek-chat", "provider": "deepseek", "model_name": "deepseek-chat",
  "factory": "openai_compat", "api_key_env": "DEEPSEEK_API_KEY",
  "base_url": "https://api.deepseek.com/v1",
  "capability": {"tool_calling": true},
  "params": {"input_price_per_1k": 0.002, "output_price_per_1k": 0.008}
}'
```

看懂这个请求：`api_key_env` 说的是"Key 从哪个环境变量读"（不是把 Key 传上来）；`base_url` 是 OpenAI 兼容端点（换成 vLLM/Ollama 就是你的自建地址）；`params` 里两个单价字段供费用归因用——数字以 DeepSeek 官网当前价格为准，下面用的是本指南写作时的价格，随时可改。也可以走工作台**模型页**可视化完成同样的事。

还有个字段别漏看：`capability: {"tool_calling": true}`。这是模型能力在注册时的**声明**——运行期框架先校验再执行：Agent 要调工具，槽位解析到的模型却声明不支持 tool calling，请求不会照发，而是受控降级到可用模型。能力声明与真实能力不一致的坑（比如某开源模型宣称支持工具调用但格式不稳定），在注册时就被隔离成一条数据问题，而不是运行时的玄学故障。

这一步做的事，用第 2 节的图说就是往中间那层"槽位映射"的下一级——模型记录表——插了一行。Agent 和槽位此时都还不知道它的存在。

预期结果：返回 200 与模型详情。工作台模型页出现 `deepseek-chat`。

### 步骤 3：绑到 smart 槽位

```bash
curl -X PUT http://localhost:8000/v1/brain-mappings -H "Content-Type: application/json" \
  -d '{"profile": "smart", "model_key": "deepseek-chat"}'
```

预期结果：返回 200。查询映射确认：`curl http://localhost:8000/v1/brain-mappings?env=dev` 里 smart 指向 deepseek-chat。

到这里，第 2 节那条解析链全部接通：小图（brain: smart）→ smart（deepseek-chat）→ 模型记录（api.deepseek.com）。下一个开口的对话就走了真模型。

### 步骤 4：兑现时刻——问小图是谁

调试台选 `my-lib-assistant`，输入：`你是谁？能帮我做什么？`

预期结果：一段**用你的人设说话**的回复——自称小图、列出借阅查询/挂失/规章咨询的服务范围、超范围会建议去前台。和「本地运行」的固定台词对比，这就是真大脑的差别。

这个时刻值得停下来品一下：你在「创建自己的 Agent」写的 YAML 从没被改过，但它的表达力从"复读机"变成了"活人"。**定义没变，能力变了——变的只是定义底下那条解析链的终点。**

### 步骤 5：看一次真实的工具调用

换 `customer-service-bot`（它有工具），调试台输入：`帮我查一下订单 ORD-1001`

预期结果：回复里出现"无线蓝牙耳机""299 元"这样的真实订单数据——这些数据来自本地 9100 端口的 Mock 业务服务（客服示例的假订单系统）。如果报"连接失败"，先起它：

```bash
.venv/bin/python -m demos.customer_service.mock_services   # 占终端，建议开新窗口或加 &
```

再重跑「本地运行」那条 curl（`curl -N -X POST .../customer-service-bot/runs -d '{"input": "帮我查一下订单 ORD-1001"}'`），这次事件流里多出两帧——

```
event: tool.started      ← 模型决定调 query_order
event: tool.finished     ← 代码真去 9100 拿回了订单数据
```

「Agent 基础概念」画的“模型说、代码做”，现在在你终端里。

顺带校准一下你对事件流的理解：`tool.started` / `tool.finished` 这对事件是你以后排障的心电图。模型嘴上说“我帮你查了”但 started 没出现——它在编；started 出现但 finished 迟迟不来——工具卡住或超时；finished 回来了但答案不对——模型组织答案的环节出了问题。三段式定位，比“反正不对劲”高效得多。这个分层思路在「编写业务工具」会升级成完整的排障流程。

这两帧事件值得记住格式：`tool.started` 出现意味着模型已经做出决策、框架开始执行；`tool.finished` 意味着代码执行完毕、结果喂回模型。后续开发你会自己造出这样一对事件。

### 步骤 6：走一次人工审批

/chat 页选 `customer-service-bot`，输入（**退款原因要一起说**，模型按 SOP 会先查证）：

```
我要退订单 ORD-1006 的款，899 元，质量有问题，键盘按键失灵
```

预期结果：聊天气泡里出现**「批准 / 拒绝」按钮**——899 元超过 500 元的审批线，`refund_apply` 是高风险工具，代码拦下执行等人点头。点「批准」，退款真实执行（Mock 服务返回退款单号），对话继续。整个过程在事件流里是 `tool.approval.requested` → 你点按钮 → `tool.approval.resolved`。

注意谁在拦你：不是模型"自觉"不退款，是代码闸门。让模型在 Prompt 里"承诺"不乱花钱，「Agent 基础概念」就说过——拦不死。899 元这笔退款被拦下，靠的是 `refund_apply` 工具声明里的一个字段，由框架在执行前强制检查。「编写业务工具」你会自己写一个这样的高风险工具，`approval_required=True` 一个参数的事。

也请记住这个体验的完整链路，它是你在生产里向业务方解释“AI 不会乱来”时的标准叙事：模型决定发起 → 代码判定高风险 → 拦下等人 → 人批准 → 真实执行 → 全程留痕。每一环都可审计，没有一环依赖模型的自觉。

### 步骤 7：换脑演示——改映射不改代码

把 smart 槽位换绑到 fake（演示换脑链路本身）：

```bash
curl -X PUT http://localhost:8000/v1/brain-mappings -H "Content-Type: application/json" \
  -d '{"profile": "smart", "model_key": "fake-chat"}'
```

调试台再问小图"你是谁"——回到固定台词。再换回来：

```bash
curl -X PUT http://localhost:8000/v1/brain-mappings -H "Content-Type: application/json" \
  -d '{"profile": "smart", "model_key": "deepseek-chat"}'
```

预期结果：两次换绑之间，小图的 YAML、数据库里的定义、代码——**一个字都没动过**，行为却整个切换了。这就是"换模型 = 改库映射"的实感。也可以将第二个真实模型绑定到 cheap 槽，再对比输出与费用。

顺带你也该发现了：**换脑是即时的、按对话生效的**。换绑之前已经在跑的对话不受影响，新起的对话立即走新模型。生产上做灰度切换、故障降级，用的就是这同一个动作。

### 步骤 8：验证重启不打回（重要）

这个坑值得专门验证一次：很多人配好真实模型后，某天重启了服务，发现"怎么回复又变回假台词了"——那是老版本 init 的行为（无条件覆盖槽位）。现在不是了：

```bash
bash scripts/dev.sh restart
```

预期结果：重启后再问小图，仍是真模型回复（smart 槽位还是 deepseek-chat，工作台模型页可查）。`luban init` 的播种**只填空位**：槽位上有映射就不动，空槽位才填 fake 兜底。重启自由了。

"只填空位"这四个字是播种语义的关键：`luban init` 的职责是让系统**开箱能用**（空槽位给 fake 兜底），不是**替你做决策**（覆盖你已绑定的真实模型）。「部署与升级」部署上生产后，这条语义是你在服务器上放心重启的前提。

这也是一条通用的设计品味：**播种（seed）和配置（config）必须是两种操作**。播种管“从无到有”，幂等地填空白；配置管“从有到优”，由人显式决策。两者混在一起——比如 init 顺手覆盖已有映射——就是“重启后配置丢了”这类经典事故的根源。

### 步骤 9：算一次对话的成本

工作台 **Traces 页**，点开刚才小图那次"你是谁"的 Run。

预期结果：Token 消耗（输入/输出）与费用。拿计算器验一下：费用 ≈ 输入 token ÷ 1000 × 0.002 + 输出 token ÷ 1000 × 0.008（0.002/0.008 是写作时的价格，换成你注册时填的单价算）。一次人设对话大约几厘钱，实际消耗取决于模型、输入与调用次数。如果显示 0，检查注册模型时 `params` 里的单价字段是否填了。

对上了吗？对上了，开头的第 3 题就有答案了：框架从没问过 DeepSeek——**每次 Run 结束时 Token 消耗就记进了 Trace，乘以你注册模型时填的单价，费用是本地算出来的**。这也是为什么单价没填，费用就显示 0：不是查询失败，是根本无从计算。

把这次验证变成习惯：以后每次换模型、调参数、改人设，都去 Traces 里看一眼费用变化——**成本不是月底对账的事，是每次改动的事**。「部署与升级」部署上生产后，这个习惯就是你的成本护栏。

- [ ] 模型注册进工厂，smart 槽位绑到 deepseek-chat
- [ ] 小图用真模型按人设说话（步骤 4）
- [ ] 事件流里亲眼看到 tool.started / tool.finished（步骤 5）
- [ ] 大额退款在 /chat 走完「审批按钮 → 批准 → 执行」（步骤 6）
- [ ] 换绑槽位两来回，Agent 定义零改动（步骤 7）
- [ ] 重启后真实模型绑定不被打回（步骤 8）
- [ ] Trace 里能读出 Token 与费用（步骤 9）

对照开头的三个问题：它们分别落在目标 1（槽位）、步骤 1-2（Key 的位置）、步骤 9（费用的来源）——学完可以回头验收自己的猜测。

清单用法：不是扫一眼，是逐条动手验——每一条都对应一个步骤的具体输出。八条里任何一条对不上，回对应步骤重走；带着“大概对了”进入后续开发，欠的账会在后面连本带利讨回来。

## 4. 常见问题

先给一个排障心法：本文的问题几乎全出在三处——`.env`（Key）、模型注册参数（单价、变量名）、槽位映射（绑到哪了）。报错先对号入座，九成不用翻日志。

**配置后报 CONFIG_ERROR 找不到 Key。** 检查 `.env` 里的变量名与注册模型时的 `api_key_env` 完全一致（大小写敏感）；改完 `.env` 要重启服务（环境变量在进程启动时读入）。

**查订单"连接失败"。** Mock 业务服务（9100）没起。见步骤 5 的说明——`dev.sh` 不会自动起它，需要单独跑。

**退款对话里模型只说不做，没有审批按钮。** 看输入里是否带了退款原因——模型按 SOP（查证→算金额→提交）走，信息不全它会先追问而不是直接提交退款工具。这是设计行为，不是故障。

**Trace 费用显示 0。** 注册模型时没填 `input_price_per_1k` / `output_price_per_1k`。补上（PUT 重新注册即可），下一次 Run 就有费用了。

**重启后又变假台词。** 确认你看到的"假台词"不是第 7 步自己换绑 fake 的残留——查一下当前映射 `curl http://localhost:8000/v1/brain-mappings?env=dev`。确实是 init 打回去的话，那是遇到了 bug，提 Issue。
