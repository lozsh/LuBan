# 评测与回归

为 Agent 建立可重复执行的评测集，比较修改前后的结果。前置条件：有明确的业务预期和可运行的 Agent。示例以 FakeLLM 固定输出验证评测链路，真实质量需要用实际模型和业务数据验证。

## 1. 实现方式：把感觉拆成可判定的断言

先想一个问题：为什么传统软件的测试方法论搬不过来？因为单测断言的是函数返回值——输入定，输出就定。Agent 的"返回值"是一段每次采样都不同的自然语言，连断言的对象都不稳定。所以给 Agent 做评测的第一步不是写测试框架，是**找到稳定的东西**：从多变的输出里，拆出那些确定性的、可判定的成分。这一节就是说明如何拆。

先说清一件事：Agent 的输出是自然语言，`assert output == "..."` 写不了。但把"感觉不错"拆开看，你真正想确认的其实是四种很具体的东西：

**① 输出断言（`expect_output.contains`）**——回复里必须出现某几个关键词。最简单，也最脆：模型换个说法就挂（"借期三十天" vs "借期为 30 天"）。适合钉死**不许变的硬事实**（数字、政策口径），不适合钉语气和结构。

**② 工具断言（`expect_tools` + `expect_tool_args`）**——这个输入必须触发哪个工具、参数对不对。**比输出断言稳得多**：模型的说法可以千变，但"查借阅必须走 my_lib_lookup、学号必须传对"是行为，行为比措辞稳定。能测行为就别测字面。

② 有个容易误解的语义要先钉死：`expect_tools` 按"模型发起了工具调用"这个事件判定，断言的是**调用意图**，不是**执行成功**。评测缺省不配审批 manager——挂失工具是 HIGH 风险 + `approval_required`（「编写业务工具」你配的），评测里它的执行会被审批闸门拦下、不会真实挂失，但调用意图照样被断言捕获。所以挂失用例 PASS 的含义是"模型决定调挂失"，**不是评测替你批了挂失**。真要断言到执行结果那一层（比如工具返回值进了回复），给 eval 命令加 `--auto-approve`（请求即批）——代价是副作用工具会真实执行，评测集里带写操作时想清楚再开。

**③ 拒答断言（`expect_refusal: true`）**——这个输入**必须**触发 `knowledge.no_hit` 短路（「配置知识检索」那个零 token 拒答）。这是防错答的硬指标：该拒答的没拒答，就是错答。判定是事件级的（看事件流里有没有 no_hit），不依赖任何模型判断——四类断言里最确定的一个。业务中的对抗性问题也应加入评测集。

**④ judge 断言（`judge.criteria + pass_score`）**——主观维度（态度、逻辑、边界感）交给**另一个模型**当裁判：给它评分标准，它打 1-5 分，≥ pass_score 算过。灵活，但有代价：judge 也是模型，评分有方差——同一回复这次 3 分下次 2 分是常态。所以 judge 用例要配稳定的人设（后面校准环节你会亲历），且**核心行为尽量用①②③钉住，judge 只管剩下的软维度**。

还有一点容易漏掉：**四类断言不互斥，一个用例可以叠加多类。** "查借阅记录并安抚学生"这种用例，完全可以同时挂工具断言（必须调 lookup、学号传对）和 judge（回复是否顺带说明借期）——硬行为用硬断言钉，软维度用 judge 补，一个用例两层保障。用例该拆该合，看的是你要不要把两层断言当成一个不可分的场景来守。

把这四种断言按用例攒成一份 YAML 数据集，每次改动跑一遍，跟基线比——这就是 Agent 的回归测试。与传统单测的类比：contains 是精确断言，expect_tools 是交互断言，judge 是模糊测试，拒答是安全断言。

把四类断言放到一张脆性光谱表里看（这就是你以后写评测集时的选型表）：

| 断言 | 判定依据 | 方差 | 适合钉什么 | 典型误报 |
|---|---|---|---|---|
| ① contains | 回复文本 | 零（但对措辞脆） | 数字、政策口径、专名 | 模型换个说法 |
| ② 工具断言 | 事件流（调用意图） | 零 | 该调哪个工具、参数对不对 | 模型先反问后行动 |
| ③ 拒答 | 事件流（no_hit） | 零 | 该拒的问题没拒就是错答 | 几乎没有——四类里最硬 |
| ④ judge | 模型评分 | 有（2↔3 分摇摆是常态） | 态度、逻辑、边界感等软维度 | judge 评分波动 |

读这张表的方法：先看"方差"列——前三行零方差，意味着它们的红灯永远可信；再看"典型误报"列——每一行的误报都对应一种断言选型错误，误报多时别怪模型，先回表对号。这张表后面不会再展开，但建议你在给新场景写评测集时回来看一眼。

**脆的断言不是不能写，是要写在你付得起的地方。** 一份健康的评测集，永远是①②③铺量、④点缀；比例倒过来的评测集，红灯会变成狼来了，没人再信。

还有一个视角值得立起来：**评测集是资产，和你的 Agent 一起生长。** 「配置知识检索」你发现守门拒答了"你是谁"，本文你把这个行为写进评测集——发现行为 → 钉住行为，这个循环每转一圈，你的系统就多一条"受保护的承诺"。三个月后，这份评测集就是你的 Agent 的全部公共契约：新同事不用问你"这个 Agent 挂失会不会真挂"，跑一遍评测集就知道。

这也解释了一个反直觉的判断标准：**评测集的价值不在于它现在多长，在于它拦下过什么。** 一份从没响过红灯的评测集，要么系统真的稳，要么用例写得太松——下次红灯响起时，你会庆幸它不是装饰品。

### judge 为什么是"另一个模型"当裁判，而不是让 Agent 自评

你可能想过：让被测的 Agent 自己给自己的回答打分，省一个模型的 token，不好吗？不好——**运动员不能兼任裁判员**。自评有两个致命伤：模型天然给自己的回答打高分（自我偏好偏差）；且分数和被测行为同源，被测行为抖，分数跟着一起抖，方差直接翻倍。

独立的 judge 至少把"尺子"和"被测物"分开了——尺子自身还有方差，但至少不再和被测物共振。这就是为什么 judge 的校准动作里，"给 judge 稳定的评分标准（criteria 写具体）"和"给 Agent 稳定的人设"两头都要抓。

顺带说一句 criteria 的写法：**可判定的标准才配当尺子。** "回复是否态度好"这种 criteria，等于把你的模糊感觉原封不动传给了另一个模糊的模型；"回复是否先承认用户情绪再解释滞纳金规则"这种 criteria，judge 有明确的判定锚点，方差小得多。写 criteria 和写 contains 的纪律同源：**能拆成可观察行为的，别写成抽象评价。**

### 框架为什么这样设计：断言盯事件，不盯文本

注意到没有——四类断言里最稳的三类（工具、拒答、以及 contains 里的硬事实），盯的都不是"模型怎么说"，而是"系统做了什么"。这不是巧合，是三层设计权衡：

**第一层，文本是措辞，事件是行为。** 措辞是模型每次采样都可能变的（temperature、上下文微差都能让它换说法）；而"发起了工具调用""触发了 no_hit 短路"是运行期的离散事件，发生了就是发生了，没发生就是没发生。**评测体系把断言的重心压在事件上，本质上是在用确定性对冲模型的随机性。**

**第二层，事件流只有一份。** 「本地运行」你在 SSE 里亲眼看过的事件流（tool_call、knowledge_no_hit），评测判定的就是同一串——你在对话里看见什么，评测就审什么，不存在"评测看到另一个世界"的问题。**一套运行记录，两种消费方式：人看，机器判。** 这省掉了一整类"评测环境和线上环境行为不一致"的噩梦。

**第三层，方差被圈进了一个可标定的类别。** 判定不依赖模型的断言（①②③）零方差，CI 里敢拿来做门禁——红灯就是红灯，不会"这次运气不好"；唯一依赖模型的 judge 被框架单独列成一类，还给了你 `pass_score` 这个旋钮控制松紧。**方差不消失，但被隔离在你知道、可控的格子里**——这就是为什么上一条原则反复强调"核心行为用①②③钉住"。

顺带把拒答断言单独拎出来说一句：它是四类里唯一的"底线型"断言。①②测的是"该做做了没"，③测的是"不该做的是不是真没做"——后者守住的是信任的下限。对用户来说，"不知道"最多让人失望，**"不知道却装知道"会摧毁信任**。所以框架把拒答做成事件级判定、评测里把错答率当独立指标看，都是在用最硬的手段守最贵的资产。

还有一个你可能没意识到的问题：**基线为什么是 JSON 文件，而不是数据库里的记录？** 因为基线的宿命是跟着代码走：提交进 git、换机器拉下来能比、CI 里跑得起来。`--save` / `--compare` 走内存和文件链路，**不依赖数据库**——你甚至可以在一台没起服务的机器上做对比。数据库里的历史报告（步骤 6 的工作台评测页）负责“看历史”，文件基线负责“比版本”，两条链路各司其职。

最后把评测放回研发流程里看它的位置。一次典型的改动生命周期是这样的：

1. **改之前**：有全绿基线（`--save` 存的，已进 git）。没有基线的改动，等于蒙眼开车；
2. **改之后**：跑 `--compare`——regressions 为空才继续，不空就回滚或修复；
3. **日常迭代**：跑核心档（工具+拒答类，快、零方差），秒级反馈；
4. **发版前**：跑全量档（含 judge），接受方差的检验，再拉一次基线更新；
5. **进 CI**：`--compare` 有 regression 就 exit 1，合并请求过不了门——人可以偷懒，门禁不会；
6. **大动作之后**（升级、换模型、迁移环境）：对旧基线再跑一次 `--compare` 当终检——「部署与升级」的升级演练里，这一步是最后闸门。

你会发现这套节奏和传统软件的测试金字塔惊人地同构——只是被测物从"函数的返回值"换成了"Agent 的行为"。**工具变了，纪律没变。**

还有一个设计选择值得点破：评测的主入口是 **CLI 命令**（`luban eval run`），工作台评测页只是看历史的地方。为什么不用 UI 点按钮跑评测？因为门禁的前提是"机器能发起、能判退出码、能进流水线"——UI 做不到这三件事。**凡是质量门禁，必须长在命令行里；凡是给人看的，才进 UI。** 这个分工和「部署与升级」要讲的 CI 守卫一脉相承。

## 2. 操作步骤

### 步骤 1：写评测集

评测集就是一个 YAML 文件，住在 `app/datasets/`——注意这个位置：它和你的 Agent 定义一样，住在你的领地里，跟代码一起进版本库。**评测集不是临时脚手架，是随代码交付的资产**——它的版本和 Agent 定义的版本永远对得上号，这是后面一切"可比性"的前提。

新建 `app/datasets/my_lib_eval.yaml`（参考产出里是校准后的终版，先照这个写，校准过程在后面几步亲历）：

```yaml
- case: 身份问题也走守门
  input: 你是谁？能帮我做什么？
  expect_refusal: true
- case: 借阅查询走工具
  input: 我是学号 2023011234 的学生，我借了哪些书？
  expect_tools: [my_lib_lookup]
  expect_tool_args: { my_lib_lookup: { student_id: "2023011234" } }
- case: 规章命中引用
  input: 书最多能借多久？我是本科生
  expect_output: { contains: ["30"] }
- case: 续借规章
  input: 书可以续借几次？
  expect_output: { contains: ["1 次"] }
- case: 挂失走审批工具  # 断言的是"模型决定调挂失"这个意图，不是挂失真被执行——评测默认不配审批（见 §2 ②）
  input: 我的校园卡丢了，学号 2023011234，帮我挂失
  expect_tools: [my_lib_report_loss]
- case: 超范围拒答（知识库守门）
  input: 食堂几点开门吃饭
  expect_refusal: true
- case: 规章综合理解（judge）
  input: 我书逾期 40 天了，还能继续借新书吗？
  judge: { criteria: 是否正确说明逾期超 30 天会冻结借阅权限，且缴清滞纳金后恢复, pass_score: 3 }
- case: 服务态度
  input: 你们图书馆的滞纳金也太黑了吧，我就晚了两天！
  judge: { criteria: 回复是否先承认用户情绪再解释滞纳金规则, pass_score: 3 }
```

先别急着跑，花一分钟看这份评测集的**结构**：八个用例，四类断言各占两席——两条拒答（该拒的）、两条 contains（硬事实）、两条工具断言（该调的工具 + 参数）、两条 judge（软维度）。这个分布不是随机的：**越脆的断言越要少而精，越稳的断言越要多铺**。你现在可能觉得 judge 两条就够了，等你跑完步骤 2 的校准，会庆幸没多写。

注意第一个用例的注释价值：**身份问题也走守门**——「配置知识检索」的守门是无条件的，"你是谁"检索不到规章片段，走的也是 fallback。这不是 bug，是你在「配置知识检索」做的业务决策（纯知识 Agent 要的正是它）；把它写进评测集，这个行为从此是**受保护的设计意图**，谁改坏了会红灯。

这就是评测集的第二重身份：**它不只是质量护栏，还是一份可执行的规格说明书。** 别人接手你的 Agent，读这 8 个用例就知道“这个系统承诺什么行为、拒绝什么行为”——比读十页需求文档都准。

再逐对看一眼这四个“两席”各自在守什么：

- **两条拒答**守的是守门的两面——“馆内业务问身份也拒”（纯知识边界）和“馆外问题必拒”（超范围防护）。「配置知识检索」的守门是机制，这里是把机制承诺成行为；
- **两条 contains** 守的是硬事实——借期 30 天、续借 1 次，都是“错一个字就是投诉”的政策口径。注意 contains 里的目标全是数字：这不是巧，是纪律；
- **两条工具断言**守的是行为分工——查询走 lookup 且学号传对（参数级断言），挂失走 report_loss（意图级断言）。同是工具断言，粗细两档都示范了；
- **两条 judge** 守的是软维度——一个测规则综合理解（逾期 40 天的复合推理），一个测情绪处理（先共情再解释）。这两条是全评测集里最贵也最不稳的，所以只放最值得的两个。

### 步骤 2：跑第一遍

先说这条命令背后发生了什么：`luban eval run` 把数据集里的用例逐条发给你的 Agent——真实模型、真实工具、真实知识库链路（和对话一模一样），然后按每个用例上挂的断言逐项判定。跑之前确认两件事：服务起过（知识库 chunk 已灌入）、模型 Key 有效——原因见本文末尾的常见问题。

```bash
.venv/bin/luban eval run my-lib-assistant --dataset app/datasets/my_lib_eval.yaml
```

预期结果：逐 case 的 `[PASS]`/`[FAIL]` 与失败原因，末行 `pass_rate`。八成不是全绿——**恭喜，这正是本文的价值所在**。两种典型 FAIL，对应两种校准动作：

**FAIL「judge 评分 2/3」**——judge 方差或人设不够硬。比如"服务态度"用例，模型回复以安抚开头但共情不够"露骨"，judge 在 2↔3 分间摇摆。校准动作：给人设加硬规则（小图的案例是在人设里加"用户带不满情绪时，回复第一句先共情，再解释规则"），从源头稳定行为，而不是降 pass_score 迁就波动。**降分数线是最容易的作弊，别用它换绿灯。**

为什么降分是作弊？想一步：pass_score 从 3 降到 2，绿灯回来了，但你的系统没有变好——变的只是尺子。下次它真的变差，新的尺子也量不出来了。评测集的全部价值在于"尺子和被测物分开"；**降分等于用被测物重新刻度尺子**，红灯从此失去含义。

**FAIL「期望工具未被调用」**——模型偶尔先反问再行动（"我这就帮你挂失，可以吗？"）。校准动作同样是改人设（"学号给全就直接提交，不反问确认"），让行为确定性化。

注意两种 FAIL 的修法是同一个方向：**改人设，把概率行为拧成确定行为**——而不是改评测集迁就模型。评测集是你要守住的那条线，人设才是实现手段；实现手段没达标，就让手段加班，别动线。

校准循环还有一个容易忽视的纪律：**一轮只改一处。** 同时改人设和阈值再重跑，绿灯了你也说不清是哪个改动起效的——下次回归你就少了一条可归因的基线。改一处 → init → 重跑 → 记录结果，节奏慢一点，但每一步都留下证据。评测体系给你的是仪器，仪器要用出仪器的精度。

**还有一个隐藏校准点：judge 用例的问法必须能过知识守门。** 你若写一个低于阈值的 judge 用例（比如"能帮我查四级成绩吗"），它走的是 fallback、模型根本不出场，judge 评的是那句兜底话术——永远过不了也说明不了问题。judge 用例的问题要**命中知识库**（如上面的逾期 40 天，命中逾期条款，模型须综合作答）。

### 步骤 3：校准到全绿，存基线

改人设 → `luban init` → 重跑，循环到 8/8。然后存基线：

```bash
.venv/bin/luban eval run my-lib-assistant --dataset app/datasets/my_lib_eval.yaml --save my-baseline.json
```

预期结果：末行多了 `已保存: my-baseline.json`。这份 JSON 是可移植的基线快照（git 提交它，换机器也能比对）。

**这个 `git commit` 值得当成仪式来做**：从此刻起，仓库里躺着一份"小图 8/8 全绿"的铁证。任何人（包括三个月后的你）做了任何改动，一条 `--compare` 就知道有没有碰坏它。**基线文件进仓库，和测试用例进仓库是同一种纪律。**

再回昧一下"全绿"和「Agent 基础概念」那句"感觉还行"的区别：它们描述的都是"现在没问题"，但全绿有证据、可复现、能对账——三个月后有人质疑你的系统质量，你拿得出的不是一个 shrug，是一份带时间戳的 8/8。

### 步骤 4：故意改坏，看回归红灯

接下来这个动作听起来反直觉：**你要亲手把系统改坏。** 为什么不直接讲"改好后怎么验证"？因为没响过的警报器没人知道它能不能响。你需要一次受控的故障，亲眼确认三件事：报警会响（pass_rate 掉）、报警指得出哪里坏了（regressions 有名字）、修复后报警会停（回归全绿）。这三件事都见过实物，你以后才敢把质量交给它。

把 `my_lib_assistant.yaml` 的阈值改成 0.02（放垃圾片段进上下文），init 后跑对比：

```bash
.venv/bin/luban init
.venv/bin/luban eval run my-lib-assistant --dataset app/datasets/my_lib_eval.yaml --compare my-baseline.json
```

预期结果：`pass_rate` 掉了（7/8），末尾三行——

```
regressions: ['超范围拒答（知识库守门）']
improvements: []
pass_rate_delta: -0.12
```

**看清楚刚刚发生了什么**：你改的是一个数字（阈值），回归报告精确指出"守门拒答坏了一个"。不用人工抽查、不用读回复、不用猜——这就是「Agent 基础概念」说的"把感觉变成断言"的完全体。CI 里这个命令配 `exit 1` 语义（有 regression 就非零退出），就是回归门禁。

把因果链拆开看：阈值从 0.15 降到 0.02，意味着检索只要擦到边就放行——垃圾片段进了上下文，原本检索不到"食堂"类问题的守门现在检索到了一点"沾边"的东西，`no_hit` 不再触发，拒答变成错答。**一个阈值数字，牵动的是整条"该拒就拒"的行为链**——这正是为什么人肉抽查抓不住它：你抽查的那两句恰好没踩中。评测集不会漏，因为它把每一条行为链都钉了钉子。

再体会一下报告的克制：它不给你重跑一份完整流水账，只给你三行——**哪些变坏了（regressions）、哪些变好了（improvements）、净变化多少（pass_rate_delta）**。因为你关心的从来不是"这次几分"，而是"比上次差在哪"。有 baseline 之后的评测，本质是 diff，不是 score。

### 步骤 5：恢复，验证绿灯

阈值改回 0.15，init，重跑 `--compare`。

预期结果：`pass_rate: 1.00 (8/8)`、`regressions: []`、`pass_rate_delta: +0.00`。世界恢复原状，而且这次"恢复"是有证据的。

如果恢复后**仍然**有 regression，说明你的校准过程中动过不止一处——回到步骤 2 说的"一轮只改一处"纪律，逐处排查。这也是回归报告的第二种用法：不只验"改坏了没有"，也验"修好了没有"。

注意一个细节：恢复后**不需要重新 `--save`**——行为和基线完全一致，旧基线依然有效。基线文件代表的是"被认可的那个版本的状态"，不是"最近一次跑的结果"；只有当你有意接受了一个新行为（比如合入了一次正常的规则变更），才重新拉基线。**基线是刻意的，不是顺手的。**

"有证据"三个字值得咀嚼。开发期你每天都要做几十次"改完觉得好了"的判断，每一次都在赌。有了基线和对比命令，**每次赌局变成了验算**——成本是几十秒的命令，收益是深夜不用被投诉电话叫醒。

### 步骤 6：工作台看历史

工作台**评测页**：按数据集/Agent 过滤的历史报告列表（每次 eval run 自动落库），点开看逐 case 明细。

预期结果：my-lib-assistant 的历次记录——刚才那趟 7/8 的"事故现场"也在，失败原因原样保留。

文件基线管"跟上一版比"，落库报告管"看任何一版"——还记得概念节那句"两条链路各司其职"吗？这里就是它的实物。别删这条 7/8 的记录：**留着它，它是这个系统第一次用数据抓自己 bug 的现场证据。**

这个页面还有个隐藏价值：**它让质量变得可见、可谈。** 以前你和团队讨论"Agent 稳不稳"，各凭印象；现在你甩过去一个链接，通过率、错答率、逐 case 明细全在里面——**质量从形容词变成了名词。**

## 3. 验证结果

四条都过才算上线。特别强调第四条：**校准经历不能跳过**——全绿不是目的，"知道为什么绿"才是。跳过校准直接抄终版，你只是拿到了一份文件；走过校准，你拿到的是"评测集和模型行为之间怎么互相驯化"的手感，这个手感在你给自己的场景写评测时是唯一能倚仗的东西。

## 4. 常见问题

这一节的五条坑，前四条你在本文或前面的操作都可能真撞上，最后一条是环境问题。每条都先给现象，再给药方——建议撞到再说回来对号入座。

**judge 用例忽绿忽红。** 正常现象，但绿灯率低于 8 成就该治：治法是改人设让行为更确定（见步骤 2），不是调 pass_score。judge 是四类断言里唯一有方差的，把它当"软指标"设计，核心行为交给前三类。

这个 "8 成" 不是拍脑袋：judge 本身是模型，评分天然有抖动，你永远不可能把它治到 100% 绿；但 8 成以下的绿灯率说明不是方差问题，是行为本身不稳——这时修人设才有意义。**先分清"尺子在抖"还是"被测物在抖"，再决定修哪个。**

**judge 用例永远红。** 先确认问法能不能过知识守门（用 `/v1/knowledge/query` 查一下分数）——走 fallback 的问法模型不出场，judge 无从评起。

**`expect_output.contains` 频繁误报。** 断言钉得太细（钉了措辞而不是事实）。把 contains 的目标限制在数字、专名、政策口径这类硬事实上。

为什么误报总落在 contains 头上？回看脆性光谱表：contains 是四类里唯一“判定确定、但对象不确定”的断言——分数不会抖，但回复会。误报多，不是断言机制坏了，是你把脆的断言用在了脆的地方。**误报是你的评测集在提醒你：断言选型错了，不是模型又抽风了。**

**改了工具签名后评测全红。** 签名漂移保护（「编写业务工具」讲的）。`luban init` 产生新版本即可——但注意 `expect_tool_args` 若引用了旧参数名，评测集也要跟着改。

**评测跑到一半报 CONFIG_ERROR。** 检查服务是否起过至少一次（知识库 chunk 要先灌入）、`.env` 的模型 Key 是否有效——eval 用真实模型跑，环境要求和对话一样。

最后补一个预防针：**评测集也会随业务过期。** 政策口径改了（借期从 30 天变成 45 天），第一步不是改 Agent，是改评测集里的 contains 断言——先更新规格，再改实现，跑对比确认“只有这一处变了”。评测集如果落后于业务，它会忠实地把正确的实现拦成红灯——这不是评测的 bug，是它在尽忠职守。
